---
description: 設計を独立マージ可能なPR単位に分割し、GitHub issue 化する
argument-hint: [設計書のパス or 設計の要約] [元の issue 番号 (任意)]
---

対象: $ARGUMENTS (設計書のパスが渡された場合は全文を読む)

**元の issue**: 引数に issue 番号・URL があるか、設計書が元の issue を明記している場合だけ、それを親とする。どちらにも無ければ親は無しとし、タイトルや内容の近さから推測で結び付けない (無関係な issue に子が付くため)。

設計された実装を、独立してマージ・テスト可能なPR単位に分割してください。レビュー単位が小さいほどレビュー精度が上がる ([Google Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html))。セッション内のタスク分解は superpowers:writing-plans の担当であり、このコマンドが扱うのはPR/issue 単位 (チーム・セッション横断の成果物単位) の分割のみ。

**分割の原則**:

- 縦切り (機能スライス) で切る。層ごとの横切り (モデル層だけ・UI層だけ) は単体でマージ・検証できないため禁止
- 各単位は「それ単独でマージしてもプロジェクトが壊れない」こと。依存があるなら順序を明示する
- 目安: 1単位 = 変更5ファイル以内。設計書の「構成と責務」の境界を第一の切り口に使う
- 分割しても1単位で済む規模なら「分割不要」と報告して終了する

**分割案の提示** (issue 作成前に必ずユーザーへ見せる)。各単位について:

1. タイトル (日本語。そのまま issue タイトルになる)
2. スコープ: 含む変更と、触るファイルの見込み
3. 完了条件: 単独でマージ可能と判断できる検証内容
4. 依存: 先行してマージが必要な単位 (なければ「独立」)

**issue 化**: 分割案を AskUserQuestion で確認し (issue を作成する / 分割案のみで終了。「依存」がそのまま blocked by として登録されることも示す)、承認された場合のみ `gh issue create` で作成する。作成の前に、各単位のタイトルの主要語で `gh issue list --search '<キーワード>' --state all --limit 100` を起票とは別のコマンドとして実行し、結果ごとに次のどれかに決める:

- 重複する issue がある: 作成せず、その番号を報告する
- 検索のコマンドが失敗した (終了コードが0でない): 重複なしとはみなさず、作成しない (失敗を重複なしと読むと、同じ issue を二重に作るため)
- 結果がちょうど上限の100件: その外に重複があり得るので重複なしとはみなさず、作成しない (`--limit` を付けないと既定の30件しか返らず、取りこぼしても終了コードは0のため)。キーワードを絞って検索し直すと、広いキーワードでだけ当たる重複が見えなくなるので、絞り込みで続けない
- それ以外: `gh issue create` で作成する

検索の失敗・検索の上限・作成の失敗 (`gh issue create` の終了コードが0でない) で issue の無い単位を、以下「未作成の単位」と呼ぶ。重複の単位は既存の issue があるので未作成の単位に含めない。

タイトル・本文は日本語。本文には設計書のパス・スコープ・完了条件・依存関係を記載する。

**サブ issue 化**: 親がある場合は、分割案の確認で親の番号も示し、新しく作成した issue だけを親のサブ issue に登録する (重複として報告した既存の issue は登録しない。別の親を持っていることがあるため)。`gh` にはサブ issue を作るフラグが無いので REST API を使う。`sub_issue_id` は番号ではなく issue の `id` で、整数として渡す (`-f` だと文字列になり失敗する):

```bash
id=$(gh api repos/{owner}/{repo}/issues/<子の番号> --jq .id) &&
  gh api -X POST repos/{owner}/{repo}/issues/<親の番号>/sub_issues -F sub_issue_id="$id"
```

親と子は同じオーナーのリポジトリにある必要がある。登録に失敗した issue は黙って飛ばさず、番号と理由を報告する (issue 自体の作成は取り消さない)。

**blocked by の登録**: 分割案の「依存」から決める。単位 A が単位 B の先行マージを要するなら、A を B に blocked by にする。分割案に無い依存をこの段階で足さない (承認されていない判断になるため)。依存が循環する分割案は、どの単位も着手できなくなるので issue 化の前に作り直す。依存の片側が重複として報告した既存の issue に当たる場合は、先行側でも後続側でもその既存の issue を使う (サブ issue と違い、blocked by の追加は既存の関係を置き換えないため)。`issue_id` も番号ではなく `id` を整数で渡す:

```bash
blocker_id=$(gh api repos/{owner}/{repo}/issues/<先行の番号> --jq .id) &&
  gh api -X POST repos/{owner}/{repo}/issues/<後続の番号>/dependencies/blocked_by -F issue_id="$blocker_id"
```

登録に失敗した組と、未作成の単位を片側に含む組 (登録できない) は、どちらも「未登録の依存」として、組の両側 (issue のある側は番号) と理由を報告する。黙って飛ばすと、後続側が blocked by の無いまま着手されるため。

**作成結果の確認**: 登録の応答ではなく、読み直した結果で確かめる。

- 親がある場合: `gh api repos/{owner}/{repo}/issues/<親の番号>/sub_issues --paginate --jq '.[].number'` に、作成した issue がすべて含まれる
- 作成した各 issue: `gh api repos/{owner}/{repo}/issues/<番号>/dependencies/blocked_by --paginate --jq '.[].number'` が、分割案の依存から未登録の依存を除いたものと過不足なく一致する
- 依存の後続側になった既存の issue: 同じコマンドの結果に、分割案の依存 (未登録の依存を除く) がすべて含まれる (分割前からの関係があり得るので、余分は食い違いとしない)

読み直しのコマンドが失敗した (終了コードが0でない) 場合は、一致とはみなさず「未確認」と報告する。失敗すると `--jq` は当たらず、エラーの JSON (`"status": "401"` など) が標準出力に出るので、出力ではなく終了コードで判定する (その数字を issue 番号と読み違えないため)。食い違いがあれば、番号と内容を報告する。最後に、次の3つを1つの一覧にして報告する (途中の報告だけだと、最後の一覧から抜け落ちるため):

- 読み直した issue ごと (上の確認の対象と同じ。作成した issue と、依存の後続側になった既存の issue) の番号・親 (作成した issue のみ。登録に失敗したなら理由)・blocked by・読み直しの結果 (一致 / 未確認 / 食い違いの内容)。親と blocked by は読み直した値を書き、未確認なら「未確認」と書く (分割案の値で埋めると、確かめていないものが確かめたように読めるため)
- 作成しなかった単位と理由 (重複は既存の番号、未作成の単位は検索の失敗・検索の上限・作成の失敗のどれかと詳細)
- 未登録の依存の組と理由

`gh` が使えない、または GitHub を使っていないプロジェクトでは分割案の提示のみで終了する。
