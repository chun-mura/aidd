絞り込み: $ARGUMENTS (未指定なら open issue 全件)

カレントリポジトリの open issue から、今着手できる issue (並行するなら衝突しない組み合わせ) を選んで提案してください。使うのは、次に何を実装するかが決まっていないとき (決まっているなら `/aidd:issue-implement`)。このコマンドは提案で止める。ブランチ作成・実装・issue の編集・ラベルの付け替えは行わない。`gh` が使えない場合は、その旨を報告して終了する。

## 1. 進行中の作業を先に見る

新しい issue より先に、手を付けたまま止まっている作業を洗い出す。

- ローカルブランチと worktree (`git worktree list`)。**未 push の実装済みブランチ**も含める (リモートにもPRにも現れないため、見落とすと同じ issue を二重に実装する)。次で洗い出す
  - 未 push のコミット: `git log --branches --not --remotes --oneline`
  - 既定ブランチに未マージのブランチ: `git branch --no-merged <既定ブランチ>`
- open PR (`gh pr list`) と、その PR・ブランチが対応する issue

対応する issue は、ブランチ名・コミットメッセージ・PR 本文から読み取る。どれからも導けないブランチは issue に推測で結び付けず、「対応不明」として一覧に載せる。

進行中の作業に対応する issue は候補から外し、「先に片付ける作業」として提案の先頭に置く。

## 2. ラベルは消費するだけ

引数のラベルは絞り込みに使う。候補に優先度ラベルが付いていれば、並べる順はそのラベルに従う。ラベルの名前と順序は、系列が独自に宣言した規約 (利用側の `CLAUDE.md`・`CONTRIBUTING.md`・`.github/` の issue テンプレート)、`.aidd/issue-priority.md`、`aidd:issue-priority` skill の既定 (導入されていれば) の順に探した定義に従う (既定の `priority:P0`〜`P3` なら P0 が最上位)。同じ段の中は issue 番号順にする。優先度ラベルが付いていない issue、または定義が見つからない場合は、番号順に並べてその旨を書く (ラベルの無い issue は別にまとめ、ラベルのある issue との前後は付けない)。

このコマンドは優先度の基準を持たない。ラベル以外 (タイトル・本文・他のラベル) から優先度を推し量らず、優先度ラベルを付ける・付け替えることもしない。優先度の判定と付与は `aidd:issue-priority` skill (別の PR で追加) の役割である。

## 3. 本文の冒頭と決定済みの ADR を確かめる

候補ごとに、タイトルではなく本文を読む。

- **本文の冒頭**: 前提・「先に決めること」・依存する issue が書かれていないか。書かれていて未解決なら、その issue はまだ着手できない
- **blocked by**: `gh api repos/{owner}/{repo}/issues/<番号>/dependencies/blocked_by --paginate --jq '.[] | select(.state == "open") | .number'` が番号を1つでも返せば、先行する issue が閉じるまで着手できない。候補から外し、返った番号を先行する issue として添えて報告する
- **open のサブ issue を持つ親**: 作業は子にあり、親は子がすべて閉じるまで open のまま残る。親は候補から外し、`gh api repos/{owner}/{repo}/issues/<番号>/sub_issues --paginate --jq '.[] | select(.state == "open") | .number'` が返す open の子の番号を添えて報告する。子は他の候補と同じ判定にかける (絞り込みに当たらない子は候補に足さず、番号を示すだけにする)
- **決定済みの ADR**: `docs/adr/` に、その issue を不要にした決定、または issue の方向と衝突する決定がないか (`adr-recall` skill の手順で探す)。ある場合は候補から外し、理由を添えて報告する

blocked by と親の2つは件数 (`length`) ではなく番号を出して確かめる。`--paginate` では `--jq` が1ページごとに評価され、件数だと2ページ目以降が別の行に分かれるため。コマンドが失敗した (終了コードが0でない) issue は、着手できるとはみなさない。失敗すると `--jq` は当たらず、エラーの JSON (`"status": "401"` など) が標準出力に出るので、出力ではなく終了コードで判定する (その数字を issue 番号と読み違えないため)。「依存を確認できない」として候補から外し、失敗の理由を添えて報告する。

## 4. 人の手続きが要るものを外す

着手する前に人の手続きが要る issue は外す。承認・契約・アカウントや権限の発行・外部との調整・要件の受領待ち・人が決める仕様の選択が残っているもの。外した issue は「何を誰が済ませれば着手できるか」を1行添えて一覧にする。

## 5. 衝突する組み合わせを外す

複数を並行する場合、次のどれかを共有する組み合わせは同時に選ばない (進行中の作業との間も同じ)。衝突するなら片方を後回しにし、どちらを先にするかを提案する。

- 同じ画面
- 共有部品 (共通コンポーネント・共通ライブラリ・共通設定)
- 同じモデル (エンティティ・型・スキーマ定義)
- 同じテストファイルの新規作成 (別々に作ると同じパスで衝突する)
- マイグレーションの同時進行 (順序と番号が衝突する)
- ADR の採番 (`/aidd:adr` の採番は、他の worktree で未コミットの ADR を見られないため、並行する作業がそれぞれ ADR を書き始めると同じ番号になる)

## 6. 提案で止める

次を提示して止める (対話セッションなら AskUserQuestion で着手する issue を選んでもらう)。

1. 候補: issue 番号・タイトル・本文冒頭の要約、同時に進めてよい組み合わせ
2. 先に片付ける進行中の作業
3. 外した issue と理由 (ADR・依存 (本文の前提・blocked by・open の子を持つ親)・人の手続き・衝突の別)
4. 並べ順の根拠 (どの定義の優先度ラベルに従ったか、番号順か)

選ばれた issue の実装は `/aidd:issue-implement` に渡す。このコマンドからは始めない。
