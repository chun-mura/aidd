対象の決定: $ARGUMENTS

対象プロジェクトの ADR を作成し、`docs/adr/NNNN-<slug>.md` に保存してください (NNNN は下の「採番」で決める。slug は英語ケバブケース)。ディレクトリがなければ作成する。

**採番**: チェックアウト中の `docs/adr/` だけを見ると、複数の worktree / ブランチで並行して ADR を書いたときに同じ番号が二重に生まれる。番号は本文中と他 ADR から参照されるため、マージ時に振り直すと参照の張り替えが要る。次の順に既存番号を集め、**全ソースの最大番号 +1** を使う (どこにも無ければ 0001)。

1. `git fetch --quiet` を試す。失敗したら中止せず、リモート未確認のまま採番したことを報告する
2. ローカル作業ツリー: `docs/adr/` のファイル名
3. ローカルの全ブランチ: `git for-each-ref --format='%(refname)' refs/heads/` の各 ref に対する `git ls-tree -r --name-only <ref> -- docs/adr/`
4. マージ済みリモート: `git ls-tree -r --name-only origin/HEAD -- docs/adr/`
5. 未マージのリモートブランチ (エージェントを worktree で並行実行しているなど、並行作業がある場合は必須。ブランチ数が多いと重いので、それ以外では省略してよい):

```
git for-each-ref --format='%(refname)' refs/remotes/origin/ \
  | xargs -I{} git ls-tree -r --name-only {} -- docs/adr/
```

5 を省略した場合は、未マージブランチを見ていないことを報告する。既存の番号と衝突していることが分かった時点で、まだマージしていない側の番号を振り直す。

**検討した代替案**: 番号を採らず slug だけで一意にし、番号はマージ時に振る案もある (衝突は原理的に消える)。採らない理由は、ADR は本文中で自身の番号を参照し、他の ADR や設計書・PR からも番号で参照される慣習があり、番号のない期間があると参照が成立しないため。衝突を消す代わりに、上の手順で**書き始める前に検出する**側に倒す。

**書く前に**: 決定内容に曖昧さ (どの範囲に適用するか、いつから効くか等) があれば AskUserQuestion で確認する。決定に至る文脈が会話にない場合、関連コード・既存 ADR を読んで把握する。代替案が示されていなければ自分で2つ以上挙げて比較する。

**構成**:

1. **ステータス**: proposed / accepted / superseded (superseded の場合は後継 ADR への参照)
2. **文脈**: この決定が必要になった状況。制約条件を含む。3-5行
3. **決定**: 何をどうすると決めたか。1-3行で断定形
4. **検討した代替案**: 各案を「概要 / 利点 / 欠点 / 不採用理由」で。採用案との比較が成立する粒度
5. **影響**: この決定で楽になること・制約されること・受け入れたリスク

**ルール**:
- 1 ADR = 1 決定。複数の決定が混ざっていたら分割を提案する
- 「なぜ」を優先。実装詳細は設計書 (`/aidd:design-doc`) に委ね、ここには書かない
- 過去の ADR と矛盾する決定なら、旧 ADR を superseded に更新する

**保存後**: パスを報告する。設計全体に関わる決定なら `/aidd:design-review` での検証を提案する。
