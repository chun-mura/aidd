対象 issue: $ARGUMENTS

GitHub issue を1本、着手から完了報告まで進めてください。使うのは、実装する issue が決まっているとき (候補から選ぶ段階なら `/aidd:issue-select`)。このコマンドは入口であり、計画・TDD・デバッグ・検証の進め方は superpowers の skill に、設計・レビュー・テスト観点は aidd の既存資産に委ねる。ここに書くのは、それらをどの順で、どの条件で呼ぶかという aidd の判断だけである。push・PR 作成・マージは行わない。

## 1. 着手ゲート

`gh issue view <番号>` で本文とコメントを読む。根拠にするのは issue 本文 (と本文を更新したコメント) であり、会話中の記憶や issue タイトルからの推測ではない。`gh` が使えない場合は、本文を貼ってもらうまで進めない。

- **要件の出どころ**: 要件ごとに、受領した原文 (依頼者の言葉・仕様書・引用) か、起票時の推測 (起票者の補足・「〜と思われる」) かを確かめる。推測の要件は一次情報で裏付けるまで根拠にしない。裏付けられなければ下の3分類の3つ目として扱う
- **ADR**: 関連 ADR の洗い出しと矛盾の扱いは `adr-recall` skill に従う。関連 ADR は「決定」の節を最後まで読む (見出しや冒頭の1文で判断しない。条件・例外・適用範囲は節の後半に書かれることが多い)。`superseded` なら後継 ADR を読む

## 2. 曖昧さの3分類

着手ゲートで残った曖昧さを次の3つに分け、3つ目だけを人に上げる。

1. **一次情報で決まる**: issue 本文・受領した原文・既存コード・ADR・設計書を読めば決まる。自分で調べて決め、根拠 (ファイルと行、または引用) を完了報告に残す
2. **既存の決定と衝突する**: ADR・設計書・既存テストの決定に従う。issue がその決定を覆すことを求めているなら、覆すかどうかは仕様の選択なので3つ目に回す
3. **仕様の選択が残る**: 一次情報で決まらず、選び方で挙動が変わる。選択肢ごとに「選ぶと何が起きるか」を添えて人に上げ (対話セッションなら AskUserQuestion)、決まるまでその部分に着手しない

1と2を人に上げない。調べれば決まることを質問にすると、判断の負荷が人に戻る。

## 3. レーン判定

次のどれかに当たれば**設計レーン**、どれにも当たらなければ**直行レーン**とする。変更行数では判定しない (数行でも認可やスキーマを変える変更はあり、行数が多いだけの機械的な変更もある)。

- スキーマ変更 (DB・API・永続化するデータ形式)
- エントリポイントの追加 (新しい API エンドポイント・CLI コマンド・ジョブ・イベントの受け口)
- 認可の追加・変更
- 新しい画面
- 採否の判断が残る (実装方式の候補が複数あり、どれを採るかで後戻りの費用が変わる)
- 触るファイル数が多い (目安: `/aidd:issue-split` と同じ5ファイル超)

**設計レーン**: `/aidd:design-doc` で設計書を作り、`/aidd:design-review` にかける。反復の終了条件は `review-loop` skill に従う。design-doc が規模超過を報告したら、実装に入らず `/aidd:issue-split` を提案して止める。

**直行レーン**: 設計書を作らずに4へ進む。直行と判定した理由 (上のどれにも当たらない根拠) を完了報告に1行残す。

## 4. 実装

1. `/aidd:test-perspectives` で観点を出す (直行レーンでは issue 本文、設計レーンでは設計書を対象にする)。must の観点を TDD で書くテストの候補にする。stdd が導入されていれば、ケースの導出は `/stdd:test-design` に委ねる
2. 手順が2つ以上に分かれるなら `superpowers:writing-plans`
3. `superpowers:test-driven-development` で実装する。失敗や想定外の挙動が出たら `superpowers:systematic-debugging`
4. **新規テストは前提を壊して落ちることを1回見る**。TDD の RED を経ずに足したテスト (観点から後で足したもの、レビュー指摘で足したもの) も対象にする。テストが前提にしている条件 (実装の該当行、入力の境界、依存先の応答) を一時的に壊して落ちることを確かめ、戻す。落ちないテストは何も守っていない

## 5. レビュー

`superpowers:requesting-code-review` でレビューを受け、指摘への対応は `superpowers:receiving-code-review` に、反復の終了条件は `review-loop` skill に従う。自動マージ可否の判定まで要るなら、代わりに `/aidd:autonomous-review` を使う (観点別レビューと deferred の追跡を内包するので、下の追加分のうち silent-failure-hunter と /security-review は重ねない)。

差分の性質に応じて次を足す。該当したのに実行できなかったものは、完了報告に未実行として理由とともに書く。

- **`pr-review-toolkit:silent-failure-hunter`**: 差分に例外捕捉 (`try` / `catch` / `except` / `rescue`)、既定値へのフォールバック、空配列・`null` の返却、再送出しないログ出力のいずれかがある。pr-review-toolkit が未導入なら `aidd:reviewer` に「握り潰されたエラー、沈黙するフォールバック」の観点だけを割り当てて代える
- **`/security-review`**: 差分が信頼境界を跨ぐ (外部入力、認証・認可、秘密情報、公開エンドポイント、権限設定)。設計レーンで design-review の security-reviewer が見たのは設計書であり、実装の差分ではない
- **`/stdd:mutation-check`**: 分岐・境界条件を持つロジックを変え、その正しさをテストだけが担保している。stdd が未導入ならスキップし、未実行を完了報告の残存リスクに書く

## 6. 完了条件

- **deferred**: 今は直さないと判定した指摘は、それぞれ「確定した issue 番号」か「`.aidd/review-dismissed.md` への理由つき追記 (ユーザー承認後)」のどちらかに落とすまで完了にしない (追跡先の定義は `review-loop` skill)。issue を起票するのも、棄却一覧に追記するのも人の承認を得てからにする
- **検証**: 完了を主張する前に `superpowers:verification-before-completion` に従う

## 7. PR を出す判断は人に残す

完了報告で止める。報告には、レーンと理由、3分類で自分で決めた点とその根拠、人に上げて決まった点、実行したレビューと未実行のもの、deferred の追跡先、検証コマンドと結果を書く。push・PR 作成・マージはしない。人が次を選ぶときの選択肢は `superpowers:finishing-a-development-branch` が示す。
