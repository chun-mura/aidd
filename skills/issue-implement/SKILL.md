**パスと引数と質問の扱い**: この文書の相対パスは、この SKILL.md があるディレクトリを起点にする。`$ARGUMENTS` が文字のまま残っている場合（Codex・Cursor など）は、この skill を呼び出したメッセージのうち skill 名以外の部分を `$ARGUMENTS` とみなす。`AskUserQuestion` と書かれた箇所は、ユーザーに質問するツールがあればそれを使い、無ければ質問を書いて作業を止め、回答を待つ。回答が無いまま推測で進めない。

対象 issue: $ARGUMENTS

GitHub issue を1本、着手から完了報告まで進めてください。使うのは、実装する issue が決まっているとき (候補から選ぶ段階なら `/aidd:issue-select`)。このコマンドは入口であり、計画・TDD・デバッグ・検証の進め方は superpowers の skill に、設計・レビュー・テスト観点は aidd の既存資産に委ねる。ここに書くのは、それらをどの順で、どの条件で呼ぶかという aidd の判断だけである。push・PR 作成・マージは行わない。

## 1. 着手ゲート

最初に 8 の `start` で実行IDディレクトリを作る。以下、`outcome: …` の印は、そこで止まるときに 8 の outcome.json へ書く status と reason (または質問の kind) である。

`gh issue view <番号> --comments` で本文とコメントを読む (`--comments` を付けないとコメント本文は表示されない)。根拠にするのは issue 本文 (と本文を更新したコメント) であり、会話中の記憶や issue タイトルからの推測ではない。`gh` が使えない場合は、本文を貼ってもらうまで進めない (`outcome: blocked/gh_unavailable`)。

- **要件の出どころ**: 要件ごとに、受領した原文 (依頼者の言葉・仕様書・引用) か、起票時の推測 (起票者の補足・「〜と思われる」) かを確かめる。推測の要件は一次情報で裏付けるまで根拠にしない。裏付けられなければ下の3分類の3つ目として扱う
- **ADR**: 関連 ADR の洗い出しと矛盾の扱いは `adr-recall` skill に従う。関連 ADR は「決定」の節を最後まで読む (見出しや冒頭の1文で判断しない。条件・例外・適用範囲は節の後半に書かれることが多い)。`superseded` なら後継 ADR を読む

## 2. 曖昧さの3分類

着手ゲートで残った曖昧さを次の3つに分け、3つ目だけを人に上げる。

1. **一次情報で決まる**: issue 本文・受領した原文・既存コード・ADR・設計書を読めば決まる。自分で調べて決め、根拠 (ファイルと行、または引用) を完了報告に残す
2. **既存の決定と衝突する**: ADR・設計書・既存テストの決定に従う。issue がその決定を覆すことを求めているなら、覆すかどうかは仕様の選択なので3つ目に回す
3. **仕様の選択が残る**: 一次情報で決まらず、選び方で挙動が変わる。選択肢ごとに「選ぶと何が起きるか」を添えて人に上げ (対話セッションなら AskUserQuestion)、決まるまでその部分に着手しない (`outcome: needs_input/spec_choice`)

1と2を人に上げない。調べれば決まることを質問にすると、判断の負荷が人に戻る。

## 3. レーン判定

次のどれかに当たれば**設計レーン**、どれにも当たらなければ**直行レーン**とする。変更行数では判定しない (数行でも認可やスキーマを変える変更はあり、行数が多いだけの機械的な変更もある)。

- スキーマ変更 (DB・API・永続化するデータ形式)
- エントリポイントの追加 (新しい API エンドポイント・CLI コマンド・ジョブ・イベントの受け口)
- 認可の追加・変更
- 新しい画面
- 採否の判断が残る (実装方式の候補が複数あり、どれを採るかで後戻りの費用が変わる)
- 触るファイル数が多い (目安: `/aidd:issue-split` と同じ5ファイル超)

**設計レーン**: `/aidd:design-doc` で設計書を作り、`/aidd:design-review` にかける。反復の終了条件は `review-loop` skill に従う (上限まで回しても収束せずに止めるときは `outcome: blocked/review_unconverged`)。design-doc が規模超過を報告したら、実装に入らず `/aidd:issue-split <設計書のパス> <この issue の番号>` を提案して止める (番号を渡さないと、issue-split は親を推測で結び付けないため、子がこの issue のサブ issue に登録されない。`outcome: blocked/split_proposed`)。

**直行レーン**: 設計書を作らずに4へ進む。直行と判定した理由 (上のどれにも当たらない根拠) を完了報告に1行残す。

## 4. 実装

1. `/aidd:test-perspectives` で観点を出す (直行レーンでは issue 本文、設計レーンでは設計書を対象にする)。must の観点を TDD で書くテストの候補にする。stdd が導入されていれば、ケースの導出は `/stdd:test-design` に委ねる
2. 手順が2つ以上に分かれるなら `superpowers:writing-plans`
3. `superpowers:test-driven-development` で実装する。失敗や想定外の挙動が出たら `superpowers:systematic-debugging`
4. **新規テストは前提を壊して落ちることを1回見る**。TDD の RED を経ずに足したテスト (観点から後で足したもの、レビュー指摘で足したもの) も対象にする。テストが前提にしている条件 (実装の該当行、入力の境界、依存先の応答) を一時的に壊して落ちることを確かめ、戻す。落ちないテストは何も守っていない。確かめた結果は完了報告の対応表 (7) に書く。壊しても落ちないときに多い原因は次の3つ: テスト名が述べる前提 (ロール・状態など) を入力として渡していない、「〜しない」だけを assert していて同じテストに「〜する」の対照が無い (前提とは別の理由で通る)、テストの共通設定の mock が確かめたい性質 (キャッシュ・時刻・再試行など) を消している
5. **同じ形の箇所に広げる**。守りの処理 (認可・所有の確認、入力の検証、ログに出す値の形、例外の扱い) を足す・直す・共通の関数に切り出したときは、同じ形の呼び出し元と兄弟の処理 (同じ種類のエンドポイント・ハンドラ・action) を検索し、全部に当てるか、当てなかった箇所を一覧にして 6 (完了条件) の deferred に回す。1か所だけ直すと、残りが同じ欠陥のまま「直した」ことになる。新しい処理を既存の兄弟の隣に足すときは、兄弟を1つ読み、その検証・ログ・エラー処理の決まりに合わせる
6. **テストや項目を消すとき**。テストを消す・書き換えるときは、そのテストが守っていた性質と、代わりのテスト (または不要とした理由) を完了報告に書く。API の項目や挙動を消す・改名するときは、既定のテスト実行から外れたテスト (E2E のマーカー、別ディレクトリ、別のジョブ) も含めて名前を検索する

## 5. レビュー

`superpowers:requesting-code-review` でレビューを受け、指摘への対応は `superpowers:receiving-code-review` に、反復の終了条件は `review-loop` skill に従う (上限まで回しても収束せずに止めるときは `outcome: blocked/review_unconverged`)。自動マージ可否の判定まで要るなら、代わりに `/aidd:autonomous-review` を使う (観点別レビューと deferred の追跡を内包するので、下の追加分のうち silent-failure-hunter・/security-review・横展開のレビューは重ねない)。autonomous-review が `/security-review` を未実行と記録した場合は、実装差分の監査が済んでいないものとして、完了報告に未実行として理由ごと書く。未実行の理由が対象の範囲 (作業ツリーの差分だけ、head がチェックアウトされていない) のときだけ、変更をコミットして head をチェックアウトした状態で `/security-review` を実行し、その結果を完了報告に書く (機微情報の保存に当たる差分では、下の `/security-review` の項と同じく、委譲先が除外する種類を残存リスクに書く)。理由が「監査は走ったが、監査した範囲を確かめられない (ブロックの終了コード2)」または「ブロックが1で終わった」のときは、対象の範囲の理由ではないので、自分で `/security-review` を実行し直さない (このセッションの中で実行すると、差分の本文が展開されて文脈に入るため。監査は済んでいないので、下の `/security-review` の項により完了にしない)。対象の範囲の理由で自分で実行した場合も、差分の本文がこのセッションの文脈に入ったことを完了報告の残存リスクに書く。autonomous-review が実行済みと記録した場合は重ねない。

**監査の新しいセッションを起動した run のあと**: 次のどれかに当たる場合 (autonomous-review の `report.md` の冒頭に、`/security-review` を新しい `claude -p` のセッションで動かしたという利用者への注意がある、`state.json` の `perspective_reviews` の `security` の `reason` が「新しいセッションを起動した」で始まる、このセッションで `security-review run: launching` の行を見た)、そのセッションは利用者と同じ権限で動き、このリポジトリの `.git`・hooks・作業ツリーを書き換えうる。以後このリポジトリでは、テスト・ビルド・`/stdd:mutation-check`・6 の配置の置き直し・git・`gh` (deferred の issue の起票を含む) を含め、コマンドを一切動かさない。起票が要る deferred は完了報告に書いて人に渡す。下の追加分と 6 の検証・配置の照合は、未実行として理由 (監査の新しいセッションを起動したため) を完了報告に書き、7 の完了報告で止まって利用者の確認を待つ (`outcome: blocked/audit_session_launched`)。例外として、8 の outcome の `write` だけは実行してよい (拒否されたときの書き直しを含む。git もネットワークも使わず、リンクをたどらずに実行IDディレクトリにだけ書くため)。

差分の性質に応じて次を足す。該当したのに実行できなかったものは、完了報告に未実行として理由とともに書く。

- **`pr-review-toolkit:silent-failure-hunter`**: 差分に例外捕捉 (`try` / `catch` / `except` / `rescue`)、既定値へのフォールバック、空配列・`null` の返却、再送出しないログ出力のいずれかがある。pr-review-toolkit が未導入なら `aidd:reviewer` に「握り潰されたエラー、沈黙するフォールバック」の観点だけを割り当てて代える
- **`/security-review`**: 差分が信頼境界を跨ぐ (外部入力、認証・認可、秘密情報、公開エンドポイント、権限設定)、または機微情報 (個人情報・プロンプト・認証情報など) をファイル・ログ・キャッシュに保存する。設計レーンで design-review の security-reviewer が見たのは設計書であり、実装の差分ではないので、`/security-review` の実行済みに数えない。`/security-review` が報告対象から除外する種類 (`/aidd:autonomous-review` の「委譲先が除外する種類」) は、実行しても監査されていないので、機微情報の保存に当たる差分ではその除外を完了報告の残存リスクに書く。3 で認可の追加・変更を理由に設計レーンにした変更は、常にこの項に当たる。当たるのに実行が最後まで終わらなかったとき (権限で拒否された、エラーで終わった、autonomous-review が未実行と記録し上の段落の手順でも実行しなかった、予算や時間を理由に省いた) は、監査が済んでいないので完了にしない。完了報告に未実行として理由を書き、`outcome: blocked/required_check_not_run` で止める (人が監査を実行してから完了を判断する)
- **横展開のレビュー**: 差分が守りの処理 (認可・所有の確認、入力の検証、ログに出す値の形、例外の扱い) を足す・直す・共通の関数に切り出す。`aidd:reviewer` に「同じ形の呼び出し元と兄弟の処理 (同じ種類のエンドポイント・ハンドラ・action) に同じ処理が当たっているか」の観点だけを割り当てる。4-5 は実装者自身の検索で、ここは別の目で漏れを探す。4-5 で deferred に回した箇所は一覧ごと渡し、それ以外の漏れを報告させる
- **`/stdd:mutation-check`**: 分岐・境界条件を持つロジックを変え、その正しさをテストだけが担保している。stdd が未導入ならスキップし、未実行を完了報告の残存リスクに書く

## 6. 完了条件

- **deferred**: 今は直さないと判定した指摘は、`review-loop` skill が追跡先として認めるもの (確定した Issue / ADR の番号、または `.aidd/review-dismissed.md` への理由つき追記) に落とすまで完了にしない。issue を起票するのも、棄却一覧に追記するのも人の承認を得てからにする (`outcome: needs_input/approval`)
- **配置**: 5 の「監査の新しいセッションを起動した run のあと」に当たる場合は行わず、未実行として完了報告に書く。差分の各ファイルを、設計書の「構成と責務」に書かれた配置と照らす。配置から外れたファイルと、設計が別のコンポーネントに割り当てた責務、またはどのコンポーネントにも割り当てていない責務を引き受けたファイルは、設計どおりに置き直すか、設計書の配置と責務を直して理由を完了報告に書く。責務の集中は行数ではなく、この責務の割り当てで判定する。設計書が配置を持たない場合 (直行レーン、配置を書いていない古い設計書) は、差分の周りの既存の構造を配置とみなし、各ファイル・モジュールがすでに担っている責務を割り当てとみなす。外れたものは既存の構造に合わせて置き直すか、外れる理由を完了報告に書く
- **必要な監査**: 5 の `/security-review` の項に当たる差分では、`/security-review` が最後まで実行されていること (当たらなければこの項は無い)。満たせなければ 5 の印で止める
- **検証**: 完了を主張する前に `superpowers:verification-before-completion` に従う。5 の「監査の新しいセッションを起動した run のあと」に当たる場合は、検証のコマンドを動かさず、未実行として完了報告に書く (完了を主張しない)。検証が通らず、`superpowers:systematic-debugging` でもこの実行の中で直せないときは、完了を主張せず完了報告で止める (`outcome: blocked/verification_failed`)

## 7. PR を出す判断は人に残す

完了報告で止める (6 をすべて満たしたときだけ `outcome: done`。6 を満たさずに止まり、ほかの印のどれにも当たらないとき (配置の外れを解消できない、検証を実行できない、issue 番号が無いなど) は `outcome: blocked/incomplete`)。報告には、レーンと理由、3分類で自分で決めた点とその根拠、人に上げて決まった点、実行したレビューと未実行のもの、配置の照合結果、deferred の追跡先 (4-5 で広げなかった箇所を含む)、消したテストと代わり (4-6)、原要件とテストの対応表と適用が必要な検証の扱い (下記)、検証コマンドと結果を書く。push・PR 作成・マージはしない。`superpowers:finishing-a-development-branch` はこのコマンドの中では起動しない (選ばれた選択肢に応じて merge・push・ブランチ削除まで実行する skill であるため)。人が次に進めるときに使う skill として、名前だけを完了報告に書く。

対応表は、原要件 (受領した要件) のどれを、どの設計判断・観点・テストで確かめて結果がどうだったか、または何を実装せず誰が受け入れたかを、人が issue・設計書・観点・テストを突き合わせなくて済むように書く。新しい要件台帳は作らず、出典は既にあるものを指す。

| 原要件 (出典) | 設計判断 | 観点 (優先度) | テスト (ファイル:テスト名) | 前提を壊して落ちたか | 実行結果 | 未実装の理由と人の判断 |
|---|---|---|---|---|---|---|

- 原要件の出典: reqd の要件定義書 (`docs/requirements/`) があれば、そこにある既存の番号・見出し (ユーザーストーリー・受け入れ基準) をそのまま使う。番号が無ければ、ファイルパスと見出し (または行) で指す。要件定義書が無ければ issue 本文・受領した原文・仕様書の該当箇所 (節と行、または短い引用) を書く。1 で推測と分類した要件は、一次情報で裏付けるまで原要件に数えない (裏付けたら、その一次情報を出典にする)
- 原要件は全件を載せる。1つの原要件を複数の観点で確かめたら、観点ごとに行を分ける
- 設計判断: 設計レーンでは設計書の該当する節、直行レーンでは 2 で自分で決めた点と人に上げて決まった点のうち、その原要件に関わるもの。無ければ「なし」
- must の観点は全件を載せる。どの原要件にも結び付かない must (失敗の分岐など、観点から足したもの) は、原要件の欄を「なし (観点から追加)」とする
- should / could は、テストを書いたものだけを載せる
- 既存テストでカバー済みとした観点も、そのテストのファイルとテスト名と実行結果を書く
- 「前提を壊して落ちたか」には、4-4 で壊した条件と、落ちたかどうかを書く。確かめていなければ「未確認」と書く
- 実行結果: 6 の検証で実行したコマンドと、そのテストの pass / fail。実行していなければ「未実行」と理由を書く。失敗・未実行を pass と書かない
- 未実装の理由と人の判断: テスト・実装の無い原要件と must の観点について、理由と、それを受け入れた人の判断 (2 の3つ目で人に上げて決まった点、deferred の追跡先) を書く。人の判断がまだ無ければ「未判断」と書く。「未判断」の行が残るあいだは、2 の手順で人に上げるか、6 の deferred として追跡先を決めるまで完了にしない。完了報告で止める場合は、未完了であると明記する。人に上げる質問の形にできたら 2 や 6 の印に従い、できないときだけ `outcome: blocked/undecided_rows` とする
- 「設計判断」と「未実装の理由と人の判断」の列は、上の報告項目 (3分類で自分で決めた点、人に上げて決まった点、deferred の追跡先) の該当箇所を参照する書き方でよい

E2E・移行・性能・ロールバックの検証は、原要件か変更の性質が求めるものだけを (スキーマや永続化するデータ形式の変更なら移行とロールバック、原要件に性能の条件があれば性能、原要件が利用者の操作の流れを述べていれば E2E)、表の後に実施 (コマンドと結果)・不要と判断した理由・未実施 (理由) のどれかで書く。原要件に無い非機能目標 (性能の数値など) を自分で設けず、そのための検証も足さない。

## 8. 終了状態の記録

非対話のホストが、最終テキストを読まずに「完了・質問待ち・停止」を区別できるようにする。対話セッションの手順・質問・完了報告は変えない。スクリプトは、この SKILL.md のディレクトリを起点に `../../scripts/issue-outcome.py` を解決した**絶対パス**で呼ぶ (以下 `<issue-outcome.py>`。利用側リポジトリにある同じ名前のファイルを実行しないため)。スキーマと拒否の条件はスクリプトが持つ (設計: `docs/superpowers/specs/2026-11-28-issue-implement-outcome-design.md`)。

- **開始**: 1 の着手ゲートの前に `python3 -I <issue-outcome.py> start` を1回実行し、出力された実行IDディレクトリ (以下 `<run-dir>`) を覚える。失敗したら理由を完了報告に書き、outcome を書かずに進める (ホストからは、最後まで進めても outcome が無い = 異常終了に見える)
- **書く時点**: 止まるたびに `python3 -I <issue-outcome.py> write <run-dir>` に JSON を stdin で渡す。対話セッションで質問するときは、質問の直前に書く。回答を得て続けたら、次に止まったときに書き直す (最後の書き込みが最終状態)
- **渡す JSON**: `{"issue": "<番号>" | null, "status": ..., "reason": ..., "questions": [...], "completion": ..., "artifacts": {"design_doc": <パス> | null, "test_perspectives": <パス> | null}}`。`schema_version` と `run_id` はスクリプトが付ける。パスはリポジトリのトップからの相対パス
- **質問**: `{"question", "kind", "options": [{"label", "effect"}]}` (選択肢は2〜4件、`effect` は選ぶと何が起きるか)。ホストはセッションを再開せず、回答を issue に足してから最初から実行し直すことがあるので、質問は issue と outcome だけで読める文にする (「上の案」のように会話を指さない)。委譲先の skill (design-doc・brainstorming など) が人に質問するとき、仕様の選択なら 2 の3つ目として `needs_input` (`spec_choice`) を書く。実装の進め方の選択 (計画の実行方式など) は依頼者に渡さず 2 の1つ目として自分で決める
- **status ごとの組み合わせ**: `reason` は `blocked` のときだけ値を持ち、ほかは `null`。`questions` は `needs_input` のときだけ1件以上、ほかは空配列。`completion` は `done` のときだけ値を持ち、ほかは `null`
- **done の条件**: `completion` に `{"verification": "passed", "undecided_rows": 0, "untracked_deferred": 0, "security_review": "ran" | "not_required"}` を書く。6 の検証の結果、7 の表の「未判断」の行数、追跡先の無い deferred の数を数えた値から書き、満たさなければ done にしない。`security_review` は、5 の `/security-review` の項に当たる差分で、このセッションか autonomous-review が最後まで実行したときだけ `ran`、当たらないときだけ `not_required` と書く。当たるのに実行が終わらなかったなら `ran` と書かず、`blocked/required_check_not_run` を書く (スクリプトは `ran`・`not_required` 以外の値と欠落を拒否するが、値が実態どおりかは確かめられない)
- **拒否されたら**: 終了コード1は入力が外れている。stderr の理由を見て直して書き直す。直せない、または終了コード2なら、完了報告に「outcome を書けなかった」と理由を書く (ホストからは outcome が無い = 異常終了に見える)
- 止まる理由が複数あるときは、最初に止まった停止点の値を書く。監査の新しいセッションを起動した run は、その後コマンドを実行できないので、ほかの理由があっても `audit_session_launched` を書く

| 停止点 | 印 |
|---|---|
| 1 `gh` が使えず本文が無い | `outcome: blocked/gh_unavailable` |
| 2 仕様の選択が残る | `outcome: needs_input/spec_choice` |
| 3・5 review-loop が上限まで回しても収束しない | `outcome: blocked/review_unconverged` |
| 3 規模超過で issue-split を提案 | `outcome: blocked/split_proposed` |
| 5 監査の新しいセッションを起動した run のあと | `outcome: blocked/audit_session_launched` |
| 5 必要な `/security-review` が最後まで実行されなかった | `outcome: blocked/required_check_not_run` |
| 6 deferred の起票・棄却の承認待ち | `outcome: needs_input/approval` |
| 6 検証が通らず、この実行の中で直せない | `outcome: blocked/verification_failed` |
| 7 「未判断」の行を質問の形にできない | `outcome: blocked/undecided_rows` |
| 7 完了条件 (6) を満たさずに止まり、上のどれにも当たらない | `outcome: blocked/incomplete` |
| 7 完了条件 (6) をすべて満たした | `outcome: done` |
