# 受け入れ基準と重要性質の検証 (acceptance)

[README に戻る](../../README.md) / 主張の体系: [保証条件と責任分担](contract.md) / 例: [`examples/assurance/acceptance/`](../../examples/assurance/acceptance/)

## いつ使うか

明示選択の保証構成で、主張 `AC-SPEC-001` (成果物が、原要件と業務責任者の確認に基づき、実装と独立に作られて保護された受け入れ基準を満たす) の証拠を作るとき。具体的には次の場面で読む。

- 原要件から受け入れ基準と試験を作り、実装者 (人やエージェント) が期待値を変えられない形にするとき
- 認可の越境・二重実行のように、誤った実装でも普通の動作確認は通ってしまう性質を試験にするとき
- 「試験が通った」ことを報告するときに、何を主張でき、何を主張できないかを決めるとき

通常の aidd の利用 (`/aidd:test-perspectives` やレビュー) はこの文書の対象外で、何も変わらない。要件の書き方は reqd、試験ケースの導き方は stdd が担う。この文書は両者の手順を繰り返さず、「実装と独立した正解基準」を成り立たせる条件だけを書く。

## 主張との対応

| 主張ID ([contract.md](contract.md)) | この文書と例が示すこと | 主張の判定に足りないもの |
|---|---|---|
| `AC-SPEC-001` | 原要件 → 所有者の判断 → 受け入れ基準 → 試験 の追跡、誤実装 (認可越境・二重実行) を落とし正実装を通す試験、基準の承認 digest、承認者を実装者から分ける導入手順 | 導入先の成果物・原要件・所有者の確認と、対象版での試験の実行結果。例は架空のアプリで、aidd はこの主張を `適合` と判定しない |
| `AC-SPEC-002` (参照のみ) | 性質ベース試験は有限の標本で、性質の証明ではないこと | 状態空間の探索と、モデルと実装の対応の検査は #158 (S09) が扱う |
| `AC-PRIV-008` (参照のみ) | 基準を変更対象 PR から書き換えて合格条件を消せないことが前提であること | 保護された検証元・ruleset の参照構成は #156 (S07) が扱う |

## 独立した正解基準の条件

`AC-SPEC-001` の「実装と独立」は、次の4つがすべて成り立つことを指す。1つでも欠けたら、試験の合格は「実装が自分自身と一致した」ことしか示さない。

1. **期待値の出どころが原要件か所有者の判断である。** 受け入れ基準の各行は、由来の ID (原要件 `R-*`、所有者の判断 `D-*`) を持つ。実装を動かした結果や実装の定数を期待値に写さない。曖昧な要件は実装者が決めず、所有者に質問して判断を記録する (例の `D-1`〜`D-5`)
2. **対象外を書く。** 所有者が今回決めないこと (`X-*`) を列挙し、基準もそれを主張しない。書かれていない振る舞いは主張しない
3. **観測が実装の外にある。** 二重支払いは実装自身の記録ではなく、試験が差し替えた送金先が数えた回数で判定する。例の誤実装 `DoublePayService` は自分の記録 (`payouts()`) を1件に保つので、記録だけを見る試験は通ってしまう
4. **基準の変更に所有者の承認が要る。** 原要件・基準・インタフェース・試験の digest を所有者が承認し、変更は承認者を実装者と分けた経路でだけ入る ([導入手順](#導入手順))

### 追跡の形

例では次の表で、どの期待値がどの要件から来たかを辿れる。

| 文書 | 書く人 | 中身 |
|---|---|---|
| [`requirements.md`](../../examples/assurance/acceptance/requirements.md) | 所有者 | 原要件 `R-*`、質問と所有者の判断 `D-*`、対象外 `X-*` |
| [`criteria.md`](../../examples/assurance/acceptance/criteria.md) | 基準の作成者 (実装者でない人) が書き、所有者が承認 | 受け入れ基準 `AT-*`。由来・試験の種類・Given-When-Then の期待値・適用する ASVS 項目 |
| [`api.py`](../../examples/assurance/acceptance/api.py) | 同上 | 基準が前提にする外から見える型と例外 |
| [`acceptance_test.py`](../../examples/assurance/acceptance/acceptance_test.py) | 同上 | `AT-*` 1行につき1つの試験。実装はモジュール名で読み込み、`api` 以外を import しない |
| [`approved.sha256`](../../examples/assurance/acceptance/approved.sha256) | 所有者が承認した時点で記録 | 上の4ファイルの SHA-256 |
| `impl_correct.py`、`impl_broken.py` | 実装者 | 正実装と、誤実装2つ (試験の識別力を示すためのもの) |

要件の記法 (Given-When-Then・EARS) と曖昧さの検査は reqd の `requirements-notation`・`ambiguity-lint` を、境界値や状態遷移からのケースの導き方は stdd の `test-design-methods` を使う。

## 試験の種類と、合格が示すこと

| 種類 | 例の基準 | 使う理由 | 合格が示すこと | 示さないこと |
|---|---|---|---|---|
| 例 (具体例) | `AT-FLOW-*`、`AT-AUTHZ-01`〜`05`、`AT-PAY-01`〜`03` | 正常業務と、所有者の判断ごとの振る舞いを1つずつ固定する | その入力でその結果になる | 他の入力での結果 |
| 境界 | `AT-AMT-01` | 金額の範囲 (`R-1`・`D-2`) は端で間違えやすい。stdd の同値分割と境界値分析で、1・100万・0・100万1と型の違う値を選んだ | 範囲の端と各同値クラスの代表で正しい | 代表以外の値すべて (同値クラスの仮定に依存する) |
| 性質 | `AT-AUTHZ-P`、`AT-PAY-P` | 認可の越境と二重支払いは、操作の順序と組み合わせで起きる。具体例だけでは思い付いた順序しか試せない。不変条件 (他組織の操作は状態を変えない、送金は申請ごとに最大1回) を乱数で作った操作列で確かめる | 固定した seed の操作列 (30列×80操作) で不変条件が破れなかった | すべての操作列で成り立つこと。seed は再現のために固定しており、探索の範囲は狭い |
| 障害 | `AT-FAULT-01`、`AT-PAY-P` の送金失敗 | 支払いの途中の失敗 (`R-5`) は正常系の試験では起きない。送金先を失敗させて、記録が残らないことと、やり直しで1回だけ支払われることを確かめる | 注入した失敗の位置で、状態が元に戻り、やり直しが1回になる | 注入していない障害 (プロセスの停止、永続化の失敗、複数プロセスの同時実行。`X-4`) |

性質ベース試験は外部ライブラリを使わず、Python 標準ライブラリの `random.Random(seed)` で操作列を作る。失敗したら seed と手順の番号を表示し、同じ失敗を再現できる。

**試験の合格は、全入力での正しさの証明ではない。** 報告では「固定した標本で破れなかった」と書き、「常に成り立つ」と書かない。状態空間を網羅的に探索する検査は `AC-SPEC-002` (#158) の範囲で、それも有限範囲の探索であって無制限の証明ではない。

## 適用する ASVS の項目

例は Web/API に当たるので、[OWASP ASVS 5.0](https://github.com/OWASP/ASVS/tree/v5.0.0/5.0) から、基準が直接確かめる項目を選んだ。各項目の文言は ASVS の原文を参照する。

| ASVS 5.0 | 内容 (要約) | 基準 |
|---|---|---|
| 8.2.1 (L1) | 機能単位の操作を、権限のある利用者に限る | `AT-AUTHZ-04`、`AT-AUTHZ-05` |
| 8.2.2 (L1) | データ単位の操作を、そのデータへの権限がある利用者に限る (IDOR・BOLA の防止) | `AT-AUTHZ-01`〜`03`、`AT-AUTHZ-P` |
| 8.4.1 (L2) | マルチテナントで、利用者の操作が権限の無いテナントに影響しない | `AT-AUTHZ-01`、`03`、`05`、`AT-AUTHZ-P` |
| 2.1.3 (L2)、2.2.1 (L1) | 業務上の上限を文書化し、入力をその期待に合わせて検証する | `AT-AMT-01` |
| 2.3.1 (L1) | 業務の手順を順序どおりに、飛ばさず処理する | `AT-FLOW-01`、`AT-FLOW-02` |
| 2.3.3 (L2) | 業務処理はすべて成功するか、直前の正しい状態に戻る | `AT-FAULT-01`、`AT-PAY-P` |
| 2.3.4 (L2) | 数量の限られた資源を、業務の操作で二重に確保させない | `AT-PAY-01`〜`03`、`AT-PAY-P` |
| 2.3.5 (L3) | 価値の高い処理に複数人の承認を要する (例では自己承認の禁止だけ) | `AT-AUTHZ-04` |

選ばなかった項目の例: 8.1.1 (認可規則の文書化) は基準そのもの (`requirements.md`・`criteria.md`) が満たす文書で、試験の対象ではない。8.3.1 (信頼するサービス層での強制) は例にクライアントが無いので確かめられない。2.4.1 (自動化への対策) と認証 (V6 など) は所有者が対象外にした (`X-1`・`X-4`)。導入先では、自分のアプリが満たすべき ASVS のレベルを所有者が決め、各項目を基準の行か対象外の行に割り当てる。

## 誤実装の識別

[`tests/assurance/acceptance-test.sh`](../../tests/assurance/acceptance-test.sh) が、次を機械的に確かめる (CI の `contract-tests` で ubuntu と macOS の両方)。

| 実装 | 欠陥 | 落ちるべき基準 (過不足なく一致を確かめる) |
|---|---|---|
| `impl_correct:make_service` | なし | なし |
| `impl_broken:make_cross_tenant` | 承認者と経理が他の組織の申請を見られる (組織の確認の欠落) | `AT-AUTHZ-01`、`03`、`05`、`AT-AUTHZ-P` |
| `impl_broken:make_double_pay` | 支払いのたびに送金する (再送用の鍵と支払い済みの状態を無視) | `AT-PAY-01`、`02`、`03`、`AT-PAY-P` |

ほかに、承認 digest の一致と、基準を1行足しただけで digest の検査が落ちること、`criteria.md` の `AT-*` と試験関数の一対一の対応、由来の ID が `requirements.md` にあること、すべての `R-*`・`D-*` がどれかの基準に使われていること、試験側が実装を import していないことを確かめる。

落ちるべき基準を過不足なく指定するのは、誤実装が「何かの試験で落ちた」だけでは、欠陥を捉えたのが目的の基準なのか偶然なのかが分からないからである。

手元での実行:

```bash
bash tests/assurance/acceptance-test.sh
cd examples/assurance/acceptance && python3 -B acceptance_test.py --impl impl_broken:make_double_pay
```

## 導入手順

業務上の妥当性 (この基準が業務として正しいか) は所有者が確定する。AI は質問の洗い出し・基準と試験の下書き・追跡の検査までを行い、基準を確定しない。

1. **所有者と基準の作成者を決める。** 所有者は業務責任者。基準の作成者は、その成果物の実装者 (実装を担当するエージェントのセッションを含む) と別の人か、別のセッションにする。誰が何をしたかを記録する
2. **原要件を所有者の言葉で残す。** `requirements.md` に相当する文書に、要件・対象外を所有者が書くか、所有者が確認する。reqd の `ambiguity-lint` で曖昧な点を洗い出し、質問と所有者の回答を `D-*` として残す。AI が回答を推測で埋めない
3. **基準と試験を作る。** 各行に由来の ID を付け、期待値を原要件から導く。Web/API なら ASVS のレベルを所有者が決め、項目を基準か対象外に割り当てる。試験は実装を名前で読み込み、外から観測する
4. **誤実装で識別力を確かめる。** 基準が守る性質ごとに、それを破る小さな誤実装を作り、目的の基準だけが落ちることを確かめる。落ちない基準は、試験を直すか、示せる範囲を限界に書く
5. **所有者が承認し、digest を記録する。** 承認者・承認日・承認した digest を残す (例の `approved.sha256`)
6. **変更の経路を分ける。** 基準のファイルを、所有者だけが承認できる場所に置く。GitHub なら、基準のパスの CODEOWNERS を所有者にし、ruleset で code owner の承認と最新の push 後の承認を必須にして、実装者 (エージェントの token を含む) が自分の変更を承認できないようにする。同じ PR で実装と基準を同時に変えた場合は、基準の変更として所有者の承認を要する。参照構成は #156 (S07) が示す (`AC-PRIV-008`)
7. **対象版で実行して証拠にする。** 信頼する CI で、対象の SHA に対して試験を実行し、結果を [contract.md の記録項目](contract.md#主張の記録項目) に記入する。判定者は開発の実行と分ける
8. **基準が変わったら失効させる。** 受け入れ基準の変更は [失効条件](contract.md#失効条件) に当たる。承認をやり直し、再実行するまで `AC-SPEC-001` を `未検証` に戻す

`approved.sha256` は変更の **検出** であって **保護** ではない。実装者が同じ PR で digest も書き換えれば一致してしまう。保護は手順6の承認経路が担う。

## 限界

- 例のアプリは架空で、単一プロセス・メモリ上だけで動く。複数プロセスからの同時の支払い要求、永続化、障害からの復旧は扱わない (`X-4`)。実際の二重実行対策には、データベースの一意制約やロックなど、実装の外の仕組みの検証が要る
- 例の基準は認証済みの利用者を受け取る前提で、認証は扱わない (`X-1`)
- 基準に書いていない振る舞い、性質ベース試験の標本の外、注入していない障害については、試験の合格は何も示さない
- 所有者の判断の妥当性そのもの (例: 他組織の申請に「存在しない」と返す方針) は試験では確かめられない。所有者の責任である
