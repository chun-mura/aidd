# 保証条件と責任分担 (assurance contract)

[README に戻る](../../README.md) / 記入用の雛形: [`templates/assurance-claims.md.template`](../../templates/assurance-claims.md.template)

## いつ使うか

aidd を使う開発で「安全性」「成果物の正しさ」を誰かに説明する必要があり、その根拠を主張ごとに示すとき。具体的には次の3つの場面で読む。

- 強い保証を求める構成 (隔離した実行基盤・公開ゲート・証跡など) を導入先が明示的に選ぶか決めるとき
- 保証ロードマップの後続 issue (#150〜#161) を実装し、どの主張の証拠を作るのかを決めるとき。後続 issue は下の [主張カタログ](#主張カタログ) の主張ID を引用する
- 導入先が雛形に記入した主張の状態を判定・承認するとき

通常の aidd の利用 (skill・hook・`/aidd:doctor`) はこの文書の対象外で、何も変わらない。

## この文書が宣言しないこと

aidd は「完全に安全」「すべての入力で正しい」とは宣言しない。宣言するのは「この前提と対象版の下で、この主張は、この証拠によって、この状態と判定された」という個別の主張だけである。

- 通常の利用は保証の主張をしない。hook の多くは失敗しても処理を止めない作り (fail-open) で、`tool-reminder.sh` の警告は助言である。これらを「保証」の証拠に使わない。通常の利用の方針 (hook の fail-open、#122 のローカル証跡の非ブロック警告、#129 で決めたモデル評価の入力・文脈の分離方針と、評価に OS の読み取り隔離を一律に必須としないこと、同種モデルによる独立レビューの条件) はこの文書で変えない
- 強い保証は **明示選択の保証構成** だけが扱う。導入先の所有者が構成と主張を選び、承認して初めて効力を持つ
- AI のレビューの合格、テストの成功、モデルが攻撃を試みなかったこと、fixture だけでの成功は、それだけでは「適合」の証拠にならない ([証拠の要件](#証拠の要件))

考え方は、主張・論拠・証拠で保証を組み立てる NIST SP 800-160 の assurance case と、証明の前提と限界を明記する seL4 の書き方に倣う。

- [NIST SP 800-160 Vol.1 Rev.1](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-160v1r1.pdf)、[NIST SSDF (SP 800-218)](https://csrc.nist.gov/pubs/sp/800/218/final)
- [seL4: Proof assumptions](https://sel4.systems/Verification/assumptions.html)

## 主張IDの体系

主張は3つの種別に分けて別々に管理する。種別が違う主張は互いの証拠にならない (手順を守ったことは成果物が正しいことを示さず、権限を絞ったことは仕様に合うことを示さない)。

| 接頭辞 | 種別 | 何を主張するか | 典型的な証拠 |
|---|---|---|---|
| `AC-PROC-` | 手順遵守 | 決めた手順・検査が、対象の版に対して実際に実行され、その結果が改ざんを検出できる形で残っている | 信頼する CI の実行記録、対象 SHA・digest に結び付いた証跡 |
| `AC-PRIV-` | 権限制限 | エージェント (と、エージェントが書いたコード) が、決めた範囲の外の操作をできない | 外側から直接打つ決定的な probe (拒否されることの実測)、基盤・CI の実効設定 |
| `AC-SPEC-` | 仕様適合 | 成果物が、実装と独立に作られ保護された受け入れ基準や、明示した性質を満たす | 受け入れ試験の実行結果、モデル検査の結果と、モデルと実装の対応の検査 |

ID の規則:

- 形式は `AC-<種別>-<3桁の番号>` (例: `AC-PRIV-005`)。番号は種別ごとの通し番号で、意味の区切りを持たない
- ID の意味 (主張文が何を主張するか) は固定する。主張を強める・弱める・範囲を変えるときは、新しい ID を足し、古い ID を `廃止` にする。限界の記述を足す、言い回しを直すなど、主張する内容を変えない変更は同じ ID のまま行える
- 廃止した ID は再利用しない。カタログに `廃止 (日付・理由・後継 ID)` として残す
- カタログへの追加は追記だけで行う。後続 issue が新しい主張を要するときは、その issue の PR でこの文書のカタログに行を足す
- 導入先が自分で足す主張は `AC-<種別>-L<3桁の番号>` (例: `AC-SPEC-L001`) にする。aidd のカタログの番号と衝突しない。種別の3分類には必ず入れる

## 状態

状態は「主張 × 対象構成 × 対象版」ごとに1つ持つ。

| 状態 | 意味 | なる条件 |
|---|---|---|
| `未検証` | 主張が成り立つかどうか、有効な証拠が無い | 既定の状態。証拠が無い・期限切れ・対象版が違う・検査が未実行・判定者が判定していない、のどれか。他の文書や報告の「未確認」はこの状態を指す |
| `不適合` | 証拠が、主張が成り立たないことを示している | 1件でも主張に反する結果 (拒否されるべき操作が通った、必須検査が成功していない、など) が出た |
| `適合` | 有効な証拠が、対象版で主張が成り立つことを示している | [証拠の要件](#証拠の要件) を満たす証拠があり、判定者が判定し、所有者が承認している。期限内で、失効条件が起きていない |
| `対象外` | この構成では主張が意味を持たない | 理由と承認者を書く (例: 配布物を作らない構成の `AC-PROC-002`)。成り立たない主張を隠すためには使わない。報告では「この構成はこの主張を扱わない」と明示する |
| `期限付き例外` | `未検証` か `不適合` のまま、期限まで受容している | 下の [期限付き例外](#期限付き例外) の条件をすべて満たす |

### 期限付き例外

例外は、主張が成り立っていないことを期限つきで受容する記録であって、主張を緩める仕組みではない。

- 例外の下の状態 (`未検証` か `不適合`) を必ず併記する。例外は `適合` にならない
- 書く項目: 理由、代わりの対策、期限 (最長90日)、承認者、例外の下の状態
- 期限を過ぎたら、更新の承認が無い限り、例外の下の状態に自動で戻る。更新には期限の延長ごとに承認が要る
- カタログで `例外` が「不可」の主張 (重大な禁止事項) は例外にできない。これらが `適合` でない構成は、構成全体を `適合` と報告できない
- 例外を設定・更新できるのは導入先の所有者 (承認者) だけで、開発の実行 (エージェント) は書けない。エージェントが書いた例外は無効とする

### 構成全体の報告

- 構成全体を `適合` と報告できるのは、採用したすべての主張が `適合` か `対象外` のときだけ
- `期限付き例外` が1件でもあれば、構成全体は「例外あり (件数、最も早い期限)」と報告し、`適合` と書かない
- `未検証` か `不適合` が1件でもあれば、構成全体は `適合` と報告しない。どの主張がその状態かを列挙する

## 主張の記録項目

雛形 ([`templates/assurance-claims.md.template`](../../templates/assurance-claims.md.template)) は、主張ごとに次の項目を持つ。

| 項目 | 書くこと |
|---|---|
| 主張ID | カタログの ID、または導入先の `AC-<種別>-L<番号>` |
| 対象構成 | 構成ID (導入先が付ける名前)。同じ主張でも構成が違えば別の行にする |
| 対象版 | 判定に効くものの版をすべて: OS・CPU アーキテクチャ・実行基盤・ハーネスとその版・モデル・policy (設定ファイルの版や digest)・aidd の版・対象リポジトリの SHA や成果物の digest |
| 前提 | 主張が成り立つために正しいと仮定していること (例: VM の hypervisor が侵害されていない)。前提が崩れたら主張は失効する |
| 信頼する構成要素 | 検証せずに信頼している部品 (例: 基盤の VM 境界、通信を仲介する proxy、CI サービス)。ここに書いた部品の不具合は主張の外にある |
| 証拠 | 種類 (決定的な probe・信頼する CI の実行記録・証跡・受け入れ試験の結果)、置き場所、取得日時、対象 SHA・digest、取得した人や仕組み |
| 限界 | 主張が扱わないこと (例: 許可した宛先への漏えいはドメインの制限では防げない) |
| 責任者 | 主張の所有者、判定者、承認者 ([責任分担](#責任分担)) |
| 状態 | [状態](#状態) のどれか、判定日 |
| 失効条件 | 下の [失効条件](#失効条件) のうち当てはまるもの、と証拠の有効期限 |
| 例外 | `期限付き例外` のときだけ: 理由・代わりの対策・期限・承認者・例外の下の状態 |

### 証拠の要件

- 証拠は対象版と同じ版・SHA・digest に対するものに限る。別の版の証拠は流用しない
- 判定者は開発の実行 (エージェントのセッション) と分ける。エージェントが自分の作業について書いた「適合」は証拠にならない
- `AC-PRIV-*` は、拒否されるべき操作を外側から直接試して拒否されたことの実測を要する。モデルが攻撃操作を試みなかったことは境界が効いた証拠にならない
- `AC-SPEC-*` は、実装と独立した基準での検証を要する。AI のレビューの合格やテストの成功だけでは業務上の正しさや全入力への適合を宣言しない
- fixture だけでの成功を、実際の VM・実際の CI での成功として報告しない
- 証拠に秘密・プロンプトの本文・本番データ・顧客データを含めない

### 失効条件

次のどれかが起きたら、影響する主張は `未検証` に戻る (再検証して改めて判定するまで)。

- 対象版に書いたもの (OS・基盤・ハーネス・モデル・policy・依存・aidd・受け入れ基準) の変更
- 前提が崩れたこと、または信頼する構成要素の脆弱性の公表
- 証拠の有効期限切れ (雛形に主張ごとの期限を書く。書いていなければ判定から90日)
- 証拠が改ざんされた、または対象版と結び付かないことの発覚

再検証の範囲と責任者の詳細な運用は #160 (S11) が定める。

## 責任分担

aidd は手順・接続・報告を担い、隔離と権限の制御は実行基盤、公開の強制は CI、業務上の妥当性は導入先が持つ。どの主体も、自分の担当でない主張の証拠を作ったことにしない。

| 主体 | 担うこと | 担わないこと | 主に関わる主張 |
|---|---|---|---|
| aidd (このプラグイン) | 主張の体系・カタログ・雛形の提供、手順 (skill) と報告の書式、後続 issue での参照構成・試験の例の提供 | 隔離・通信・資格情報の強制、公開の強制、導入先の業務上の正しさ、適合の判定と承認 | 全種別の定義。証拠は作らない |
| 実行基盤 (最初の対応構成では OrbStack の Linux VM、作業ごとの Docker コンテナ、squid のサイドカー) | 作業環境の隔離・資源上限・廃棄、外向き通信の制限、資格情報の非継承、成果物の取り込みの境界 | 成果物の正しさ、公開の判断 | `AC-PROC-003`、`AC-PRIV-001`〜`AC-PRIV-007` |
| CI・公開サービス (例: GitHub の Actions・ruleset・attestation) | 必須検査の実行と結果の集約、検証元と設定の保護、証跡の生成と配布側での検証 | 実行基盤の隔離、受け入れ基準の内容 | `AC-PROC-001`、`AC-PROC-002`、`AC-PRIV-008`、`AC-PRIV-009` |
| 導入先の業務責任者 (所有者) | 採用する構成と主張の選択と承認、受け入れ基準の内容の確認、判定者の指名、例外の承認、失効時の再検証の指示、利用先のデータ復旧 | (委任しても承認の責任は残る) | `AC-SPEC-*`、`AC-PROC-004`、すべての主張の承認 |

判定者は、導入先の業務責任者が指名する、開発の実行から分けた人または仕組み (信頼する CI の検証 job など) である。

## 採用の条件

- 明示選択の保証構成は、導入先の所有者が承認して初めて採用される。雛形をコピーしただけ、主張を記入しただけ、では採用にならない (雛形の初期状態は `草案`)
- 承認は、承認者・承認日・対象構成・採用する主張ID の一覧・次の見直し日を記録して行う。承認者は開発の実行 (エージェント) であってはならない
- 雛形に入っている記入例はすべて架空のサンプルで、状態は `未検証` である。サンプルの記入を一般的な保証の宣言として扱わない。aidd がこの文書や雛形で「適合」と宣言しているものは無い
- 採用後の記録ファイルの変更 (状態・例外・承認) は、所有者の承認を要する設定変更として扱う。保護の仕組みは #156 (S07) が参照構成を示す
