# 重要な状態遷移の形式検証 (formal methods)

[README に戻る](../../README.md) / 主張の体系: [保証条件と責任分担](contract.md) / 例: [`examples/assurance/formal/`](../../examples/assurance/formal/)

## いつ使うか

明示選択の保証構成で、主張 `AC-SPEC-002` (または導入先の `AC-SPEC-L<番号>`) の証拠を作るか決めるとき。対象は「並行する操作や障害の割り込みで壊れうる、状態遷移の不変条件」に限る。

この文書は、小さな架空の承認/公開の状態機械1つでモデル検査を試した結果と、導入先の性質へ適用するかどうかの判断基準を書く。通常の aidd の利用には関係しない。

## 対応する主張と、この例が示さないこと

[`AC-SPEC-002`](contract.md#ac-spec-仕様適合): 「明示した重要な性質 (状態遷移の不変条件など) が、明示した前提・状態範囲・並行と障害のモデルの下でモデル上成り立ち、モデルと実装の対応を検査した範囲で実装に反映されている (有限範囲の探索を無制限の証明と呼ばない)」。

この例は主張の2つの部分にそれぞれ1つずつ証拠の形を示す。

| 主張の部分 | この例の証拠 | 形 |
|---|---|---|
| モデル上成り立つ | 正しいモデルの全到達状態で不変条件が破れないこと (TLC の網羅探索)。欠陥版で反例が出ること | 有限範囲の網羅探索。証明ではない |
| 実装に反映されている | 実装の実行トレースが、モデルの名前付きの遷移として1歩ずつ再現できること (トレース検査) | 標本の検査。実装のすべての実行は覆わない |

示さないこと:

- **どの構成の `AC-SPEC-002` も `適合` にしない。** 対象は架空の状態機械と、例のために書いた小さな Python 実装である。判定は導入先の判定者が、導入先の性質・対象版で行う ([証拠の要件](contract.md#証拠の要件))
- モデル検査の合格を、実装全体の正しさや業務上の正しさの証拠にしない。性質として書いた1つの不変条件だけを扱う
- この試験の実行と結果は、このセッション (エージェント) が作った。判定者を分ける要件は満たしていない

## 対象: 架空の承認/公開の状態機械

成果物 (artifact) ごとに「検証済み」「承認が有効」「公開中」の3つの真偽値を持つ。公開する側 (publisher) は、成果物を確かめる手順 (`Check`) と公開する手順 (`Publish`) を別の呼び出しで行う。その間に承認の取り消し (`Revoke`) や内容の変更 (`Modify`) が割り込める。

| 遷移 | 起きること |
|---|---|
| `Verify(a)` | 現在の内容が検証を通る |
| `Approve(a)` | 検証済みの内容を承認する |
| `Revoke(a)` | 承認を取り消し、同じ一歩で公開を取り下げる |
| `Modify(a)` | 内容が変わり、検証・承認・公開がすべて外れる |
| `Check(p, a)` | publisher `p` が、検証済み・承認済み・未公開の `a` を公開予定にする |
| `Publish(p)` | 公開予定を公開する。正しい版は、この一歩で検証と承認を読み直し、外れていれば公開しない |
| `Crash(p)` | publisher が `Check` と `Publish` の間で落ち、公開予定を失って再起動する |

性質 (不変条件 `SafePublish`): **公開中の成果物は、検証済みで、承認が有効である。**

欠陥版 (`RecheckOnPublish = FALSE`) は、`Publish` が `Check` の結果を信じて読み直さない (確認した時点と使う時点がずれる TOCTOU)。

## 明示する前提と範囲

| 項目 | 内容 |
|---|---|
| モデル | [`Publish.tla`](../../examples/assurance/formal/Publish.tla) |
| 不変条件 | `SafePublish`、型の不変条件 `TypeOK` |
| 状態範囲 | 成果物 2件 (`a1`, `a2`)・publisher 2つ (`p1`, `p2`)。[`Publish.cfg`](../../examples/assurance/formal/Publish.cfg) (正しい版)、[`PublishDefect.cfg`](../../examples/assurance/formal/PublishDefect.cfg) (欠陥版) |
| 並行モデル | 各遷移は共有ストアの1つの不可分な操作で、別の主体の操作は任意の順に交互に起きる (interleaving)。ストアが各操作を不可分に実行することは前提 (例の実装では1つの lock) |
| 障害モデル | publisher の crash と再起動 (`Check` と `Publish` の間の記憶を失う)。ストア自体の障害・永続化・通信の喪失や重複・時計は扱わない |
| 性質の種類 | 安全性 (起きてはならない状態に至らない) だけ。「いずれ公開される」などの活性は検査しない |
| ツール | TLA+ の TLC (`tla2tools.jar` v1.7.4、TLC2 Version 2.19、rev `5a47802`)。jar の sha256 `936a262061c914694dfd669a543be24573c45d5aa0ff20a8b96b23d01e050e88` を実行のたびに照合する |
| Java | ローカルの `java`、または Docker の `eclipse-temurin@sha256:d77e090ae1f6970c047b443c6f0a6c1358b0426d44432bb5a7753408cd43de0d` (Temurin 21.0.13、`--network none`) |

版・digest の固定は [`run-tlc.sh`](../../examples/assurance/formal/run-tlc.sh) に書いてある。

## 結果 (2026-11-28)

| 検査 | 結果 |
|---|---|
| 欠陥版 | `SafePublish` が破れる反例 (TLC exit 12)。`Verify(a1)` → `Approve(a1)` → `Check(p1, a1)` → `Revoke(a1)` → `Publish(p1)` で、承認が無いのに公開中になる。記録: [`counterexample.txt`](../../examples/assurance/formal/counterexample.txt) |
| 正しい版 (2件・2つ) | 違反なし (exit 0)。到達可能な状態 134、探索の深さ 10、未探索 0 |
| 正しい版 (3件・3つ、参考) | 違反なし。到達可能な状態 3970、深さ 15。cfg は置いていない (`Publish.cfg` の集合を広げて手で実行した) |

### 有限範囲の探索と証明の違い

正しい版の結果が言えるのは「**この cfg の定数 (成果物 2件・publisher 2つ) で、到達可能なすべての状態で `SafePublish` が成り立つ**」までである。

- 成果物や publisher の数を任意にした場合は確かめていない。この例は各成果物の状態が独立していて、数を増やしても新しい種類の交互実行が増えないと考えられるが、それはモデル検査の結果ではなく推論である。無制限に言うには、TLAPS などの定理証明で帰納的不変条件を証明する必要があり、この例ではしていない
- TLC は状態を fingerprint (ハッシュ) で区別する。2つの状態が同じ fingerprint になると片方を探索しない可能性があり、TLC 自身がその確率を見積もって出力する (この例の正しい版では 5.8×10^-15)
- モデルに書いていないこと (上の障害モデルの外、活性) は何も言えない

## モデルと実装の対応の検査

[`impl/publish_service.py`](../../examples/assurance/formal/impl/publish_service.py) は、モデルを import しない普通の書き方の実装である (改訂番号を持つストアと、確認と公開を分けて呼ぶ publisher)。対応は次の3つで検査する。

1. **抽象化関数** (`abstract_state`): 実装の状態をモデルの変数に写す。例: 「検証済み」は「検証した改訂番号 = 現在の改訂番号」
2. **トレースの記録**: 実装に操作を順に適用し、受け付けられた操作ごとに、操作名と操作後の抽象状態を `TraceData.tla` に書く。乱数 (seed 1〜5、各60操作) の5本と、上の反例と同じ順の1本を作る
3. **トレースの再生** ([`TraceCheck.tla`](../../examples/assurance/formal/TraceCheck.tla)): 最初の抽象状態がモデルの初期状態に一致し、各一歩が **記録された名前のモデルの遷移** で、**記録された状態にちょうど到達する** ことを TLC で確かめる。合わない一歩があると TLC は deadlock として止まる

結果: 正しい実装の6本はすべて再生できた。欠陥を入れた実装 (`--defect no-recheck`、公開時に読み直さない) の反例順のトレースは、5つ目の操作 (`Publish`) で再生が止まった (exit 11)。モデル検査で見つけた欠陥が実装にあれば、この検査で見分けられることを示す。

### 未証明の部分

- **抽象化関数そのものの正しさ。** 写し方を誤ると、実装の不具合がモデル上は見えなくなる。例: 実装は「どの改訂を公開したか」を持つが、モデルは「現在の内容が公開中か」しか持たない。確認後に内容が変わって再承認された場合に新しい改訂が公開されることは、モデルでは問題にならず、検査もしない
- **トレースは標本。** 記録した6本の実行だけが対象で、実装のすべての実行の対応は示さない。乱数の偏りで通らない遷移の組み合わせがありうる
- **実際の並行実行。** トレースは1つのスレッドで順に操作を呼んで作る。lock が各操作を不可分にすることは前提で、複数スレッドでの検査はしていない
- **モデルの外の部分。** 永続化・再起動後の復元・API の入力検査・権限など、モデルに無いものは何も示さない

## 手動で実行する

CI の contract-tests は Java・Docker・ネットワークを前提にしないため、この試験は CI に入れていない。手で実行する。

```bash
bash tests/assurance/formal-test.sh
```

- 必要なもの: `bash`・`python3`・`curl`、ローカルの `java` か Docker (Java が無いときは固定した Java イメージを使う。arm64 macOS の OrbStack で確認した)
- 初回は `tla2tools.jar` を GitHub の release から取得し、`${XDG_CACHE_HOME:-$HOME/.cache}/aidd-formal/v1.7.4/` に置く。置き場所は `AIDD_FORMAL_CACHE` で変えられる。sha256 が合わなければ実行しない
- `AIDD_FORMAL_JAVA=local|docker` で Java の取り方を固定できる (既定は `auto`: ローカルの `java` が動けばそれ)
- 1つのモデルだけ検査するとき: `bash examples/assurance/formal/run-tlc.sh <作業用ディレクトリ> Publish.tla Publish.cfg` (作業用ディレクトリに `.tla`・`.cfg` を写してから実行する。TLC はその下に `states/` を作る)

2026-11-28 に、ローカルの Java (`AIDD_FORMAL_JAVA=auto`) と Docker (`AIDD_FORMAL_JAVA=docker`) の両方ですべての検査が通った。

## 再検証の条件

次のどれかが変わったら、上の結果は使えない。モデル検査とトレース検査をやり直し、主張の状態は再検証が済むまで `未検証` に戻す ([失効条件](contract.md#失効条件))。

| 変わったもの | やり直すこと |
|---|---|
| 実装 (状態を変える処理、lock・トランザクションの範囲、publisher の手順) | 抽象化関数の見直し、トレース検査。遷移の種類が変わったらモデルも直してモデル検査 |
| 設定 (状態の数の上限、並行する publisher の数、再試行の方式) | 状態範囲がそれを覆っているかの見直し、モデル検査 |
| 前提 (ストアの操作が不可分でなくなる、障害の種類が増える、例: ストアの再起動や複製) | モデルの並行・障害モデルを直してモデル検査 |
| 性質 (不変条件の文言、扱う状態) | 新しい主張ID かどうかを [ID の規則](contract.md#主張idの体系) で判断し、モデル検査とトレース検査 |
| ツール (`tla2tools.jar` の版・sha256、Java の版・イメージの digest) | 同じモデルで検査をやり直し、結果 (状態数・反例) が変わらないことを確かめる |
| 抽象化関数・トレースの作り方 | トレース検査。欠陥版の実装で再生が止まることも確かめ直す |

## 導入先の性質へ適用する判断基準

形式検証は費用が高い (モデルを書き、実装に合わせて保守する人が要る)。次をすべて満たす性質に限って使う。

1. **違反の影響が重い**: 起きると取り消せない、または外部に出る (公開・課金・権限付与・データ削除など)
2. **状態遷移の不変条件として書ける**: 「〜の状態では必ず〜」の形で、真偽を機械で判定できる。業務上の妥当性や見た目の正しさは対象外 (受け入れ試験 `AC-SPEC-001` で扱う)
3. **交互実行か障害の割り込みで壊れうる**: 確認と実行が別の一歩、複数の主体が同じ状態を変える、途中で落ちて再試行する、など。単一スレッドの純粋な計算なら単体テストや property-based testing で足りる
4. **小さく抽象化できる**: 重要な変数が数個で、状態の数を有限の小さな範囲に絞っても意味のある交互実行が残る
5. **対応を検査できる**: 実装の状態をモデルの変数に写す関数が書け、実装からトレース (操作と状態) を取り出せる。取り出せないなら「モデル上成り立つ」までしか主張できない

適用するときに雛形 ([`templates/assurance-claims.md.template`](../../templates/assurance-claims.md.template)) へ書くこと:

- 対象版: 実装の SHA、モデル・cfg・トレース生成のファイルの SHA、ツールの版と sha256・Java の版
- 前提: 並行モデル・障害モデル・不可分性の前提
- 限界: 状態範囲 (定数の値)、検査していない性質 (活性など)、抽象化で落とした情報、トレースの本数と作り方。「有限範囲で探索した」と書き、証明と書かない
- 証拠: TLC の出力 (状態数・未探索 0・fingerprint の衝突確率)、欠陥版の反例、トレース検査の結果
