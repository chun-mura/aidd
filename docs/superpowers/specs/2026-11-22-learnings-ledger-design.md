# 知見の台帳 (#104)

## 目的

`/aidd:incident-retro` は今のセッションの会話しか見ないので、同じ事故が前にもあったかを知る手段が無く、運用ルール2 (2回ルール) を人の記憶で判定している。利用側リポジトリに観測を貯める台帳を置き、チームで回数を合算できるようにする。機密を入れないことを、項目の制限と機械の検査で担保する。

この変更は土台だけを作る。auto memory の取り込み (#105)、asset-audit の対象追加 (#106)、aidd 本体への還流 (#107)、autonomous-review の指摘の記録 (#108) はやらない。

置き場の比較 (1ファイルの jsonl・orphan ブランチ・issue・マシンの中との比較) は #104 のコメントにある。

## 置き場

利用側リポジトリの `.aidd/learnings/<UTC時刻>-<乱数>.json` に1観測1ファイルで置き、コミットして PR で共有する。

- ファイル名: `YYYYMMDDTHHMMSSZ-<16進8桁>.json` (例 `20261122T031500Z-1a2b3c4d.json`)。ファイル名の幹が観測の ID になる。ファイル名が別なので、同時に書いてもマージで衝突しない。
- `.aidd/learnings/` の直下にこの名前で置いたもの以外は、検査で拒否する (`promotions/` などの別の置き場は、使うときに検査へ足す)。
- 観測は書いたあと書き換えない。昇格の記録は別ファイルにする (後回し)。

## スキーマ (`schema_version` 1)

すべて必須。ここに無いキーは拒否する。重複したキーも拒否する。ファイルは 4096 バイト以下の UTF-8 の JSON オブジェクト。

| キー | 型・値 | 内容 |
|---|---|---|
| `schema_version` | 整数 `1` | スキーマの版 |
| `source` | `incident-retro` / `auto-memory` / `autonomous-review` | 書いた経路。今書くのは `incident-retro` だけで、残りは #105・#108 のために予約する |
| `scope` | `project` / `tool` / `aidd` | 知見が効く範囲。このリポジトリだけ / 共通の道具 (git・gh・Claude Code) の挙動 / aidd の資産。#107 は `tool`・`aidd` を還流の候補にする |
| `status` | `observed` / `applied` / `declined` | 記録した時点の扱い。対策を見送った / 承認されて反映した / ユーザーが断った。書いたあとは変えない |
| `signature` | 文字列 (80字以下、8語以下) | コマンド名 (またはツール名) とフラグとサブコマンドだけ。例 `git stash`、`gh pr create --fill`、`Edit`。引数の値・パス・ブランチ名を入れない。昇格の判定はこの文字列の完全一致で数える |
| `fact` | 文字列 (1〜200字、改行・制御文字なし) | 何が起きたかの事実。唯一の自由記述 |
| `evidence` | 文字列の配列 (0〜10件) | コミット SHA (16進7〜40桁)・PR/issue 番号 (`#123`)・リポジトリ相対パスのどれか。URL・絶対パス・`..` を含むパスは拒否 |
| `session` | 16進12桁 | セッション ID の SHA-256 の先頭12桁。同じセッションの観測を1回と数えるため。作成者名は持たない |

`signature` の語の規則: 1語目は `[A-Za-z][A-Za-z0-9_.-]*` (コマンド名・ツール名)、2語目以降は小文字のサブコマンド `[a-z][a-z0-9-]*` か、値を持たないフラグ `-x` / `--name` (`=` を含まない)。サブコマンドとブランチ名 (`main` など) は形で区別できないので、残りは書く側の規則と PR のレビューに任せる。

## 検査の規則

検査は `scripts/learnings.py` (python3 の標準ライブラリだけ、`python3 -I` で起動) にまとめ、書く時点 (incident-retro) とコミット時 (`tool-reminder.sh`) で同じ関数を使う。該当したら**伏せ字にせず拒否**し、書き直させる。理由の文には該当した値を含めない (値そのものが秘密でありうるため)。

スキーマ検査 (上の表) に加え、すべての文字列値に次の正規表現をかける:

| 規則 | 拒否するもの | 通すもの (誤検出の対策) |
|---|---|---|
| 絶対パス | `/` で始まり2段以上のパス (`/Users/x/y`)、Windows のドライブ (`C:\`) | `/aidd:retro` のようなスラッシュコマンド、`A/B`・`and/or`、`~/.claude/...` (ユーザー名を含まない)、`/dev/null`・`/dev/stdout`・`/dev/stderr` |
| メール | `name@host.tld` | `@types/node` のような scope 名 |
| URL | `scheme://`、`www.` | — |
| IP | IPv4 の4つ組、IPv6 (4組以上、または `::` を含む16進の組) | `12:30:45` のような時刻 |
| FQDN | よく使う TLD・社内向けの名前 (`com`・`net`・`org`・`io`・`dev`・`jp`・`local`・`internal`・`corp` など) で終わる名前 | `app.ts`・`foo.test.ts`・`Node.js` のようなファイル名・製品名 (拡張子と重なる TLD は一覧に入れない) |
| token の接頭辞 | `ghp_`・`gho_`・`ghu_`・`ghs_`・`ghr_`・`github_pat_`・`sk-`・`AKIA`/`ASIA`・`xox[abprs]-`・`glpat-`・`AIza` に続く長い文字列、`-----BEGIN` | 接頭辞だけ (`ghp_` という語に言及するだけ) |
| 高エントロピー | `-`・`_`・`.`・`/` で区切った16字以上の連なりのうち、英字と2つ以上の数字を含み、シャノンエントロピーが 3.5 bit/字以上のもの (無作為な英数字20字の約86%、24字の約91%を捕まえる)。16進で41字以上と UUID も拒否 (ID なので) | 16進40字以下 (コミット SHA)、ファイル名の幹 (`20261122T031500Z-1a2b3c4d`)、識別子・版・パス (`AIDD_REQUIRED_LABEL_PREFIX`・`x86_64-apple-darwin25`・`generateAssetIndex2`) |
| 会社名の手がかり | `株式会社`・`有限会社`・`合同会社`・`(株)`・`㈱`・`Inc.`・`Corp.`・`Corporation`・`Ltd`・`LLC`・`GmbH`・`K.K.` | — |

顧客名・業務の固有名・ホスト名だけの社内システム名は正規表現で捕まらない。最後の防衛線は PR での人のレビュー (4層目) で、incident-retro はそれを利用者に伝える。顧客名の拒否リストはそれ自体が機密になるので作らない。

## 有効化

既定で無効。リポジトリの clone ごとに次を実行したときだけ incident-retro が台帳を読み書きする:

```bash
git config aidd.learnings true
```

- `.git/config` に入るので、コミットされず、clone・fork で引き継がれない。公開リポジトリ・fork で知らずに書き始めることが無い。
- 環境変数にしなかったのは、マシンのすべてのリポジトリ (公開リポジトリを含む) で有効になるため。`.aidd/` に置く設定ファイルにしなかったのは、コミットされて fork に引き継がれるため。
- worktree は `.git/config` を共有するので、同じ clone の worktree でも有効になる。

**コミット時の検査は有効化に関係なく動く**。台帳のファイルがステージされていれば、有効化していない人のコミットでも検査する。秘密を含むファイルがコミットされる危険は、書いた人の設定に関係なく同じだから。台帳のファイルを含まないコミットでは挙動を変えない。

## 機密を入れない4層

1. **項目の制限**: 自由記述は `fact` だけ。`signature`・`evidence` は形を限り、`source`・`scope`・`status` は列挙値。作成者名を持たない。`session` はハッシュ。
2. **書く時点の検査**: incident-retro は観測を `python3 -I scripts/learnings.py add` に渡す。スクリプトが検査し、通ったときだけファイル名を決めて書く。モデルが Write で直接書かない。
3. **コミット時の検査**: `tool-reminder.sh` は PreToolUse の `git commit` で、同じ検査を次のファイルにかけ、1つでも通らなければ拒否する。
   - ステージ済み (`git diff --cached --diff-filter=ACMR`) の `.aidd/learnings/` 配下のファイル (インデックスの中身を読む)
   - 同じコマンドの `git add` と `git commit` に名指しされたパスのうち、`.aidd/learnings/` 配下か、その親ディレクトリを指すもの (作業ツリーの中身を読む)。`git add x && git commit` は PreToolUse の時点ではまだステージされていないため。シェルのグロブは展開して見る
   検査スクリプトを読み込めないときは、台帳のファイルがあるコミットだけを拒否する (検査せずに通さない)。Claude を通さないコミットは止められないので、利用側 CI で gitleaks を動かすよう README で案内する (雛形は後回し)。
4. **PR での人のレビュー**: 正規表現で捕まらない固有名は、レビューで止める。マージ後に消すには履歴の書き換えが要ることも README に書く。

hook が書いてよいのは `~/.claude/aidd/` だけという方針は変えない。コミット時の検査は読むだけ。台帳を書くのは incident-retro (利用者が起動する skill) だけ。

## incident-retro の手順

- 手順1の後に、有効なときだけ、事故ごとに `signature` を決める。
- `python3 -I scripts/learnings.py candidates --session-id <ID> --signature <S> ...` が、既定ブランチ (`origin/HEAD`、無ければ `origin/main`・`main`) と作業ツリーの `.aidd/learnings/` を読み、検査を通った観測だけを数える。今回の事故の `signature` を今のセッションの観測として足したうえで、同じ `signature` が別の `session` で2回以上あれば昇格候補として出す。
- 手順3の表に「台帳の回数」の列を足し、2回目以上を昇格候補として示す。1回目は従来どおり、一般則にせず事故の状況に限った書き方に留める。
- 台帳への記録も AskUserQuestion の承認に含め、承認されたものだけ `add` で書く。拒否されたら伏せ字にせず書き直す。正典 (CLAUDE.md・hook・skill) の反映は従来どおり承認後だけ。
- セッション ID は Claude Code の `${CLAUDE_SESSION_ID}` を渡す。文字のまま残る環境 (Codex・Cursor) では、この実行の開始時刻 (UTC) を1つ決めて全観測に同じ値を渡す。スクリプトがハッシュにするので、生の値はファイルに残らない。

## #105〜#108 との境界

- #105 (auto memory の取り込み): `source: auto-memory` で `add` を呼ぶ。検査とファイルの形はそのまま使う。
- #106 (asset-audit): 昇格の記録 (`promotions/`) ができてから、それを読んで memory の削除候補を出す。検査に `promotions/` の規則を足すのは #106 か昇格の記録を作る変更。
- #107 (還流): `scope` が `tool`・`aidd` の観測を草案の候補にする。草案に入れる signature・事実は検査を通ったものなので、固有の情報を伏せる手間が減る。
- #108 (autonomous-review): `source: autonomous-review` で `add` を呼び、指摘の型を `signature` に入れる。指摘の型はコマンド名ではないので、`signature` の語の規則を広げるかは #108 で決める。

## 検証

- `tests/learnings-test.sh`: 検査の拒否すべき入力 (各正規表現・スキーマ違反・項目外のキー・長すぎる `fact`・URL を含む `evidence`・不正なファイル名) と通すべき入力 (正常な観測・SHA・相対パス・PR 番号)、`add` の有効化の確認とファイル名、`candidates` の数え方。テストデータの token らしい文字列は実行時に組み立て、リポジトリに置かない。
- `tests/hook-contract-test.sh`: 検査に通らない台帳ファイルを含む `git commit` (ステージ済み・同じコマンドの `git add`) を拒否し、通るもの・台帳を含まないコミットは拒否しない。
- `tests/command-contract-test.sh`: incident-retro に、検査を通った観測だけを書く・2回目を昇格候補として示す・既定で無効、の文言がある。

## 残るリスク

- 業務の固有名は正規表現で捕まらない (4層目に頼る)。
- マージ後に消すには履歴の書き換えが要る。
- `git add -p`・`git add -u` のような名指しでない追加と同時のコミットは、PreToolUse の時点で台帳のファイルを見られないことがある (`-u` は既存の hook が拒否する)。
- Codex・Cursor の adapter 経由でコミット時の検査が同じように効くかは未検証。
- 顧客案件のリポジトリでの運用 (台帳に何を入れてよいか) は社内の確認が要る。
