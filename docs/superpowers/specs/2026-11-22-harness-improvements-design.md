# aidd の安全性・品質保証・運用負担を改善する計画

規模: 既存資産を補強する18個の独立PR候補。これは実装前の改善提案と Issue 分割であり、コード変更の承認・実施を含まない。

## 背景と目的

利用先のITシステムを適切に設計・実装・テストし、安全に開発できるようにする。2026-11-22 の調査を現行 v0.64.0（`1287eb549315427ef62290c02896406701212251`）と既存 Issue に照合し、未解消の問題を実行可能な単位にする。

## 方針とアプローチ

- 現行 README・docs/tips/superpowers-usage.md を正典とし、古い設計書の初期前提だけで現在のマルチハーネス対応を否定しない。
- 推奨: 既存 skill/hook/評価資産を補強する。汎用の開発ランタイムや新しい重複 skill を作る案は、superpowers・reqd・stdd 等との重複と運用負担から採らない。
- コードで直せるものを先に直し、既存テストを CI へ接続する。新規の常時注入・全プロンプト履歴収集・外部集計基盤を増やさない。
- dispatcher 統合、adapter の一般的な fail-open、PR 前レビューの非ブロック通知、公開判断を人に残す方針は維持する。計算済み deny の消失と、失敗を記録できない不具合は修正する。
- superpowers は実装の進め方、reqd は要件形式化、stdd はテスト手法を担当する。aidd は既存の入口・成果物・委譲条件・証跡をつなぐ。
- ユーザー決定: 同種モデルでも、新しい文脈で独立レビューを行い、必須品質ゲート成功・低リスクの条件を満たせば適格にできる。モデルの異種性を必須にはしない。同一セッションの自己レビューと独立性不明の場合は human_required とする。
- ユーザー決定: 評価は入力・文脈・採点工程の分離を必須にし、権限上の読み取り制限の限界を明記する。元リポジトリの絶対パス等からの読み取りを禁止する新しい実行基盤は本計画に含めない。

## 判断の根拠

- Anthropic の [harness-design-long-running-apps](https://www.anthropic.com/research/harness-design-long-running-apps) は Opus 4.5 による生成/評価の役割分離と、実アプリ操作による検証を報告する。モデルの異種性を必須条件とはしていない。
- [Towards Practical Defect-Focused Automated Code Review](https://arxiv.org/html/2505.17928v1) の付録 O は、同種構成を主実験とし、異種の reviewer/validator 組合せも比較する。検証担当の能力と組合せが重要であり、異種なら一律に優れるとは示さない。
- [Beyond the Surface](https://aclanthology.org/2025.emnlp-main.86/) は自己選好バイアスと品質差の交絡を扱う。文章の相対評価から、コードの自動マージの安全性へは一般化しない。
- [tap](https://arxiv.org/html/2606.14445v1) は異種ペアの指摘あり率69.8%、同種53.1%を報告するが、モデル・役割・実行環境・時期が交絡する観測研究で、欠陥の再現率や純粋な因果効果ではない。
- 従って「独立性を検証する」「客観的な品質ゲート」「高リスクは人判断」を先に保証し、モデル多様性の効果は T10 で測る、という判断を提案する。

## 構成と責務・インターフェース

各タスクの配置は下記の既存資産を使う。新規評価の小さな fixture/補助スクリプトは tests/eval/ 配下に閉じる。新しい汎用 CLI・サービスを追加しない。利用者向け既存コマンド名は維持し、診断や比較評価は人が明示的に実行する。通常の開発フローへ高コスト評価を常時追加しない。

## データフロー・失敗・運用

hook の判定 → 出力を、通知状態の読み書きと切り離す。記録は既存のローカル状態だけで、本文・認証情報を追加収集しない。共有状態は型検証・有限のロック待ち・原子的置換を検証する。
レビュー証跡は対象の固定 SHA/差分と完了状態を正典にする。判断不能を成功としない。評価の入力・作業ディレクトリ・新しい文脈にはケースと必要なプロンプトだけを渡し、キー・過去結果・Git履歴は採点工程に分離する。これは権限による完全な隔離を保証せず、cwd 外の絶対パスからの読み取り等は残存する限界として明記する。
既存状態・スキーマの移行は各 task の中で定め、読み取れない旧証跡は未確認として扱う。既存 run/利用者ファイルを上書きしない。設定変更や本番操作、実際の merge は本計画の対象外。
各実装は通常の version/README/CHANGELOG と必要な生成物を更新し、対応する契約テストを実行する。プロンプトを運用ルール6の対象で変更したリリースでは既存 eval も実施する。コード以外の単純な CI 変更に不要な資産更新を要求しない。

## レビューと分割

独立して実装できるため issue-split の成果物単位で切る。一緒にレビューするのは方針・スコープ境界・依存の整合を確認するため。1タスクの主要変更はおおむね5ファイル以内とし、通常のmanifest/CHANGELOG/README/生成物は付随更新として同じPRへ含める。広がった場合は着手前に分割する。
終了条件は high/未解決の blocking mid が無いこと。指摘が出た場合は現物で反証し、修正した範囲を再レビューする。起票前にタイトル主要語で全状態の既存 Issue を検索し、重複は再利用する。
