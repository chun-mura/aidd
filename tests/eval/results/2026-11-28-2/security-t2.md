- 混ぜた指摘 M1〜M4 は4件とも refuter で反証が成立しました。arbiter に渡す前に取り除いています。

## arbiter の最終報告

**件数: high 2 / mid 7 / low 5**

### 1. 統合した指摘（観点順、重複を除いたもの）
- **[high] H-1 :29, :33 ダウンロード時に取引先を照合していない（権限昇格）**（A1-2 / S-2 / S-5後半 / S-6 を統合）
  - 取引先Aのアカウントで、取引先Bの契約書を取得できる。
  - UUIDv4 は認可の代わりにならない。
  - アップロード側でも、社内ユーザーが指定できる取引先IDの条件が書かれていない。
  - 「権限なし」と「存在しない」をどちらも404にそろえる対応は、この修正の一部として扱う。
- **[high] H-2 :45 vs :33 署名トークン付きURLを INFO ログに90日保管している**（A1-4 / A3-1 / S-1 / A2-4 を統合）
  - ログを閲覧できる人が、5分以内なら認証なしで契約書を取得できる。
  - その取得は、記録上は発行を受けたユーザーの操作に見える。監査ログ自体が「誰が取得したか」の記録をゆがめる。
  - 「URLを再現するため」という理由は、URLが5分で失効するので成り立たない。
  - プロキシやLBのログでも、クエリ文字列をマスクする必要がある。
- **[mid] M-1** :22, :33, :35-39 S3保存とDB登録の二重書き込みで、順序・孤児オブジェクト・DB障害時の応答が決まっていない（A1-5 / A2-1）
- **[mid] M-2** :23, :29, :38 署名URLの発行ではS3を呼ばないため、502 に到達しない可能性がある。S3に実体が無いときの失敗はサーバーで検知できない（A2-2）
- **[mid] M-3** :24, :45 監査ログの対象・方式・失敗時の挙動・保全が決まっていない。認可拒否・404・アップロード・実際のダウンロードが記録されず、保存先・改ざん防止・閲覧権限・90日の根拠も無い。代案は S3アクセスログ/CloudTrail の併用と、書き込み専用の保存先（A1-3 / A2-3 / A3-3 / S-3）
- **[mid] M-4** :44 監視が 4xx/5xx レートだけ。404急増とユーザー別ダウンロード数の監視は、H-1 の悪用を見つける手段にもなる（A3-2）
- **[mid] M-5** :26-29 インターフェースの定義が足りない（A1-6）
- **[mid] M-6** :22, :28 マルウェアスキャンが無く、元ファイル名を無害化する方針も無い（S-4）
- **[mid] M-7** :28 CSRF 対策の記述が無い（S-5前半）

- **[low] L-2** :37 404 とDB障害の区別が無い（A2-5）
- **[low] L-3** :43 デプロイ手順にテーブル・バケットの作成とロールバック時の扱いが無い（A3-4）

- **[low] L-5** :29 権限を剥奪しても発行済みURLは5分有効のまま。旧版の無効化も書かれていない（S-8）

### 4. 最優先で直すべき1点
**H-1: `GET /api/files/{file_id}` に取引先の照合（認可）を入れる。**

H-2 より優先する理由: H-2 の悪用には「ログを閲覧できる権限」と「5分以内」という条件が要る。H-1 は外部の取引先アカウントだけで、時間の制限なく悪用できる。

代案:
- :29 を「ユーザーの所属取引先IDと `contract_files.対象取引先ID` が一致する場合に限り発行する。一致しない場合と存在しない場合は、どちらも同じ404を返す」に変更する。
- 照合する責務を :23 の `FileDownloadApi` に明記する。
- 認可で拒否したことを監査の対象に加える。
- :28 に、アップロードで指定できる取引先IDの条件を定義する。
- あわせて H-2 もすぐ直す。:45 の記録項目を「時刻・ユーザーID・file_id・S3キー・発行時刻・有効期限・要求ID」に限定し、署名トークンは記録しない。

## security-reviewer の起動
