**深刻度と統合の裁定:** reviewer 同士で結論が逆になった指摘はありませんでした。arbiter が変えたのは次の3点です。
- R5 を H2 にまとめた。:29 と :39 は同じ判断の表と裏なので、H2 を直せば R5 も消える。
- R2・R3・R11 を mid から low に下げた。:7 に「要約形式」と明記されているため。
- R1・R8・R15 を M1 にまとめた。どれも :34 で DB と Redis の両方に書いていることが原因。

**観点を重ねて見えた指摘:** :40 でバッチを失敗させる条件は「認証エラー・5xx連続」だけで、タイムアウトが続く場合は入っていません。そのため WMS が止まって全件タイムアウトすると、:38 に従って全商品が在庫0で書き込まれます。バッチは exit 0 で終わるので監視にも出ず、サイト全体が売り切れ表示のまま誰も気づきません。arbiter はこのケースを H1 に含めました。

**最優先で直す1点: H1（:38）。** 理由は次のとおりです。
- 正の DB とキャッシュの両方に誤った値を書き込む、唯一の仕様である。
- 全件タイムアウトのときにサイト全体が売り切れになる。
- H2 は値が古くなる問題だが、H1 は誤った値で上書きする問題で、利用者が直接目にする影響が大きい。

arbiter が示した直し方:
- タイムアウトした商品は書き込まず、前回の値を残す。
- `SyncResult` の `timed_out` と `failed` を分けて数える。
- `inventory` に `synced_at` を持たせ、StockApi で在庫数と一緒に返す。
- 前回の値が無い新規商品は、0ではなく「不明」として返す。
- タイムアウト率が閾値を超えたら、:40 と同じくバッチを失敗させる。
- タイムアウトの件数を WARN ログとメトリクスに出す。

（arbiter の注記: これはレビューとして観点を整理したもので、設計を採用するかどうかの最終判断ではありません。設計書に反映する前に、担当者が事実と運用への影響を確認してください。）

## security-reviewer の起動
**no。** 起動条件に当たらないと判断しました。
- `StockApi` は `/internal/` パスで「サイト内部からのみ参照」（:30）。外部に公開されるエンドポイントではない。
- 設計の中心は、社内の WMS から在庫数を取り込むバッチ処理。
- 扱う在庫数は機微情報ではなく、認証の仕組みを新しく作る設計も無い。秘密情報や個人情報をファイル・ログ・キャッシュに保存する記述も無い。

WMS の認証は :40 で失敗条件として触れられているだけで、資格情報をどう扱うかは設計の範囲に入っていません。Agent 6 から high/mid のセキュリティ指摘は出ていないので、実装後の `/security-review` は推奨していません。
