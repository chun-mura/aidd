## arbiter の最終報告

**件数: high 1件 / mid 5件 / low 2件**

### 矛盾の裁定
- **裁定1**: A1-1 の分割案は schedule コンポーネントを残しているが、YAGNI の low（A3-1）はスケジュール管理を消すよう求めている。**low 側を採る。** L56・L30 から、実行のきっかけは既存の cron が持っている。L22 の cron 設定の読み込み・次回実行時刻の管理と、L24 の送信スケジュールは、使われない二重管理である。schedule は分割案から外し、L15 の「送信スケジュール管理」もスコープから外す。
- **裁定2**: L22（収集クエリの発行は ReportManager の責務）と L34（呼び出し側が SELECT する）の食い違いは本文どおりで、指摘は有効。指摘1を直すときに一緒に解消する。

### 統合した指摘
**構造**
- **[high] ReportManager に責務が集中し、スケジュールも二重に管理している（L15, L22, L24, L26）**
  - 統合元: A1-1、A1-2、A3-1、A2-3
  - 問題:
    - 集計・整形・送信はそれぞれ変わる理由が違うのに、1つのクラスにまとまっている。
    - 使わないスケジュール管理も抱えている。
    - 配置先が書かれていない。
  - high にした理由: 下の mid の多くは、このクラスをどう分けるかで置き場所が決まる。
- **[mid] generate() の引数に内部実装が漏れ、戻り値も無い（L32-L37）**
  - 統合元: A1-3、A1-4
  - 代案: `run_weekly_report(week_start: date, *, force: bool = False, dry_run: bool = False) -> SendResult`

**データとエラー**
- **[mid] 一部の宛先だけ失敗したことを検知できない（L49, L52）**
  - 統合元: A2-1、A3-4 のうち一部だけ送られる部分
  - 問題:
    - sendmail は一部の宛先が拒否されても例外を上げず、戻り値の dict で返す。例外だけを見る設計では L52 の方針が守られない。
    - L36 で接続済みの SMTP を外から受け取るため、リトライで誰が再接続するのか、何を単位にリトライするのかが決まっていない。
  - 代案:
    - 戻り値が空でなければ失敗として扱い、拒否された宛先を ERROR ログに出す。
    - 接続とリトライは mailer の中に持たせ、宛先ごとにリトライする。
- **[mid] 同じ週のレポートを二重に送る余地がある（L30, L44, L56）**
  - 統合元: A2-2、A3-4 のうち再実行で重複する部分
  - 代案:
    - 対象週と宛先をキーにした送信履歴を残し、送信済みの宛先は飛ばす。
    - CLI で送り直すときは `--force` を必須にする。
    - 多重起動はロックで防ぐ。

**運用**
- **[mid] 観測できる情報が足りない（L44, L57）**
  - 統合元: A3-2、A3-4 のうち HTML を捨てる部分
  - 代案:
    - 実行ID・対象週・段階ごとの所要時間・行数・リトライ回数・失敗した段階を構造化ログに出す。
    - 送信サマリ（件名と宛先ごとの結果）も残す。
- **[mid] ジョブが起動しなかったときに誰も気づかない（L48-L52, L57）**
  - 元の指摘: A3-3
  - 代案: 最終成功時刻を記録し、8日を超えたら警報を出すデッドマン監視を置く。
- **[low] 集計クエリのインデックスの前提と、週あたりの行数の上限が書かれていない（L34, L44, L61）**
  - L61 の「数万行」を上限として明記する。
- **[low] 旧版に戻す手順と、初回の dry-run 検証が書かれていない（L56）**
  - 上の `dry_run` を使い、送信せずに HTML だけ出力する手順を加える。

### 最優先で直す1点
**ReportManager の責務集中とスケジュールの二重管理（L15, L22, L24, L26）**

まずスケジュール管理を消し、残りを分ける。配置は、対象サービスのパッケージ直下に `report/` を置く想定。

| 配置 | 責務 |
|---|---|
| `report/repository.py` | `usage_events` から1週分を SELECT する（読み取りのみ） |
| `report/aggregator.py` | 行から集計結果への変換（純粋関数） |
| `report/renderer.py` | 集計結果から HTML への変換（jinja2 は中で組み立てる） |
| `report/mailer.py` | SMTP の接続、宛先ごとのリトライ、拒否された宛先の判定。`SendResult` を返す |
| `report/job.py` | `run_weekly_report(week_start, *, force, dry_run) -> SendResult`。上の4つをつなぎ、送信履歴を確認・記録する |
| `config/report.yaml` | 宛先リストだけを持つ（スケジュールの項目は消す） |
| cron 定義（既存のバッチ基盤） | スケジュールの唯一の持ち主 |

この分割で、次の3点もまとめて片付く。
- 配置先が書かれていない問題（A1-2）
- L22 と L34 の食い違い（SELECT の持ち主が repository に決まる）
- 送信結果の判定と冪等性の mid（実装する場所が mailer と job に決まる）

この裁定は設計段階のたたき台です。設計書に反映する前に、担当者が事実関係と既存のバッチ基盤との整合を確認してください。

## security-reviewer の起動
**no**

理由: 対象は既存のバッチ基盤で cron として動く社内向けの集計・メール送信バッチです。外部からの入力も、認証・認可も、外部に公開するエンドポイントもありません。SMTP クライアントは接続済みのものを受け取るだけで、設計書には秘密情報の扱いが出てきません。集計の途中結果はメモリだけに置き、HTML は送信後に捨て、キャッシュは L61 で行わないと決まっています。機微な情報をファイル・ログ・キャッシュに保存することもありません。SKILL.md は、このような「内部ライブラリ・バッチ処理」には起動しないとしているため、起動していません。
