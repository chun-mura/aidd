# 最終裁定: 契約書ファイル共有API 設計書

### 1. 統合した指摘（観点順、重複は統合済み）

**構造**
- **S-A 取引先の認可がどこにもない**（構造-2 とセキュリティ-1 を統合。セキュリティ-7 は修正案に含めた）— L29、L20-24、L33
- **S-B AccessLogger の仕様が足りない**（構造-4、データ-2、実用-2、セキュリティ-3 を統合）— L24、L45。次の点がどれも決まっていない。
  - 呼び出し元
  - 記録対象（成功・404・拒否・アップロード）
  - 書き込むタイミング
  - 失敗時に fail-open にするか fail-closed にするか
  - 項目（結果コード・送信元IP・リクエストID）
  - 保管先の分離と改ざん防止
- **S-C POST の入力と応答が決まっていない**（構造-5 と、セキュリティ-4 のうち取引先IDの指定権限・ファイル名の検証を統合）— L28、L33
- **S-D エラーのステータスと本文の形式が足りない**（構造-6）— L35-39
- S-E FileUploadApi に責務が集中し、S3 キーの体系を2つの API が暗黙に共有している（構造-3）— L22
- S-F コードを置く場所が書かれていない（構造-1）— L20-24
- S-G contract_files を誰が読むかが書かれていない（構造-7。書き込み側は L22 から読み取れるので、残るのは読み取り側だけ）— L33
- S-H ロールバック時に S3 と DB のデータをどう扱うかが書かれていない（構造-9 と実用-4 を統合）— L43

**データ**
- **D-A 署名付きURLを丸ごとログに残している**（構造-8、データ-1、実用-1、セキュリティ-2 を統合）— L45。L33 の「保存しない」とも矛盾する
- D-B S3 と DB の片方だけ成功したときの扱いがない（データ-3）— L22、L35-39
- D-C DB に行があるのに S3 に実体がない場合を検知できない（データ-4）— L29、L37

**実用**
- D-D 監視が既存の 4xx/5xx レートだけ（実用-3）— L44

**セキュリティ**
- X-A CSRF 対策と、PDF の中身（JavaScript・マルウェア）の検査がない。S3 キーを file_id から作る（セキュリティ-4 の残り）— L28
- X-B レート制限と同時実行の制限がない（セキュリティ-5）— L28、L43
- X-C 次の点が書かれていない（セキュリティ-6）— L29、L33
  - S3 バケットの保護（パブリックアクセスブロック・SSE・IAM の最小権限）
  - 302 応答の Cache-Control
  - 取引先アカウントの MFA

### 2. 矛盾の裁定

**2-1. 構造-6「401/403 を定義せよ」と、セキュリティ-1・セキュリティ-7「認可の不一致は 404」**
- 裁定: 両立する。次のように使い分ける。
  - 未認証: 401
  - POST で社内ロールがない場合: 403
  - GET で取引先が一致しない場合: 存在しない場合と同じ 404
- 根拠: L37 は、存在しない file_id への応答に「ファイルの存在有無以外の内部情報は含めない」と定めている。他社の file_id に 403 を返すと、その file_id が存在すると分かってしまい、この方針に反する。

**2-2. データ-1 は独立した指摘か**
- 裁定: 独立させず D-A に統合し、深刻度は D-A の high に揃える。
- 根拠: L33 と L45 の矛盾の原因は L45 の1か所なので、L45 を直せば矛盾も消える。「二重に残る」は言い過ぎだという refuter の判断は支持する。

**2-3. 構造-2 の代案「FileDownloadApi に照合を足す」と「FileAccessPolicy に分ける」**
- 裁定: どちらでも目的は果たせるので、矛盾ではない。
- 根拠: 本設計はエンドポイント2本の要約形式（L7）なので、FileDownloadApi の責務に照合を明記すれば足りる。Policy に分けるのは、プレビューなど別の取得経路が増えたときでよい。

### 3. 指摘を組み合わせて初めて見える問題（追加1件）

**N-1（mid）: 外部に返す 404 を揃えると、内部で失敗の理由を区別できなくなる**
- S-A の修正（不一致も 404）、D-D（404 の急増でアラート）、S-B（結果コードを記録）は、それぞれ単独では正しい。
- ところが外部への応答を揃えると、HTTP ステータスを見る監視からは、他社ファイルへの試行と、単に存在しない file_id とを見分けられない。
- 修正案: AccessLogger の結果コードに、内部用の区分 `ok / not_found / denied / s3_error` を持たせる。監視は `denied` の件数（ユーザー単位）でアラートを出す。

### 4. 深刻度の確定

| 区分 | 指摘 | 判断理由 |
|---|---|---|
| high | S-A 取引先の認可がない | 取引先アカウントがあれば、file_id を入手した時点で他社の契約書を取得できる。file_id の入手経路は、L45 のログや URL の転送など設計の中にある |
| high | D-A 署名付きURLのログ記録 | 署名付きURLは、持っていれば誰でも使える資格情報。ログ閲覧者はアプリの認可を通らずに5分間取得でき、X-Amz-Credential も90日間さらされる。目的の「障害調査での再現」は、リクエストIDと S3 アクセスログの突き合わせで代わりが利く |
| mid | S-B AccessLogger の仕様不足 | 監査が目的の機能なのに、失敗・拒否・アップロードが記録されず、否認を防げない |
| mid | N-1 拒否を内部で区別できない | S-A の修正を運用で検知するための前提 |
| mid | S-C POST の入力・権限・応答 | 誤った取引先に紐付けると、その取引先へ漏えいする。S-A の照合は、紐付けが正しいことが前提 |
| mid | X-A CSRF と PDF の中身の検査 | multipart は CSRF の対象になる。取引先の端末にマルウェアを届ける経路になりうる |
| mid | D-B S3 と DB の整合性 | 孤立したオブジェクトや、実体のないメタデータが生まれる |
| mid | S-D エラーの定義 | 2-1 の裁定どおりに追記すればよい |
| mid | D-D 監視 | N-1 とセットで直す |
| low（mid から下げた） | S-E 責務の集中 | 要約形式でエンドポイント2本の規模なので、分割は必須ではない。キー体系の論点は X-A で解決する |
| low（mid から下げた） | X-B レート制限 | アップロードは社内ロールに限られ、ダウンロードは 302 を返すだけで負荷が軽い。file_id は UUIDv4 なので列挙できない |
| low（mid から下げた） | S-F 配置、S-G 読み取り主体 | 記述が欠けているだけで、リスクは小さい |
| low | S-H、D-C、X-C | 変更なし |

### 5. 最優先で直すべき1点

**S-A: GET /api/files/{file_id} に取引先の認可を入れる**（L29）

D-A も high だが、悪用するにはログの閲覧権限が要る。S-A は取引先アカウントがあるだけで悪用でき、L45 のログや転送された URL から file_id が漏れたときの被害も、この欠陥を通して起きる。そのため S-A を先に直す。

L29 を次の文に置き換える。

> `GET /api/files/{file_id}` : 認証済みユーザーについて `contract_files` から `file_id` の行を取得し、取引先ユーザーはセッションの取引先IDと行の `対象取引先ID` が一致する場合のみ、社内ユーザーは社内ロールを持つ場合のみ、S3 署名付きURL (有効期限5分) を発行して302リダイレクトする。行が存在しない場合と不一致の場合はどちらも同じ 404 を返し、AccessLogger には内部区分 `not_found` / `denied` を分けて記録する。

あわせて次の2か所も直す。
- L23 の FileDownloadApi の責務に「contract_files の参照と、取引先IDの照合」を加える。
- L37 に「認可の不一致も 404」と書き足す。

（いずれも設計書を直すための提案で、ファイルには変更を加えていない。設計書に反映して実装・適用する前に、担当者がセキュリティ面を確認すること。）

**件数**
- high: 2件（S-A、D-A）
- mid: 7件（S-B、N-1、S-C、X-A、D-B、S-D、D-D）
- low: 7件（S-E、X-B、S-F、S-G、S-H、D-C、X-C）

**補足（スキルの規定による記載）**: Agent 6 が high/mid のセキュリティ指摘を出したため、実装後に `/security-review` を実行することを推奨します。

## security-reviewer の起動

yes。次の2つの条件に当たると、内容から判断しました（`--security` は付けていません）。
- **信頼境界を跨ぐデータフローがある。** 取引先ユーザーが呼ぶ外部公開の `GET /api/files/{file_id}` があり、セッション認証とロールによる認可を使い（L28-29）、外部入力のファイルを受け付けている（L28）。
- **機微情報をログに保存している。** 署名トークンを含む URL 全体を INFO ログに 90日保管している（L45）。このトークンは認証情報と同じ働きをする。
