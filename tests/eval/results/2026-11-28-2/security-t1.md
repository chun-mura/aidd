## arbiter の最終報告

**件数（統合後）: high 2 / mid 7 / low 7**

### 矛盾・注記への裁定
1. **構造-4「両APIがDBを直接触る」**: 設計書に書かれていないので外しました。分割の提案は low に下げています。要約形式の設計書（:7）に対しては過剰な要求だからです。
2. **実用-3「テーブル等の新設」**: 新設とは断定できません。そこで「:43 と :33 の関係が分からず、ロールバックの範囲を判断できない」と言い直して mid に残しました。
3. **セキュリティ-4**: PDF検証と20MB上限の部分は外しました。残したのは、アップロード先の取引先に対する認可、ファイル名のサニタイズ、レート制限で、mid としています。
4. **重複の統合**
   - 構造-1 とセキュリティ-1 → H1
   - 構造-2・データ-1・実用-1・セキュリティ-2 → H2
   - 構造-5・データ-3・セキュリティ-3・実用-2 の一部・low のアップロード監査 → M1
   - 構造の low「アップロード途中失敗」→ M4

### high
- **H1（セキュリティ/構造）IDOR**: :29 は認証済みであれば署名付きURLを発行し、:33 の対象取引先IDを照合していません。そのため取引先Aのアカウントで、取引先Bの契約書を取得できます。UUIDv4 は認可の代わりになりません。
- **H2（データ/実用/セキュリティ/構造）署名付きURLのログ保管**: :45 で署名トークンごとINFOログに90日残しており、:33 と矛盾します。5分以内ならログを読める人やログの転送先が使えます。失効した後は「再現する」という目的も成り立ちません。
  - 代案: クエリ文字列は記録しない。記録するのは時刻・ユーザーID・file_id・結果・有効期限だけにする

### mid
- **M1** AccessLogger の仕様が未定義です。認可拒否・アップロード・S3への直接アクセスを記録しない、fail-closed にするか決まっていない、一般のINFOログに混ざっている、の3点です。代案は、専用の出力先と権限を設け、書き込みに失敗したら発行を拒否し、S3アクセスログか CloudTrail で補うことです。
- **M2** アップロード側の取引先に対する認可、ファイル名のサニタイズ、上限をどこで強制するか、レート制限が無い（:28）
- **M3** インターフェースが未定義（POST成功時のレスポンス、パラメータの渡し方、401/403/413）
- **M4** S3保存とDB登録の一方だけが失敗したときの扱いが無い（書き込み順・補償処理・DB障害時の応答）
- **M5** デプロイとロールバックについて、:43 と `contract_files` の関係、migration、共有済みファイルの扱いが分からない
- **M6** 監視が足りない（502の分離・レイテンシ・404急増・アラート条件）
- **M7**（low から格上げ）背景 :11 で版管理を目的に挙げているが、それに対応するメタデータが無い

### low
- コードの配置と、既存のルーティング・認証との対応
- FileStorage/Repository への切り出し
- file_id のインデックスの前提
- 取引先アカウントの認証強度
- Referrer-Policy など、URLが漏れる経路への対策
- 権限不足も404に揃え、400の理由を固定文言にすること
- GETのレート制限

### 最優先で直す1点
**H1 の IDOR** です。H2 は有効期限とログの閲覧権限で被害が限られますが、H1 は取引先アカウントさえあれば外から他社の契約書を取得できます。直し方は次のとおりです。
- :29 を書き換え、取引先IDが一致したときだけ発行する。社内ユーザーが取得できる条件も書く
- 一致しないときは、存在しない file_id と同じ404を返す
- 責務表 :23 に、認可を FileDownloadApi の責務として書く
- 拒否したリクエストも AccessLogger で記録する

この報告は設計レビューの観点を整理したたたき台です。設計書に反映するかどうかは、担当者が確認して決めてください。

**セキュリティ委譲**: Agent 6 が high/mid のセキュリティ指摘を出しました。SKILL.md の規定どおり、実装後に `/security-review` を実行することを推奨します。

## security-reviewer の起動
**yes**。対象の設計は信頼境界を跨ぐデータフローを含みます。具体的には、取引先という外部ユーザー向けの公開エンドポイント `GET /api/files/{file_id}`、セッション認証と認可、外部から入力されるファイルのアップロードです。加えて、資格情報に当たる署名トークンをログに保存します（:45）。`--security` や `--no-security` の指定は無く、この条件判定で起動しました。
