## arbiter の最終報告

arbiter（aidd:design-arbiter）には、反証を経て残った9件、重複の関係、agent 間の矛盾（A1-3 と A3-2）、参考として low を渡しました。以下は報告の全文です。

> # 最終裁定: cases/structure.md
>
> ## 1. 統合した指摘（観点順、重複は統合済み）
>
> ### 構造
> - **S1+P1 責務の集約とスケジュールの二重定義** (L15, L22, L24, L26, L56)
>   ReportManager が6つの責務を持っている。そのうち「cron設定の読み込みと次回実行時刻の管理」は、L56 で起動を cron に任せているため不要であり、定義元が2か所になっている。
>   代案: まず P1 に従い、L15「送信スケジュール管理」、L22 の該当責務、L24 のスケジュール設定を削除する。残る収集・集計・整形・送信は repository / aggregator / renderer / mailer に分け、薄い service でまとめる。スケジュールを先に削除すれば、S1 の分割は4責務で済む。
> - **S3+D3 データ収集の責任の矛盾と依存の漏れ** (L22, L34-36, L48)
>   L22 は「クエリ発行は ReportManager」と書き、L34 は「呼び出し側が SELECT して渡す」と書いている。L22 と L34 の一方を本文で確認でき、矛盾は事実である。呼び出し側はスケジューラと CLI の2系統ある (L30) ので、SELECT・Jinja 環境の構築・SMTP 接続をそれぞれに重複して実装することになる。L48「集計クエリ失敗で中断」の担当者も決まらない。0件時の扱い（障害で空になったのか、本当に利用が0件なのか）も、判定する場所が無いため定義されていない。
> - **S2 配置パスの未記載** (L22)。low に格下げする（理由は3節）。
>
> ### データとエラー
> - **D1+P3 送信の部分失敗が観測されない** (L36, L49, L52, L57)
>   宛先の一部が拒否されても、smtplib は例外ではなく dict を返す。そのため L52「silent failure を作らない」という約束と矛盾する。リトライの単位は送信全体と読めるので、途中で失敗すると一部の宛先にだけ届き、リトライのたびに重複して送られる。
> - **D2+P3 冪等性と排他が無い** (L30, L44, L56)
>   2系統の呼び出し元、失敗後の手動再実行、リトライのどれでも同じ週のレポートが重複送信され得る。送信済みの記録も、再実行手順も無い。D2 と P3 の再実行の部分は同じ問題なので1件に統合した。
>
> ### 実用性
> - **P2 観測性の不足** (L57)
>   exit code だけでは、cron が起動しなかった場合を検知できない。exit code が出ないからである。0件時の扱いは S3+D3 に統合したので、ここでは扱わない。
>
> ### 新規（横断）: SMTP 接続の所有者とリトライが噛み合わない (L36 × L49)
> S3 は「接続済みの smtp_client を呼び出し側が渡す」ことを指摘し、P3 は「リトライ」を指摘している。2つを合わせると次の問題が見える。どちらの reviewer も単独では見ていない。
> - 送信が SMTPServerDisconnected などの切断で失敗した場合、ReportManager は接続を持っていないので再接続できない。
> - そのため L49 の「3回リトライ」は、切断された同じオブジェクトに3回送るだけになり、意味を持たない可能性が高い。
> - 代案: SMTP 接続を渡すのではなく、接続を作る factory（または mailer）をコンストラクタで注入する。リトライのたびに再接続できるようにする。
>
> ## 2. agent 間の矛盾への裁定: jinja_env / smtp_client の引数注入
>
> **裁定: 構造 reviewer の S3 を採る。実用性 reviewer の「テスト容易性」の論点は、コンストラクタ注入で満たせる。**
>
> 根拠:
> - テスト容易性を担保しているのは「依存を外から注入できること」であり、注入の場所がメソッド引数である必要はない。コンストラクタ注入でもモックを差し込める。実用性 reviewer も、括弧書きでコンストラクタ注入を許容している。
> - メソッド引数にすると、L30 の2系統の呼び出し元がそれぞれ Jinja 環境と SMTP 接続を構築することになる。その結果、構築ロジックが重複して波及する。
> - 1節の横断指摘のとおり、接続済みのクライアントを引数で受け取ると、L49 のリトライ（再接続）が成立しない。現状維持は機能面でも誤りである。
> - raw_rows を引数にすると、L22 との矛盾を生む。テスト容易性では正当化できない。
>

## security-reviewer の起動

no

理由: 対象は社内ダッシュボードの利用イベントを集計し、関係者にメールで送る既存バッチ上の cron ジョブです。外部入力、認証認可、外部公開エンドポイント、秘密情報の受け渡しは、設計書から読み取れません。SMTP クライアントは接続済みのものを受け取ります。機微情報をファイル・ログ・キャッシュに保存することもありません。レポートの HTML は送信後に破棄し、キャッシュは L61 で行わないと決定済みで、ログに出すのは送信件数だけです。以上から、SKILL.md の起動条件（信頼境界を跨ぐデータフロー、または機微情報の保存）には当たらないと判断しました。`--security` も `--no-security` も指定されていないため、条件判定の結果に従っています。
