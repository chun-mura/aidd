## 経路

- **前提の確認**: 対象 `cases/sensitive-cache.md` は1ファイル・48行です。指示に従い、小規模対象のショートカットは使わずに並列 dispatch しました。`.aidd/` ディレクトリが無いため、`review-dismissed.md` (棄却済み一覧) と `design-perspectives.md` はどちらもありません。
- **dispatch した agent** (すべて1つのメッセージで並列起動。渡したのは対象のパス、担当観点、「このファイルだけをレビューする」という指示のみ)
  1. aidd:reviewer: Agent 1 構造 (責務分割・インターフェース)
  2. aidd:reviewer: Agent 2 データとエラー (データフロー・データモデル・性能・エラー処理)
  3. aidd:reviewer: Agent 3 実用性 (YAGNI・運用)
  4. aidd:security-reviewer: Agent 6 セキュリティ
  5. aidd:refuter (sonnet): 反証ステージ。high/mid があったので起動しました
- **条件付きの agent**
  - Agent 4 (プロジェクト固有観点): 起動していません。`.aidd/design-perspectives.md` が無いためです。
  - Agent 5 (aidd:source-verifier): 起動していません。`--verify-sources` が指定されていないためです。
  - Agent 6 (aidd:security-reviewer): 起動しました。理由は「security-reviewer の起動」の節に書きます。
  - aidd:refuter: 起動しました。reviewer から high と mid の指摘が出たためです。
  - aidd:design-arbiter: 起動していません。depth が standard の場合、arbiter を起動するのは「agent 間に矛盾がある」か「Agent 5 がある」ときだけです。今回は Agent 5 がありません。また、どの指摘も同じ箇所を同じ向きに指摘していて、深刻度も揃っています (個人情報の保存は3つの agent がそろって high)。代案に「キャッシュを廃止する」か「キャッシュを分割して TTL を付ける」かの違いはありますが、どちらもプロンプト全文を保存しないという点で両立するので、矛盾ではないと判断しました。

## refuter の判定

high/mid の21件すべてについて**反証失敗**でした (どの指摘も成立)。根拠の要旨は以下のとおりです。

- A1-1 反証失敗: L18-26 の表と L46 のどちらにも、配置先が書かれていない
- A1-2 反証失敗: L25 (再実行を防ぐ) と L35 (問い合わせ対応) で、2つの用途が割り当てられている
- A1-3 反証失敗: 判定の担当が表に無い。L42 の「作り直す」が何を指すか定まらない。無効化の記述も無い
- A1-4 反証失敗: L23「すべてそのまま」によって全項目が流れ、L25 と L36 に影響が広がる
- A1-5 反証失敗: 表にログの担当が無い。L25・L26・L36 に複製される
- A2-1 反証失敗: 保存の順序が書かれていない。L41 は「キャッシュがあれば作り直さない」と読めるので、DB への書き込みに失敗した社員を取りこぼす可能性を否定できない
- A2-2 反証失敗: キーは `<社員番号>.json` だけで、再作成の条件は「キャッシュに無い」ことだけ
- A2-3 反証失敗: L26 は「書く」としか書いておらず、編集済みの下書きの扱いも無い
- A2-4 反証失敗: 飛ばしたときの終了コードが決まっていない
- A2-5 反証失敗: L40 が扱っているのは「エラーを返した」場合だけ
- A2-6 反証失敗: L22→L25→L35 (削除なし・022) と L36 (52週) の記述が一致する。L24「ネットワーク通信なし」は、ホスト内での複製を否定しない
- A3-1 / A3-2 反証失敗: 原文が指摘と一致する
- A3-3 反証失敗: A2-1〜A2-3 と同じ根拠で成立する
- A3-4 反証失敗: 監視は L47 の終了コードだけ
- A3-5 反証失敗: L46 にはロールバックとして cron の削除しか書かれていない
- SEC-1 反証失敗 (セキュリティ反証規則を適用): 攻撃手順は「同じホストの一般ユーザーが `/var/cache/onboarding-draft/*.json` を読む」。ディレクトリの権限が書かれていないので、この手順が成り立つ条件を排除できない。L30-31 (起動は cron だけ) と L24 は、ホスト内での読み取りを防がない
- SEC-2 反証失敗: L36 にプロンプト全文、本番での DEBUG、52週が明記されている。ログの権限は書かれていない
- SEC-3 反証失敗: 案内文 (L11) にこれらの項目が必要だという記述が無い
- SEC-4 反証失敗: 書き込み権限が書かれておらず、キャッシュから DB に書く経路が L41 から読み取れる。内容の検証も署名も無い

## 最終報告

> **design-review 結果: `cases/sensitive-cache.md` (入社案内文の作成バッチ 設計書) / depth=standard**
>
> 経路: 構造・データとエラー・実用性・セキュリティの4 agent を並列でレビュー → refuter で high/mid 21件を反証 → 全件成立。agent 間の矛盾が無く Agent 5 も無いため、arbiter は起動していない。重複した指摘は以下のとおり統合した。
>
> ### high (2件)
> 1. **キャッシュに個人情報を含むプロンプト全文を、期限なく・全ユーザーが読める状態で保存している** (L25, L35)。氏名・個人メール・携帯電話番号・自宅住所・生年月日が `/var/cache/onboarding-draft/<社員番号>.json` に平文で、umask 022 のまま、削除されずに残る。同じホストの一般ユーザーが全入社者分を読める。[SEC-1, A3-2, A2-6]
>    - 代案: プロンプト全文を保存しない。再実行するかどうかは `onboarding_drafts` の既存の行で判定し、キャッシュは廃止する。どうしても残す場合は、中身を下書きと入力のハッシュだけにし、ディレクトリを 0700・ファイルを 0600 にし、入社日から N 日後に削除することを設計書に書く。
> 2. **本番で DEBUG を有効にし、プロンプト全文を run.log に52週残す** (L36)。キャッシュとは別に、もう1系統で個人情報が約1年分残る。[SEC-2, A3-1, A2-6, A1-5]
>    - 代案: 本番は INFO に固定する。ログには実行 ID・社員番号・プロンプトのハッシュ・テンプレートの版・所要時間・結果だけを出す。ログを書く担当を責務表に加える。ログの権限は 640 にし、保持期間を短くする。
>
> ### mid (10件)
> 3. 案内文に要らない項目 (生年月日・携帯・自宅住所・個人メール) まで「すべてそのまま」プロンプトに入れている (L22-23)。Reader と Builder の入出力も決まっていない。→ 許可リストで項目を絞り、`Employee` 型と入出力を定義する。[SEC-3, A1-4]
> 4. 下書きをキャッシュと DB の2か所で持っていて、保存の順序が決まっていない。DB への書き込みに失敗した社員が翌日キャッシュヒットして作り直されないおそれがある。判定の担当も書かれていない (L25, L41-42)。→ DB を唯一の正本にし、DB に下書きがあるかどうかで判定する。処理の流れを明記する。[A2-1, A1-3, A3-3]
> 5. キャッシュのキーが社員番号だけなので、情報を直しても古い下書きが使われる。書き込み権限も書かれておらず、改ざんした文面が DB に入るおそれがある (L25, L41)。→ キャッシュを廃止するか、入力のハッシュと版をキーに含め、書き込み権限を限定し、スキーマを検証する。[A2-2, SEC-4]
> 6. DraftWriter の INSERT/UPSERT と、人事担当が編集した下書きを上書きするかどうかが決まっていない (L26)。→ 社員番号と入社日を一意キーにして UPSERT し、編集済みの行は上書きしない。[A2-3, A3-3]
> 7. 一部の失敗が終了コードに表れず、監視が終了コードだけになっている。起動漏れも所要時間の超過も検知できない (L40, L47)。→ 失敗が1件でもあれば非0で終了する。件数のサマリを出す。ハートビートと所要時間の閾値を監視に載せる。入社の N 日前になっても下書きが無ければ人事担当に通知する。[A2-4, A3-4]
> 8. モデルが正常終了したのに空や欠落のある出力を返した場合を扱っておらず、そのままキャッシュされる (L24, L40)。→ 書き込む前に検証し、検証に失敗したら飛ばし、キャッシュしない。[A2-5]
> 9. ロールバックが cron の削除だけで、書き込み済みの下書きを取り消せない。dry-run も無い (L46)。→ `--dry-run` を用意し、作成元の識別子を付け、ロールバックの手順を明記する。[A3-5]
> 10. DB に書き込むアカウントの権限、認証情報の保管方法、書き込みの追跡が書かれていない (L22, L26, L40)。→ `onboarding_drafts` だけを扱える専用アカウントを使い、認証情報はシークレットストアに置き、監査ログを残す (中身は残さない)。[SEC-5]
> 11. コンポーネントのコード上の配置 (ディレクトリ・ファイル) と、cron の設定の置き場所が書かれていない (L18-26, L46)。→ 表に「配置」列を足す。[A1-1]
> 12. DraftCache が「再実行の防止」と「後日の問い合わせ用の記録」の2つの責務を持っている (L25, L35)。→ 問い合わせには DB の下書きを使い、キャッシュの責務を1つにする (または廃止する)。[A1-2]
>

> high の 1・2 と mid の 3 は、根っこが同じ問題 (個人情報の過剰な取り込みと長期保存) です。「プロンプトに必要な項目だけを入れる」「プロンプト全文をキャッシュにもログにも残さない」の2点を設計に入れれば、被害の大半が消えます。そのうえで、キャッシュを廃止して DB の行で冪等性を判定すれば、mid の 4・5・12 もまとめて解消します。
>
> ### セキュリティ委譲
> Agent 6 が high/mid のセキュリティ指摘を出したので、**実装後に `/security-review` を実行することを推奨します**。

**件数**: high 2件 / mid 10件 / low 6件 (重複統合後。統合前の high/mid は21件で、すべて反証失敗)

## security-reviewer の起動

**yes**。この設計は機微情報 (氏名・個人メール・携帯電話番号・自宅住所・生年月日を含むプロンプト) を、ファイル (`/var/cache/onboarding-draft/<社員番号>.json`、L25・L35) とログ (`run.log` に DEBUG でプロンプト全文、L36) に保存します。これは Agent 6 の起動条件「機微情報をファイル・ログ・キャッシュに保存する場合」に当たります。キーワードで拾ったのではなく、内容から判断しました。外部入力や公開エンドポイントは無い (起動は cron だけ、L30) ものの、この条件だけで起動要件を満たします。`--security` と `--no-security` はどちらも指定されていません。
