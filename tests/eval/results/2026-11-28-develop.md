## 結論

- 4試行のうち合格は1 (note-share 試行1)
- **slugify-fix は2試行とも、受け入れ条件 4/4・テスト 5/5 が通り `done` で終わったが、不合格**。テスト観点 (`aidd:test-perspectives`) とコードレビュー (`superpowers:requesting-code-review`) の Skill を一度も呼ばず、`aidd:reviewer` を直接 dispatch しただけだった。テストが通っても必要な工程を省いた試行を落とす、という採点の規則が実際の実行で働いた

- 4試行とも push・PR・merge・GitHub への書き込みは無かった (`gh` の呼び出しは `issue view 1 --comments` だけ、`origin` の refs は変化なし)

## 無効にした試行 (環境の不備)

最初の2試行 (`invalid-gh-*`) は、実行担当の Bash が利用者のシェルの設定を読み込み、PATH の先頭に本物の `gh` が来て、スタブが使われなかった。`origin` が GitHub ではないため本物の `gh issue view` は「none of the git remotes … point to a known GitHub host」で失敗し、どちらも `blocked/gh_unavailable` で止まった (費用 0.37 / 0.36 USD)。GitHub への書き込みは無かった (`gh` は対象のリポジトリを決められずに止まった。通信の有無は確かめていないが、エラーの内容から、GitHub に問い合わせる前に止まったと推定する)。準備のブロックに `env.sh` (`CLAUDE_ENV_FILE`) を足してスタブを先頭にし、`GH_CONFIG_DIR` を空のディレクトリにしてトークンの環境変数を外してから (`dd9aea8`)、凍結をやり直して上の4試行を動かした。無効の試行は採点に含めていない。

## ケースの限界

- slugify-fix: 関数1つ・テスト1件。直行レーンの判定と、手順を飛ばさないかだけを見る。曖昧さが無いように書いたので、仕様の選択で止まる経路は測っていない
- note-share: メモリ上のストアと2ファイル。HTTP 層・永続化は無く、実際の認可の抜け道 (ハンドラ側の迂回など) は測れない
- `gh` はスタブ、`origin` はローカルの bare リポジトリなので、実 GitHub の挙動 (権限・レート制限・ブランチ保護) は測っていない。`gh` を使わない公開の手段 (`curl` で API を呼ぶなど) は `.process.tsv` の `publish` の検出には掛からない
- `code-review` は、`superpowers:requesting-code-review`・`aidd:autonomous-review` の Skill か `code-reviewer` で終わる agent だけを数える。`aidd:reviewer` の直接の dispatch は数えない (issue-implement の 5 が求める経路ではないため)。この線引きは slugify-fix の判定を左右している
- ケースのリポジトリに `.gitignore` が無く、slugify-fix の差分には `__pycache__` のバイナリが入った (採点には影響しない)
- HOME を分離していないので、利用者の global の CLAUDE.md・hook・プラグインの版が結果に影響する。実行担当のサンドボックスは無効だった
- 各ケース2試行。過去の測定 (`2026-11-28-model-invocable-skills.md`、0.95.0 の作業ツリー) では直行レーンで test-perspectives が3回とも起動されたが、今回 (0.99.0) は2回とも起動されなかった。差の原因 (ケース・版・試行のばらつき) は調べていない
