4. D-M5/P6 (インデックス) は **low** に下げる。実装段階で検出できる性能の詳細。

### high
- **H1** CS の「残高編集」画面による point_balances の直接書き換え (S1, D-H1, P3, X1 / 367, 246, 248, 74, 372行)
  - 63行と246行の規則に矛盾する。台帳にも operator_id にも残らず、画面のロールも決まっていない。翌日の再計算で上書きされ、drift メトリクスが誤発報する。
  - 代案: 手順と画面を削除し、訂正はすべて `POST /admin/v1/adjustments` で行う。
- **H2** 利用の判定と引き当てが仮付与まで対象にしている (S2, D-H4, X2 / 269-270, 51, 101, 236, 311行)
  - 仮付与を使った後に元の注文を返品すれば、ポイントを持ち逃げできる。
  - 代案: 判定を confirmed_balance だけにし、引き当ても `status='confirmed'` に限る。
- **H3** DB 書き込み失敗時に 200 を返して後から非同期で記録する (S7, D-H2, X4, P4 / 319行)。最優先の1点 (後述)。
- **H4** 冪等キーの保持 (24h) が再送期間 (72h) より短い (D-H3, P2, X3 / 361, 320, 109行)
  - 24h を過ぎた再送で二重に引き当てる。同じキーで中身の違うリクエストを照合しない。クリーンアップジョブが構成表にも監視にも無い。
  - 代案: 保持を7日以上にし、リクエストのハッシュを照合して違えば 422 を返す。ジョブを構成表と監視に追加する。
- **H5** 旧列の削除がデプロイより前にあり、ロールバックできない (D-H5, P1 / 302, 303, 339, 382行)
  - 代案: 同じリリースでは列を残して書き込みだけ止め、削除は次のリリースで行う。
- **H6** 状態を読んでから書く処理に排他が無い (D-H6 / 279-281行ほか)
  - 返還が並行すると二重加算になる。返品と確定、返還と失効の組み合わせも同じ。
  - 代案: FOR UPDATE または条件付き UPDATE を使い、ロック順序を `point_balances` → `point_grants` に統一する。
- **H7** D2 の全体延長が確定・失効・通知に反映されていない (S11, D-M4 / 379, 261, 285, 293行)
  - 代案: 確定時に会員の confirmed 付与全体の期限を更新する。または期限を会員単位の1列で持つ。

### mid

  - 代案: イベント経由に一本化する。

### 最優先で直すべき1点
**H3: DB 書き込みに失敗したとき「200 を返して redemption_retry で後から記録する」方式 (319行)**

理由:
- この1か所で、残高を確かめないまま支払いが成立し、redemption_id が無いため返還もできない。返還の経路 (M2・M5) がすべて塞がる。
- 失敗経路が2系統になり、二重に記録されるおそれがある。
- H4・M5 の直し方も、この経路が決まらないと決まらない。

代案:
- 書き込みに失敗したら 503 を返し、何もコミットしない。
- 注文サービスは 503 をタイムアウトと同じに扱い、320行のアウトボックスから同じキーで再送する。
- redemption_retry キュー、それを消費する処理、監視行 (351行) を削除する。
- 前提として、H4 の保持期間も同時に直す。
