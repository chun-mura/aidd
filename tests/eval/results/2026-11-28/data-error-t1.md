# 在庫数同期バッチ設計書 裁定レポート

**結論:** タイムアウトした商品を在庫0として書き込む仕様（L38）が最大の問題です。サイトに誤った在庫を出し、しかも監視では気づけません。指摘を統合した結果は high 3件、mid 6件、low 3件です。

### 構造・データ整合性

- **[high] H1 (L34) DB と Redis の在庫を守る責任者がいない**（統合元: S1, D2, D3 のうち ProductAdminService との競合の部分）
  - 書き込みは SyncBatch、削除は既存の ProductAdminService が担い、どちらも Repository と Cache を直接操作しています。
  - 次の事項が書かれていません。
    - どちらを正とするか（source of truth）
    - DB と Redis に書く順序
    - 片方だけ失敗したときの扱い
    - Redis の TTL
    - 不整合からの復旧手段
  - 廃番の削除とバッチの書き込みに排他がありません。廃番にした直後に、古い値で在庫行が作り直されることがあります。
  - 代案:
    - DB と Redis の扱いを InventoryService（upsert / remove / get）に集約する
    - DB を正とし、Redis は DB の書き込み成功後に更新または無効化する
    - Redis に TTL を付ける
    - 廃番は論理削除にし、UPSERT の対象から外す
- **[mid] M1 (L22) SyncBatch が WMS 呼び出し・処理の組み立て・永続化を兼ねている**（統合元: S2。high から下げた）
  - 本質は責務の分け方より、H2 と H3 の判定基準が無いことです。WmsClient を分離して型付き例外を返せば、L38 と L40 の判定を置く場所が決まります。H2 と H3 の修正に付随して直すものなので、mid に下げました。
- **[mid] M2 (L29-30) インターフェースの定義が足りない**（統合元: S4）
  - SyncResult のフィールド、StockApi のレスポンスと商品が存在しないときの挙動、Repository / Cache の署名が書かれていません。
  - 代案: SyncResult を `{processed, succeeded, failed, timed_out}` にする。
- **[mid] M3 (L22, L30) 規模の見込みがない**（統合元: D4）
  - product_id の主キー/インデックスの前提がありません。
  - 全件取得の件数と所要時間の見込み、5分間隔を超えたときの扱いもありません。所要時間が5分を超えると、M5 の多重起動につながります。

### エラー処理

- **[high] H2 (L38) タイムアウトした商品を在庫0として書き込む**（統合元: D1, O2, S5 のうちタイムアウトの部分）
  - 「データが取れなかった」と「本当に在庫が0」を区別できず、在庫があるのにサイトで売り切れと表示されます。
  - その件数はログにもメトリクスにも出ないので、誰も気づけません。
- **[high] H3 (L39) 書き込み失敗を失敗件数に数えず、exit code 0 で終わる**（統合元: D5, O1, S5 のうち書き込み失敗と終了コードの部分）
  - L29 の「失敗件数を返す」と矛盾しています（設計書本文で確認）。
  - 監視は exit code だけを見ている（L45）ので、全件の書き込みが失敗してもアラートは鳴りません。ERROR ログの仕様もありません。
  - 代案: failed に数えて ERROR ログを出し、閾値を超えたら0以外の exit code で終了する。
- **[mid] M4 (L40) 「全面的に落ちている」の基準が決まっていない**（統合元: D6）
  - 「5xx連続」の閾値、リトライとバックオフ、古い在庫をどこまで許すかが書かれていません。
  - 指摘を組み合わせると、次の問題も見えます。WMS が 5xx を返さずタイムアウトだけを多発させる半障害では、L40 が発動しません。すると L38 によって大量の商品が0で上書きされ、L39 と L45 によってバッチは正常終了扱いになります。
  - この問題は新しい指摘として独立させず、H2 の深刻度を裏付ける根拠として扱いました。

  - 代案: フィーチャーフラグで段階的に導入する。

### 矛盾の裁定

**論点: タイムアウトを「失敗」に数えるか、別枠で数えるか**
- D1 は失敗件数に数える案、S5 は `timed_out` として別に数える案です。
- 裁定: **別枠で数える S5 が正しい**と判断します。
  - 設計書は「WMS 側の欠測」（L38）と「自分たちの書き込み失敗」（L39）を別の事象として書いています。原因を切り分けるには、件数を分けておく必要があります。
  - ただし、0以外の exit code を出すかどうかの閾値判定には両方を含めます。この点で D1 の意図を取り込みます。

**その他**
- D2 の「DB を正にする」案と S1 の「InventoryService に集約する」案は両立するので、H1 として1件にまとめました。
- ほかに実質的な矛盾はありません。

### 最優先で直すべき1点

**H2 (L38): タイムアウトした商品を在庫0として書き込む仕様をやめる**

理由:
- 間違ったデータを本番のサイトに出す（顧客には売り切れに見える）指摘は、これだけです。
- H3 と M4 が重なると、その誤りが検知されないまま大量に広がります。
- H3 は「検知できない」問題、H1 は「整合性」の問題で、どちらも H2 ほど直接には顧客に影響しません。

代案:
1. タイムアウトした商品は DB にも Redis にも書き込まず、前回の値を残す。
2. `inventory` に `synced_at` を持たせる。StockApi は許容期間（例: 15分）を超えた値に stale フラグを付けて返し、表示側は「在庫確認中」などにする。
3. SyncResult に `timed_out` を加え、その件数を WARN ログとメトリクスに出す。
4. `timed_out + failed` が閾値（例: 全体の5%）を超えたら、0以外の exit code で終了する。これで H3 と M4 の半障害もまとめて検知できる。

## security-reviewer の起動

**no**

理由: SKILL.md の条件（信頼境界を跨ぐデータフローがあるか、機微情報をファイル・ログ・キャッシュに保存するか）を、設計書の内容から判断しました。どちらにも当たりません。
- `StockApi` は `/internal/stock/{product_id}` で、「サイト内部からのみ参照」と明記されています（L30）。外部に公開されるエンドポイントではなく、認証・認可の設計も対象に入っていません。
- 取り込み元の WMS は社内の倉庫管理システムで、利用者からの外部入力ではありません。秘密情報の扱いも設計の範囲に入っていません。
- 保存するのは在庫数だけです。個人情報や認証情報を DB・Redis・ログに置きません。
- 中身は内部のバッチ処理とキャッシュ層の変更です。SKILL.md が起動しない例として挙げる「内部ライブラリ・バッチ処理」に当たります。

`--security` も付いていないので、起動しませんでした。security-reviewer が無いので high/mid のセキュリティ指摘も無く、`/security-review` を勧める条件にも当たりません。
