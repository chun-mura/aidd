## arbiter の最終報告

**件数: high 2件 / mid 5件 / low 6件**

### 矛盾の裁定
1. L33「保存しない」と L45「URL全体を90日保管」は食い違っており、正しいのは L33 です。URL は5分で失効するため、L45 の保管には調査上の利点がなく、リスクだけが残ります。直すのは L45 です。
2. L43 の「ルーティング追加のみ」は、新テーブル `contract_files` が要ることと合いません。ただし、テーブルの追加だけなら revert しても既存機能は壊れないため、low とします。
3. 認可の指摘は、reviewer によって high (Agent6-2・Agent1-2) と mid (Agent2-4) に分かれていました。L29 に照合の記述がまったくないため、high とします。
4. AccessLogger 関連の4件 (Agent2-2 は high、残りは mid) は、どれも「監査ログを通常の INFO ログとして設計している」ことが原因です。1件に統合して mid とします。書込失敗時の挙動は、監査記録を専用経路に移さないと決められないため、その修正の中に含めます。

### high
- **H1 [認可] L29, L33**: ダウンロードに認可がなく、他社の契約書を取得できる (IDOR)。アップロード時の取引先ID指定 (M3) と、401/403 が未定義の件 (L4) も、この修正と一緒に直す
- **H2 [秘匿] L45**: 署名トークンを含むURL全体を INFO ログに記録している。悪用できるのは5分間だが、ログ転送基盤や閲覧権限者は5分以内に使える。代案: クエリ文字列は記録せず、file_id・objectキー・有効期限・リクエストIDだけを残し、S3アクセスログ/CloudTrail と突き合わせる

### mid
- **M1 [監査設計] L15, L24, L45**: 監査ログが通常ログ扱いになっている。記録対象・書込失敗時の挙動・改ざん耐性・保管先・閲覧権限・90日の根拠が、どれも決まっていない。代案: 通常ログから分けて追記専用の保管先に置く。すべてのリクエストとアップロードを対象にし、書込失敗時は fail-closed としてアラートを定義する
- **M2 [整合性] L22, L35-39**: アップロードで S3 と DB の一方だけが成功した場合の補償処理、障害ステータス、冪等性が設計されていない
- **M3 [入力] L28, L33**: アップロード時の対象取引先IDの扱い (指定フィールド・存在検証・担当範囲・成功時のレスポンス) が書かれていない。H1 の照合が効く前提になる
- **M4 [攻撃面] L28, L39**: 悪性PDF、ファイル名の扱い、受信中のサイズ上限、CSRF、レート制限 (補助的) が書かれていない
- **M5 [保管] L22, L33**: S3 の BPA・SSE-KMS・IAM ロール分離が書かれていない

### low
- L1 (L44): 監視項目が足りない
- L2 (L43): ロールバックの記述が実態と合っていない
- L3 (L18-24): コード上の配置が書かれていない。L7 で要約形式と宣言しているため low
- L4: 401/403 が定義されていない (H1 の修正で決める)
- L5: S3障害時にログへ記録する項目が決まっていない
- L6: 302 の Location ヘッダーでURLが露出する (`no-store` と `no-referrer` を推奨)

### 最優先で直すべき1点
**H1 (L29 のダウンロード認可)**。漏れるのは他社の契約書という機密文書で、悪用できる期間に制限がありません。H2 は5分間に限られ、M1 は事後に追跡できるかどうかの問題です。

代案は、L29 を次の趣旨に書き換えることです。
- 次のどちらかを満たすときだけ署名付きURLを発行する。
  - (a) リクエスト者の所属取引先ID = `contract_files.対象取引先ID`
  - (b) リクエスト者が社内ロールで、かつ当該取引先の担当範囲内
- 満たさない場合は、存在しない場合と同じく 404 を返す。未認証は 401。
- 認可の判定結果は、許可・拒否とも監査記録に残す。

あわせて、L28 のアップロード時に取引先IDを必須にし、検証する必要があります (M3)。

(arbiter 自身の注記) 設計書への反映と実装は、担当者が確認してから行ってください。

## security-reviewer の起動

**yes**

理由: この設計は信頼境界を跨ぎます。取引先ユーザーが使う公開エンドポイント `GET /api/files/{file_id}`、セッション認証とロールによる認証認可、社内ユーザーからのファイル入力があるためです。さらに、秘密情報にあたる署名トークン付きURLを INFO ログに90日保存します。SKILL.md の Agent 6 の起動条件のうち、「信頼境界を跨ぐデータフロー」と「機微情報をログに保存する」の両方に当たると、内容から判断しました。

Agent 6 が high のセキュリティ指摘を出したので、SKILL.md の「セキュリティ委譲」の規定に従い、実装後に `/security-review` を実行することを推奨します。
