# 評価結果 2026-11-07 (比較: design-review と素の Opus 5.5)

- plugin version: 0.51.0
- 目的: 各社の標準のモデルにそのまま頼んだ場合と比べて、design-review の多段構成 (reviewer → refuter → arbiter) に検出上の利点があるかを測る
- 実行ケース: structure / data-error / security (全3ケース)。それぞれ3回
- 比較相手: 同日の design-review `--depth=deep` の3回 (`2026-11-07.md`・`-2.md`・`-3.md`)

## ベースラインの構成

- モデル: Opus 5.5 (Agent tool の `model: "opus"`、`general-purpose`)。1ケース1回につき1体。計9体
- 汚染対策: ファイルのパスは渡していない。ケース本文に行番号を付けてプロンプトに埋め込み、「ファイルは読まず、ツールも使わない」と指示した。9体とも、ツールの使用は完了報告の1回だけだった
- プロンプト (本文の前に置いた全文):

  > 次の設計書をレビューし、問題点を列挙してください。各指摘に深刻度 (high/mid/low)、該当行、理由、代案を付けてください。
  >
  > ファイルは読まず、ツールも使わず、以下の本文だけを根拠に回答してください（左の数字は行番号です）。

- 採点: ケースごとに Opus 5.5 の採点エージェントを1体置いた。渡したのはキー・ケース・3回分の出力だけで、出力がどの構成から出たものかは伝えていない。コアシードの判定は、メインがキーの一致判定基準と照らして確認した
- 採点エージェントに渡した出力は、メインが要約したものである。深刻度・行番号・論点は残し、理由は要点に縮めた

## 事前に決めた判断基準

- ベースラインがコアで3回とも 7/7、かつデコイ誤検出 0 → 「このケースの難易度では、多段構成に検出上の利点はない」
- コアの取りこぼしまたはデコイ誤検出が3回のうち2回以上で再現 → 「多段構成に検出上の利点がある」
- 1回だけの差は揺らぎとして扱う

## キー外指摘

人が1件ずつ確認する手順 (eval の手順4) は、今回は行っていない。採点エージェントの分類を、次の2つの基準で判定済みとみなして採用した (ユーザー承認)。

1. 誤検出: 引用した行と主張が矛盾している、または本文に根拠がない
2. 判断保留: 同じ種類のどの設計書にもそのまま言える一般論で、この本文に固有の根拠がない (S3 の暗号化、PDF のマルウェアスキャン、レート制限、目標レイテンシなど)

| ケース | 3回とも出た正当な指摘 | 判断保留の主なもの | 誤検出 |
|---|---|---|---|
| structure | 二重送信を防ぐ仕組みがない (3回とも mid)、集計期間とタイムゾーンが決まっていない | 戻り値が None、宛先アドレスを yaml に書く、HTML エスケープ | 0 |
| data-error | 実行時間・多重起動・WMS のレート制限 | `/internal` の内部限定をどう実現するか (3回とも。偽指摘 PL-DE3 と同じ行だが「外部に公開されている」という主張ではない)、目標レイテンシ、導入手順 | 0 |
| security | 版管理がない、共有の取り消し手段がない、アップロード時に対象取引先を確かめない | S3 の保護設定、PDF の検査、ファイル名の無害化、レート制限、保持期間 | 0 |

ベースラインの出力でキーは育てない (昇格しない)。育てると、design-review との比較の分母が動くためである。

## 結論

**事前に決めた基準では、「このケースの難易度では、多段構成に検出上の利点はない」に当たる。** コア検出率は両方とも3回すべて 7/7、デコイ誤検出も両方とも0だった。コアの深刻度一致も同じ水準である (design-review 3〜5/7、ベースライン 4/7)。

基準の外にある差:

- **S6 (失敗の種類をログで見分けられない) は、ベースラインが3回とも見逃した。** design-review は3回のうち2回検出している。ただし S6 は design-review の出力から昇格したシードなので、拡張検出率はもともと design-review に有利に偏っている。これを根拠に多段構成の利点を主張するには、design-review の出力に由来しない欠陥で同じ差が出るか確かめる必要がある
- **コストはベースラインのほうが明らかに小さい。** ベースラインは3ケースで約17万トークン。design-review は refuter だけで約10万トークンかかり、そのほかに reviewer 3〜4体と arbiter (opus) が走る。総量は未計測だが、3倍以上と見積もられる
- **ベースラインは指摘が多く、一般論の low が混ざる** (1回あたり29〜34件)。design-review の最終報告の件数は記録していないので、ノイズの量は比べられない

## 制約と次に測ること

- ケースは3件だけで、どれも45〜61行と短い。両方ともコアで満点なので、天井効果で差が出ていない。長い設計書や、複数の節を照らし合わせないと見つからない欠陥では、まだ測っていない
- design-review の総トークンと最終報告の指摘件数を記録していない。同じ条件で比べるには、design-review の側でもこの2つを記録する必要がある
- 採点はベースライン側だけを盲検で行った。design-review 側の採点は、過去の結果ファイルを転記したものである (採点した主体と時点が違う)
- 1回あたりの標本は、それぞれ3回である
