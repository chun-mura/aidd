- **`/aidd:issue-split` の提案**: しなかった。この設計は横断的な変更で、分割できないと判断した。理由は、新サービス、注文サービスと会員サービスの改修、旧列の削除と残高の移行を、同じメンテナンス枠の1リリースで切り替える前提だからである (L299-303, L338)。

- **arbiter**: 起動していない。standard で arbiter を起動する条件は「agent 間の矛盾」または「Agent 5 の結果がある」ことだが、どちらにも当たらない。

## 最終報告

> # design-review 結果: 会員ポイント台帳サービス 設計書 (`cases/crosscut.md`)
>
> 経路: standard。構造、データとエラー、実用性、セキュリティ (条件に該当) の4観点で並列にレビューした → refuter で high/mid を26件検証した (反証成立は0件) → arbiter は起動していない (agent 間の矛盾が無く、Agent 5 も無い)。
> issue-split: 提案しない。新サービス、既存2サービスの改修、残高移行を同じメンテナンス枠で切り替える横断的な変更のため。
>
> ## high (6件)
> 1. **CS の「残高編集」画面が `point_balances` を直接書き換える** (L367)。これは L63・L246 の「書き手は `PointLedgerService` だけ」と矛盾する。台帳に記録が残らず、翌 03:00 の `BalanceReconcileJob` が上書きするので、修正は黙って消える。画面はスコープ、API、ロールのどこにも無い。→ 手順と画面を削除し、訂正は `POST /admin/v1/adjustments` (`CS_CORRECTION`) に一本化する。
> 2. **仮付与が利用できてしまう** (L269-270 と L51・L101・L235 の矛盾)。仮付与を使ってから返品すると、L311 が利用済み分を回収しないため、ポイントが持ち逃げされるか残高が負になる。→ 判定は `confirmed_balance` だけ、引き当ては `status = 'confirmed'` だけを対象にする。
> 3. **冪等キーの保持期間 (24h, L361) が再送期間 (72h, L320) より短い**。24h を過ぎた再送は新規扱いになり、二重に減算される (D6 により `order_id` に一意制約が無い)。→ 保持期間を再送上限より長くする (例: 7日)。リクエストの内容が一致するかも検証する。
> 4. **DB 書き込みに失敗すると、残高を確認せずに 200 を返し、`redemption_retry` に積む** (L319)。後で残高が足りなかったときの扱い、`redemption_id`、キューの消費者と DLQ が定義されていない。→ 503 を返し、L320 の「ポイント処理待ち」とアウトボックス再送に統一して、`redemption_retry` は廃止する。
> 5. **旧列 `members.point_balance` を動作確認の前に削除するため、ロールバックできない** (L302-303, D5, L339)。→ 列の削除を、動作確認と安定稼働の後の別リリースに分ける (D5 を見直す)。少なくとも削除前に退避を取り、「戻せない時点」と復元手順を書く。

## security-reviewer の起動

**yes**。この設計は信頼境界を跨ぐデータフローを含んでおり、起動条件に当たる。

- 認証・認可を伴う境界がある:
  - 注文サービス・会員サービス → PointApi (mTLS)
  - CS 管理画面 → PointAdminApi (VPN と社内 SSO、ロールによる認可)
  - ブローカーからの外部イベントの受信
- 機微情報を保存する:
  - 会員 ID に紐づくポイント台帳
  - 社員 ID (`operator_id`)
  - 自由記述の `note`

`--security` と `--no-security` はどちらも付いていないため、内容からこう判定した。
