## 経路

- **dispatch した agent**: `aidd:reviewer` を3つ、1つのメッセージで並列に起動した。Agent 1 は構造、Agent 2 はデータとエラー、Agent 3 は実用性を担当。各 agent には対象パス `cases/data-error.md` と担当観点だけを渡し、「このファイルだけをレビューする」と指示した。棄却済み指摘は「なし」として渡した。
- **起動しなかった agent**:
  - Agent 4（プロジェクト固有観点）: `.aidd/design-perspectives.md` が無いため起動しなかった。
  - Agent 5（source-verifier）: `--verify-sources` が無いため起動しなかった。
  - Agent 6（security-reviewer）: 後述の判定により起動しなかった。
- **refuter**: 起動した（`aidd:refuter`、sonnet）。high/mid の指摘があったため。渡す前に、3 agent の重複指摘を F1〜F12 に統合した。
- **arbiter**: 起動しなかった。standard で arbiter を起動する条件は「agent 間の矛盾」か「Agent 5 の結果」があることで、どちらにも当たらない。
  - F3 の深刻度は agent によって high と mid に分かれた。ただし問題の認識と代案の向きは一致しているので、矛盾ではなく深刻度の差と判断した。
  - 深刻度は refuter の判定（high が妥当）に従った。
- **小規模対象ショートカット**: 使っていない。指示どおり並列で dispatch した。

## reviewer の生指摘

### Agent 1 — 構造

3. **[mid] L34**: `StockApi` が read-through のロジックを持っている。キャッシュミス時に Redis へ書き戻すかと、その担当も不明。

4. **[mid] L20-25**: コンポーネントのコード上の配置（ディレクトリ・ファイル）が書かれていない。

5. **[mid] L27-30**: 次のインターフェースが定義されていない。
   - `SyncResult` のフィールド
   - `StockApi` のレスポンス形式と、未登録商品の扱い（404 か 0 か）
   - Repository と Cache の削除 API
   - 代案: 型、レスポンス例、エラーコード、公開メソッドの一覧を書く。
6. **[mid] L29 と L38-39**: `SyncResult` は「失敗件数を返す」とあるのに、L38-39 の扱いでは失敗が数えられない。戻り値が実態を表さない。
   - 代案: `SyncResult` に `timed_out` と `skipped` を持たせる。
7. **[low] L20-25**: Redis のキー形式と TTL を誰が管理するかが表に出てこない。
   - 代案: `InventoryCache` の責務に追記する。

### Agent 2 — データとエラー
1. **[high] L38**: WMS がタイムアウトした商品を在庫 0 として書き込む。欠測と在庫 0 を区別できず、在庫のある商品が売り切れ表示になる（silent failure）。
   - 代案: 前回値を維持し、失敗件数に数える。`synced_at` か TTL で鮮度を判定する。
2. **[high] L39**: 個別書き込みの失敗を失敗件数に数えず、exit code 0 で終了する。L29 と矛盾し、L45 の監視では全件が失敗しても検知できない。
   - 代案: 失敗件数に数え、ERROR ログを出す。失敗率が閾値を超えたら exit code を非0にする。
3. **[high] L34**: DB と Redis に二重に保持し、2つの処理が直接書き込む。
   - 非原子的な更新のため、片方だけ成功すると不整合が残る。
   - バッチの書き込みと廃番削除が競合すると、廃番商品が復活する。
   - 多重起動の防止と TTL の記載がない。
   - 代案: DB を正本とし、Redis は派生キャッシュにする。削除経路を統一し、多重起動をロックで防ぎ、TTL を付ける。
4. **[mid] L40**: 全面障害の判定基準（5xx が何回続いたら障害か）が曖昧。全面的にタイムアウトした場合は L38 の扱いで 0 になり、全商品が 0 で上書きされる。
   - 代案: 閾値を明記し、全面タイムアウトも障害として扱う。
5. **[mid] L34**: キャッシュミス時に Redis へ再投入するか、Redis 障害時に DB の負荷がどうなるか、DB にも行が無い場合に何を返すかが書かれていない。
   - 代案: それぞれの仕様を追記する。
6. **[mid] L22**: 全商品を件数の上限なく取得する。5分間隔に収まるか見積もりが無い。主キーの前提も書かれていない。
   - 代案: 件数と処理時間を見積もり、バルク処理にする。間隔を超えたときの扱いを決め、`product_id` を主キーとして明記する。
7. **[low] L45**: 監視できるのが件数の INFO ログだけ。
   - 代案: 最終同期時刻、失敗件数、所要時間をメトリクスにする。

### Agent 3 — 実用性
- YAGNI: 指摘なし。Webhook は「やらない」に明記されている（L16）。
1. **[high] L39**: 個別書き込みの失敗が、失敗件数にも exit code にもログにも出ない。
   - 代案: `failed` に数え、WARN/ERROR ログを出す。失敗率が閾値を超えたら exit code を非0にする。
2. **[high] L38**: タイムアウトを在庫 0 として書き込む。販売機会を失う。
   - 代案: 前回値を維持し、欠測件数として数える。TTL か最終同期時刻を持たせる。
3. **[mid] L45**: 監視が足りない。失敗件数、所要時間、WMS のレイテンシ、最終成功時刻、キャッシュヒット率、run_id が無く、バッチが実行されていないことも検知できない。
   - 代案: 1回の実行ごとに構造化ログを出し、同じ項目をメトリクスにする。「最終成功から N 分経過」と失敗率のアラートを設け、多重起動の防止を方針として書く。
4. **[mid] L34**: DB と Redis が乖離したときに、検知・修復する手段が無い。
   - 代案: DB を正本として書き込み順序を決める。TTL を付け、削除経路を統一する。
5. **[mid] L44**: ロールバックが「ジョブ定義の削除」だけで、書き込み済みのデータを戻す手順が無い。
   - 代案: Redis キーの削除と全件再同期の手順を書き、マイグレーションを後方互換にする。
6. **[low] L44, L15**: 段階導入の手順と、5分間隔にした根拠（WMS の負荷）が書かれていない。
   - 代案: DB だけに書き込んで確認してから Redis に切り替える。商品数とレート制限から間隔の根拠を示す。

> ## high (3件)
>
> **H1. WMS タイムアウトを在庫 0 として書き込む (L38)**
> 欠測と在庫 0 を区別できない。在庫のある商品が、次に同期が成功するまで売り切れと表示される。WMS が遅延している間はこの状態が続き、結果にも失敗として残らない。
> → タイムアウトした商品は書き込まずに前回値を維持し、欠測件数として `SyncResult` に数えて WARN ログを出す。`synced_at` か Redis の TTL で鮮度を判定し、上限を超えたら「在庫不明」を返す。
>
> **H2. 個別書き込みの失敗を握りつぶし、exit code 0 で終了する (L39、L29・L45 と矛盾)**
> 失敗が `SyncResult` にも exit code にもログにも出ない。L45 の監視は exit code に頼っているため、全件の書き込みが失敗しても検知できない。L29 の「失敗件数を返す」とも矛盾する。
> → 失敗件数に数え、商品 ID と原因を ERROR ログに出す。失敗率が閾値を超えたら exit code を非0にし、失敗件数を監視対象に加える。
>
> **H3. 在庫を DB と Redis に二重で持ち、複数の処理が直接書き込む (L34)**
> `SyncBatch` と `ProductAdminService` が、DB と Redis をそれぞれ別々に（原子的でなく）更新する。片方だけ成功すると不整合が残る。バッチの書き込みと廃番削除が競合すると、廃番した商品が復活する。ロック、書き込み順序、TTL、復旧方法のどれも書かれていない。
> → DB を唯一の正本とし、Redis は DB への書き込みが成功した後に更新する派生キャッシュ（TTL 付き）にする。廃番の削除は `InventoryRepository` / `InventoryCache`（または 1つの `InventoryService`）経由に統一する。バッチは廃番商品を書き込まないようにし、多重起動はロックで防ぐ。
>

> - **M3. 全件取得の規模と実行時間の見積もりが無い (L22、L15)**: 5分間隔に収まるか分からず、多重起動を防ぐ手段も無い。→ 商品数と処理時間を見積もり、バルク処理にする。間隔を超えたときの扱いを決め、`product_id` を主キーとして明記する。

## security-reviewer の起動

**no**

理由: メインで対象の内容から次のように判定した。
- `StockApi` は「サイト内部からのみ参照」（L30）の内部エンドポイントで、外部には公開されていない。
- 認証・認可の設計は対象に含まれていない。
- 保存するのは在庫数で、個人情報・プロンプト・認証情報のような機微情報ではない。
- WMS API の呼び出しには認証が伴う（L40）が、この設計は資格情報の保管や受け渡しを扱っていない。外部連携は既存の業務システムからの取り込みにとどまる。

よって、主体は内部バッチとキャッシュで、条件（信頼境界を跨ぐデータフロー、または機微情報の保存）のどちらにも当たらないと判断した。`--security` / `--no-security` の指定は無い。
