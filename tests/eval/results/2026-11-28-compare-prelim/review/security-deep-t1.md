## 経路

- **並列 dispatch（1メッセージで4 agent）**
  - `aidd:reviewer` — Agent 1 構造（責務分割・インターフェース）
  - `aidd:reviewer` — Agent 2 データとエラー（データフロー・エラー処理）
  - `aidd:reviewer` — Agent 3 実用性（YAGNI・運用）
  - `aidd:security-reviewer` — Agent 6 セキュリティ（条件判定で起動。理由は最後の節）
  - 各 agent には、対象パス `cases/security.md`、担当観点、「このファイルだけをレビューする」という指示だけを渡しました。棄却済み一覧は「なし」です。
- **起動しなかった agent**
  - Agent 4（プロジェクト固有）: `.aidd/design-perspectives.md` が無いため。
  - Agent 5（source-verifier）: `--verify-sources` を付けていないため。
- **refuter（sonnet）: 起動した。** reviewer の指摘に high/mid があったためです。4 reviewer の high/mid を重複統合して10件（F1〜F10）にまとめ、引用行と一緒に渡しました。F1・F2・F7・F10 にはセキュリティ反証規則を適用しました。
- **arbiter（design-arbiter）: 起動した。** deep 経路では、反証後に high/mid が残れば arbiter を起動します。今回は残っており、さらに reviewer 間で深刻度が食い違っていました（F1: mid か high か、F4: low か mid か、F5）。arbiter には、対象パスと指摘の要約だけを渡しました。
- **小規模対象ショートカット: 使っていない。** 対象は1ファイル46行ですが、指示どおり並列 dispatch の経路で進めました。
- **issue-split の提案: しなかった。** API 2本は1つの機能（契約書の共有）を構成し、独立してマージできる単位ではないと判断しました。
- `.aidd/review-dismissed.md` は存在しないため、棄却一覧はありません。

## security-reviewer の起動

**yes**

理由: 対象の設計は、次のように信頼境界を跨ぐデータフローを含み、機微情報をログに保存しています。どちらも起動条件に当たると、文書の内容から判定しました。`--security` は付けていません。
- **信頼境界を跨ぐデータフロー**: 外部の取引先ユーザーが使う公開APIエンドポイント（`GET /api/files/{file_id}`）と、セッション認証・ロールによる認可（L28-29）がある。
- **機微情報のログ保存**: 署名トークンを含む署名付きURL（認証情報に当たる）と、ユーザーIDを含む監査ログを、INFO ログに90日保管する（L45）。
