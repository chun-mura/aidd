## 経路

- **dispatch した agent**: `aidd:reviewer` を3つ、1つのメッセージで並列に起動しました。
  - Agent 1 — 構造
  - Agent 2 — データとエラー
  - Agent 3 — 実用性
  - 各 agent に渡したのは、対象パス `cases/structure.md`、担当観点、棄却済み一覧（なし）だけです。「このファイルだけをレビューする」と明示しました。
- **起動しなかった agent**:
  - Agent 4（プロジェクト固有観点）: `.aidd/design-perspectives.md` が無いためです。
  - Agent 5（source-verifier）: `--verify-sources` が付いていないためです。
  - Agent 6（security-reviewer）: 条件に当たらないためです（理由は最後の節）。
- **refuter**: 起動しました（`aidd:refuter`、sonnet）。high/mid の指摘があったためです。mid 6件（重複をまとめた後）を、引用箇所と対象パスだけ付けて渡しました。low は規定どおり refuter に回していません。
- **arbiter**: 起動していません。standard で arbiter を起動するのは、agent 間に矛盾があるときか、Agent 5 があるときだけです。今回はどちらにも当たりません。
  - 重なる指摘はありましたが、同じ方向の指摘です。Agent 2 の指摘1と Agent 3 の指摘2（二重送信）、Agent 1 の指摘5・Agent 2 の指摘2・Agent 3 の指摘3（スケジュールの二重管理）がこれに当たります。矛盾ではないので、メインでまとめました。
- **小規模対象ショートカット**: 使っていません（指示どおり並列 dispatch しました）。
- **その他の判断**:
  - `.aidd/review-dismissed.md` は無いので、棄却済み一覧は空です。
  - 独立してマージできる単位は1つしかないため、`/aidd:issue-split` は提案していません。
  - `--review-delta` の指定も無いため、全体をレビューしました。

## reviewer の生指摘

### Agent 1 — 構造
1. **mid** ReportManager の責務が多すぎる（L22、L26）
   - 収集クエリ・集計・HTML整形・SMTP送信・cron と次回実行時刻の管理の5つを、1クラスで持っています。変更の理由がすべてこのクラスに集まります。
   - 代案: `UsageEventRepository`、`WeeklyAggregator`、`ReportRenderer`、`ReportMailer`、`ReportSchedule` に分けます。全体の流れは、それらを順に呼ぶだけの薄い `ReportService.run()` で示します。
2. **mid** コード上の配置が書かれていない（L20-24、L7）
   - `ReportManager` のファイルパスがありません。既存構造との関係も書かれていません。
   - 代案: 表に配置の列を足します。既存の規約に沿っているか、外れるならその理由を書きます。
3. **mid** インターフェースから内部の都合が漏れている（L34-36）
   - 呼び出し側が SELECT した生レコード、`jinja2.Environment`、`smtplib.SMTP` を渡す形です。このため、スキーマ・テンプレートエンジン・送信手段を変えると呼び出し側すべてに波及します。
   - L22 の「収集クエリ発行」とも矛盾しています。
   - 代案: `generate_and_send(week_start: date) -> SendResult` とし、依存はインスタンスを作るときに注入します。
4. **low** メソッド名が処理内容と合っていない（L33）
   - `generate` という名前ですが、送信まで行います。
   - 代案: `generate_and_send` に変えるか、生成と送信を別のメソッドに分けます。
5. **low** 設定の持ち主が曖昧（L24、L22、L56）
   - スケジュールが cron と report.yaml の2か所にあります。
   - 代案: cron に一本化し、report.yaml には宛先だけを置きます。

### Agent 2 — データとエラー
1. **mid** リトライで二重送信が起きうる（L49、L24）
   - 送信単位（1通で全員に送るか、宛先ごとに送るか）が決まっていません。
   - リトライ対象のエラー種別（一時エラーか恒久エラーか）も、リトライ間隔も決まっていません。
   - 代案: 送信単位を書きます。宛先ごとに送るなら送信済みの宛先を記録し、リトライは一時エラーだけに絞ってバックオフを入れます。
2. **mid** スケジュールの持ち主が3か所ある（L22、L24、L56）
   - 代案: ジョブ定義に一本化し、「次回実行時刻の管理」を責務から外します。
3. **low** 集計クエリを誰が発行するのかが食い違っている（L22、L34、L48）
   - 代案: 持ち主を1つに決め、例外を上へ伝える責務も書きます。
4. **low** 取得件数が0件のときの扱いが無い（L52）
   - 空のレポートが「成功」として送られてしまいます。
   - 代案: 失敗として扱うか、WARN ログを出すかを決めます。
5. **low** インデックスの前提が書かれていない（L34、L61）
   - 代案: 取得条件の列とインデックスの有無を書きます。「数万行」が1週あたりか、テーブル全体かも明記します。

### Agent 3 — 実用性
- YAGNI の観点では指摘なしです。キャッシュは L61 で不採用と決まっており、L16 でスコープも絞られています。
1. **mid** 観測できる情報が足りない（L57、L44）
   - ログに出るのは、送信が成功したときの送信件数だけです。取得行数・所要時間・リトライ回数・失敗した段階は残りません。
   - 代案: 1回の実行につき1行の構造化ログを出します。項目は実行ID、対象週、行数、集計・整形の所要時間、送信件数、リトライ回数、結果と失敗段階です。
2. **mid** 一部の宛先にだけ送れた状態で再実行すると二重送信になる（L49、L57、L24）
   - 代案: 1通で全員に送って送信を一体にするか、宛先ごとの成否をログに残し、送る宛先を指定して再実行できるようにします。
3. **low** ロールバック手順が足りない（L56）
   - 手動CLIとスケジュール設定の扱いが不明です。
   - 代案: 次回実行時刻の持ち主を一本化し、ロールバック後に誤って送信されないことの確認項目を足します。
4. **low** ジョブが起動しなかったことを検知できない（L57）
   - 代案: 「実行されたこと」を見張る死活監視があるか確認し、無ければ設計書に1行足します。

## 最終報告

**design-review 結果: `cases/structure.md`（週次利用レポート自動生成機能）**
深さ: standard ／ 反証ステージを通過した high/mid をそのまま報告します（arbiter は起動していません）。

### mid（6件）
1. **ReportManager の責務が多すぎる**（L22、L26）
   - 収集クエリ・集計・HTML整形・SMTP送信・スケジュール管理の5責務を1クラスで持っています。変更の理由とテストで差し替える依存がすべてここに集まります。
   - 代案: Repository／Aggregator（純関数）／Renderer／Mailer に分けます。全体の見通しは、薄いオーケストレーター（`ReportService.run()`）で確保します。
2. **コード上の配置が書かれていない**（L20-24）
   - `ReportManager` のファイルパスと、既存構造との関係が書かれていません。
   - 代案: 構成表に配置の列を足し、既存の規約に沿っているか（外れるならその理由）を書きます。
3. **インターフェースから内部の都合が漏れていて、記述も矛盾している**（L34-36 と L22）
   - 呼び出し側に、SQL の発行、Jinja2 の環境構築、SMTP への接続を任せています。このため、スケジューラと CLI の両方で同じ処理を書くことになり、変更も両方に波及します。
   - 一方で L22 は、クエリ発行を ReportManager の責務としています。
   - 代案: `generate_and_send(week_start: date) -> SendResult` にし、DB・テンプレート・SMTP はインスタンスを作るときに注入します。クエリ発行の持ち主は1つに決めます。
4. **送信が一部だけ失敗したときに二重送信が起きる**（L49、L24）
   - 送信単位（1通で全員か、宛先ごとか）、送信済みの記録、再実行手順がありません。
   - リトライ対象のエラー種別と間隔も決まっていません。
   - 代案: 1通で全宛先に送るか、宛先ごとの成否を記録して、未送信の宛先だけ再送できるようにします。リトライは一時エラーだけにし、バックオフを入れます。
5. **送信スケジュールの持ち主が3か所ある**（L22、L24、L56）
   - cron のジョブ定義、`report.yaml`、ReportManager の次回実行時刻管理の3か所です。
   - 代案: バッチ基盤のジョブ定義に一本化し、`report.yaml` は宛先リストだけにします。ReportManager の「次回実行時刻の管理」は削ります。
6. **障害調査と性能分析に必要な情報を観測できない**（L57）
   - ログは、送信が成功したときの件数だけです。
   - 代案: 1回の実行につき1行の構造化ログを出します。項目は実行ID、対象週、取得行数、集計・整形の所要時間、送信件数、リトライ回数、結果と失敗段階です。

### low（4件、反証ステージなし）

## security-reviewer の起動

**no**

対象は、社内ダッシュボードの利用イベントを社内 DB から読み取り、cron のバッチで集計して、設定ファイルにある関係者へメールで送る設計です。起動条件と照らすと、次のとおりです。

- **信頼境界を跨ぐデータフロー**: 当たりません。
  - 外部からの入力、認証・認可、外部に公開するエンドポイントは含まれていません。
  - SMTP の認証情報は「接続済みの SMTP クライアント」として外から渡され、この設計の範囲に入っていません。
- **機微情報をファイル・ログ・キャッシュに保存するか**: 当たりません。
  - 集計の途中結果はメモリ上だけに置き、生成した HTML は送信後に破棄します（L44）。キャッシュはしないと決まっています（L61）。
  - ログに出すのは送信件数だけです（L57）。

意味の上で、どちらの条件にも当たらない内部バッチ処理と判断しました。そのため `--security` を付けない既定の判定に従い、起動していません。
