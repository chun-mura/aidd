## 経路

- **dispatch した agent**: `aidd:reviewer` を3つ、1つのメッセージで並列に起動した。各 agent には対象パス `cases/structure.md` と担当観点だけを渡し、「このファイルだけをレビューする」と指示した。
  - Agent 1: 構造(責務分割とインターフェース)
  - Agent 2: データとエラー(データフローとエラー処理)
  - Agent 3: 実用性(YAGNI と運用)
- **起動しなかった agent**
  - Agent 4(プロジェクト固有の観点): `.aidd/design-perspectives.md` が無いため起動しなかった。
  - Agent 5(外部情報源の検証): `--verify-sources` が付いていないため起動しなかった。
  - Agent 6(セキュリティ): 条件に当たらないと判定したため起動しなかった。理由は最後の節に書く。
  - `.aidd/review-dismissed.md` は無いので、棄却済みの指摘は「なし」として渡した。
- **refuter**: 起動した(sonnet)。high/mid の指摘が8件あったため。refuter には指摘・引用箇所・対象パスだけを渡した。
- **arbiter**: 起動した。理由は2つある。
  - `--depth=deep` では、反証後に high/mid が残れば arbiter を起動する決まりになっている。
  - reviewer 同士の見解が食い違っていた。インターフェース指摘 S2(mid)と DI 妥当の P1(low)である。
- **小規模対象ショートカット**: 使っていない。対象は1ファイル・62行で条件には当たるが、指示に従って並列 dispatch の経路で進めた。
- **issue-split の提案**: しなかった。対象は1つの機能を追加する設計で、独立してマージできる単位を2つ以上含まないと判断した。

## security-reviewer の起動

**no**。設計の中身を見て、起動の条件には当たらないと判断した。
- **外部とのやり取り**: 社内ダッシュボードの利用イベントを集計し、関係者にメールで送る社内のバッチ処理である。外部からの入力、認証・認可、外部に公開するエンドポイントは無い。
- **秘密情報**: SMTP は接続済みのクライアントを受け取る設計で、認証情報はこの設計の中で扱っていない。
- **機微情報の保存**: 途中の結果はメモリに置くだけで永続化しない(L44)。HTML は送った後に破棄する。キャッシュは使わないと決まっている(L61)。ログに出すのは送信件数だけ(L57)。機微情報をファイル・ログ・キャッシュに保存する箇所は無い。

認証情報をどこから取るかが書かれていない点は、運用の観点から low(L1)として報告に入れた。
