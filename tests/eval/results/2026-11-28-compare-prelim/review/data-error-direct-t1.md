## 最終報告

> **design-review 結果: `cases/data-error.md` (在庫数同期バッチ 設計書) — depth=standard**
>
> **high (2件)**
> 1. **タイムアウトした商品を在庫 0 で上書きする** (エラー処理)
>    - 問題: WMS API が一時的に遅れるだけで、在庫のある商品が品切れと表示されます。本当の在庫 0 と見分けがつかず、監視にも出ません。
>    - 代案: タイムアウトした商品は書き込まずに前回値を残す。失敗件数に数える。`last_synced_at` で鮮度を管理する。
> 2. **個別の書き込み失敗を握りつぶして exit 0 で終わる** (エラー処理)
>    - 問題: 失敗件数に数えずにスキップするため、DB と Redis の不整合を含めて誰も検知できません。
>    - 代案: `SyncResult` の失敗件数に数え、商品 ID をログに出す。閾値を超えたら非0で終了するか、アラートを出す。
>
> **mid (3件)**
> 3. **DB と Redis の二重管理で、どちらが正か決まっていない** (データフロー)
>    - 問題: `SyncBatch` と `ProductAdminService` がそれぞれ両方を直接書き込み・削除します。片方だけ成功したときの不整合や、廃番の削除とバッチの書き込みの競合への対策がありません。
>    - 代案: DB を正とし、キャッシュの更新と無効化を1つの経路にまとめる。廃番商品は同期の対象から外す。
> 4. **全商品を5分ごとに取得するのに、件数・所要時間・多重起動防止が書かれていない** (性能・同時実行)
>    - 代案: ページングで取得する。想定件数と所要時間を書く。ジョブに多重起動ロックを付ける。
> 5. **監視が exit code と同期件数だけで、1・2 の異常を検知できない** (運用)
>    - 代案: タイムアウト・取得失敗・書き込み失敗の件数と最終同期成功時刻をメトリクスにし、アラートを設定する。
>

> 6. コンポーネントごとのコードの配置先 (ディレクトリ・ファイル) が書かれていない。
> 7. Redis キーの TTL と、キャッシュミス時の書き戻し方針が書かれていない。

## security-reviewer の起動

**no**

起動するかどうかは、対象の内容を読んで判断しました。

- 外部に公開するエンドポイントはありません。`StockApi` は「サイト内部からのみ参照」です。
- 扱うデータは在庫数で、個人情報・認証情報・プロンプトといった機微情報ではありません。それをファイル・ログ・キャッシュに保存する設計でもありません。
- 「認証エラー」という言葉はありますが、WMS API が落ちたときの例として出てくるだけです。秘密情報の扱いや認証の仕組みは、この設計の変更範囲に入っていません。

以上から、SKILL.md の「バッチ処理などで、どちらにも当たらない設計」と判断しました。

ただし、WMS 連携の認証情報 (資格情報) をどこにどう置くかは、この設計書からは確認できていません。WMS が社外の SaaS で、資格情報を新たに持たせるなら、外部入力と秘密情報の条件に当たる可能性があります。その場合は `--security` を付けて再レビューしてください。

Agent 6 を起動しておらず、セキュリティの high/mid 指摘もないため、`/security-review` の推奨は付けていません。
