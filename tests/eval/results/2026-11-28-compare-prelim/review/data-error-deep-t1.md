## 経路

- **深さ**: `--depth=deep`。`--security` と `--verify-sources` は付けていません。`.aidd/` が無いため、棄却済みの指摘の一覧と Agent 4 (プロジェクト固有観点) はありません。
- **小規模対象ショートカット**: 使っていません。対象は1ファイル45行ですが、指示に従い通常の並列 dispatch にしました。
- **issue-split の提案**: していません。対象は「バッチ1本＋キャッシュ層の変更」で、独立してマージできる単位が2つ以上あるとは判断しませんでした。
- **dispatch した agent** (1つのメッセージで並列に起動):
  - aidd:reviewer ×3: Agent 1 構造 / Agent 2 データとエラー / Agent 3 実用性
  - 各 agent には対象パスと担当観点だけを渡し、「このファイルだけをレビューする」と明記しました。
  - Agent 5 (source-verifier) は、フラグが無いため起動していません。
  - Agent 6 (security-reviewer) は、下の判定により起動していません。
- **refuter (sonnet)**: 起動しました。理由は high/mid の指摘があったためです。
  - **1回目の実行は捨てました。** 私が reviewer の実際の報告を受け取る前に、指摘一覧を推測で書き、それを refuter に渡してしまいました。この結果は使っていません。
  - 実際の報告にある high/mid 18件 (S1〜S5、D1〜D7、P1〜P5) で refuter を再実行しました。下の判定は、すべてこの2回目の結果です。
- **arbiter (aidd:design-arbiter)**: 起動しました。理由は2つです。
  - deep では、反証後に high/mid が残っていれば起動します。
  - agent 間で矛盾がありました。DB と Redis の整合の問題を、データ観点は high とし、実用性観点は low としていました。

### design-review 最終裁定: 在庫数同期バッチ設計書

**件数 (統合後)**: high 2 / mid 5 / low 5

#### [high] H1. タイムアウトした商品を在庫0として書き込む (L38)

- **統合した指摘**: D1、P2、S5 の前半、D6
- **問題**: タイムアウトは「在庫が0」ではなく「値が取れなかった」状態です。L38 の処理ではこれが在庫0として DB と Redis に書き込まれ、実在庫を上書きして誤った売り切れ表示になります。L29 の失敗件数にも数えられないため、外から気づけません。
- **D6 もここに統合**: L40 が全面障害とみなすのは「認証エラー・5xx連続」だけです。WMS が全面的にタイムアウトしてもこの条件に当たらず、全商品が0で書き込まれたまま exit 0 で終わります。D6 の前半「5xx連続の閾値が未定義」も、直す箇所が同じ (全面障害の判定条件) なのでここに含めます。
- **L38 の理由について**: L38 は「欠測でページ表示を壊さない」ためと書いていますが、これは前回の値を残すだけで達成できます。L34 のとおり StockApi は Redis か DB の既存の値を読む構成なので、0を書き込む必要はありません。

#### [high] H2. 書き込み失敗を数えずに exit 0 で終わる (L39)

- **統合した指摘**: D2、P1、S5 の後半、P4 の一部
- **問題**:
  - 設計書の中で記述が矛盾しています。L29 は「SyncResult は失敗件数を返す」と書き、L39 は「書き込み失敗は失敗件数に数えない」と書いています。
  - L45 の監視は exit code と同期件数だけなので、書き込みが全件失敗しても監視上は正常に見えます。
  - S5 は H1 と H2 の言い換えなので、独立した件数には数えません。
- **代案**: 書き込み失敗を失敗件数に数え、product_id 付きで ERROR ログを出す。失敗率が閾値を超えたら exit を非0にする。

#### [mid] M1. DB と Redis の二重管理で、整合を保つ責務が定まっていない (L34)

- **統合した指摘**: D3、S2、D4、P5 の一部
- **未定義の点**: どちらが正のデータか、書き込む順序、片方だけ失敗したときの扱い、TTL、キャッシュミス時に Redis へ書き戻すか
- **書き込む側が2つ**: SyncBatch と ProductAdminService が、どちらも DB と Redis を直接操作しています。
- **D4 (廃番商品の復活)**: 廃番の削除とバッチの書き込みが並行すると、廃番商品の行やキーが復活します。SyncBatch が WMS の商品一覧を基準に回るなら、復活が毎回起きる可能性もあります。商品一覧の取得元が設計書に書かれていないため、ここは未確認です。
- **代案**: `InventoryStore` を1つ設け、正のデータ・書き込み順・削除の手順をそこにまとめる。

#### [mid] M2. 多重起動と後着上書きへの対策が無い (L15, L22)

- **指摘**: D5。5分間隔で動くのに、1回の所要時間が書かれていません。前回の実行が終わらないうちに次が起動し、古い取得結果が後から書き込まれる経路を否定できません。
- **代案**: ジョブにロックをかけて多重起動を防ぐ。または、取得時刻が新しい値だけを書き込む条件付き書き込みにする。

#### [mid] M3. インターフェースの契約が未定義 (L27-30)

- **統合した指摘**: S4、キャッシュミス時の再投入
- **未定義の点**: SyncResult のフィールド、StockApi のレスポンス形式と該当商品が無いときの応答、Repository と Cache のメソッド
- **mid のままにする理由**: H2 の矛盾は、SyncResult が定義されていないために生まれました。H1・H2 を直すときの受け皿になります。TTL と書き戻しは M1 に寄せました。

#### [mid] M4. 監視とログが足りない (L45)

- **統合した指摘**: P3、P4
- **監視に無い項目**: 実行時間、各件数 (成功・失敗・タイムアウト)、最終成功時刻、起動しなかったこと・重複起動の検知
- **ログ**: 件数を INFO で1行出すだけで、run ID も product_id 付きの失敗ログもありません。
- いずれも、H1・H2 を直したあとの観測手段として必要です。

#### [mid] M5. ロールバックがジョブ定義の削除だけ (L44)

- **指摘**: P5 のうち M1 に含めなかった部分
- **問題**: ジョブを削除しても、すでに書き込まれた誤った値 (H1 による在庫0など) は DB と Redis に残ります。TTL が未定義なので、Redis は古い値を返し続けます。
- **代案**: 書き込み済みデータの戻し方を決める (前回の値への復元か再同期)。Redis のキーを無効化する手順も書く。

#### low

- **L1 (S1)**: 配置が書かれていない。L7 で要約形式と宣言しているため low とします。
- **L2 (S3)**: WmsClient が無い。バッチ1本の規模なので low とします。
- **L3 (S6)**: StockApi が Cache と Repository の両方に依存している。M1 で解消します。
- **L4 (D7 と性能目標)**: 想定件数・所要時間・レート制限・`product_id` のインデックス前提・性能目標が書かれていない。要約形式なので low としますが、M2 の判断材料になります。
- **L5 (P6)**: DB と Redis の乖離を検知する手段が無い。

#### 矛盾の裁定: D3 の深刻度

- **結論**: D3 は mid に下げて M1 に統合します。乖離を検知する手段が無い点は low (L5) のままにします。
- **根拠**: SyncBatch は全商品を5分ごとに DB と Redis の両方へ書き込みます。そのため、片方だけ書き込みに失敗しても、乖離は次の同期でほぼ解消します。
- **乖離が長く残る場合**: 次の3つで、いずれも別の項目で扱っています。
  1. 書き込み失敗が数えられず、気づかれない (H2)
  2. 廃番の削除と同期が競合する (D4)
  3. TTL が未定義のまま、ジョブ削除で同期が止まる (M5)
- D3 を high にすると H2 と二重に数えることになります。
- 2つの観点は矛盾しているのではなく、別の問いに答えています。データ観点は「整合のルールが設計されていない」こと、実用性観点は「運用で乖離を検知できない」ことを指摘しています。

#### 最優先で直す1点

**代案** (L38 と L40 の書き換え):
1. タイムアウトした商品は DB にも Redis にも書き込まず、前回の値を残す。
2. SyncResult に `timeout_count` を追加し、失敗として数える。M3 で SyncResult のフィールドを定義し、H2 の書き込み失敗と同じ扱いにする。
3. `inventory` に `synced_at` 列を追加し、同期に成功した商品だけを更新する。StockApi は在庫数と一緒に `synced_at` を返し、古さの判断はサイト側に任せる。
4. L40 の全面障害の判定に「タイムアウト率が閾値を超えた場合」を加え、その場合は exit を非0にする。具体的な閾値は、件数の前提 (L4) が決まってから設定する。
