# 在庫数同期バッチ設計書のレビュー結果

指示どおり、ファイルやツールは使わず、貼られた本文だけを見て判断しました。

## high

### 1. タイムアウトした商品を在庫数 0 として書き込んでいる（L38）
- **理由:** 在庫があるのにサイトでは「在庫切れ」と表示されます。売り逃しにつながるうえ、正しい前回値を誤った値で上書きします。欠測でページ表示を壊さないことが目的なら、0 を書く必要はありません。「値が無い」と「在庫が 0」は別の状態なのに、区別できなくなっています。
- **代案:** タイムアウトした商品は書き込まず、前回値を残します。同時に `SyncResult` の失敗件数に数えます。必要なら、データに取得時刻を持たせて「古いデータ」として扱えるようにします。

### 2. 書き込み失敗を数えず、exit code 0 で終わる（L39）
- **理由:** L29 の「失敗件数を返す」と食い違っています。L45 の監視は exit code だけを見ているため、全件の書き込みが失敗していても正常終了に見えます。障害に誰も気づけません。
- **代案:** 書き込み失敗は失敗件数に数え、ログには商品 ID と例外を出します。失敗率がしきい値（例: N% 以上）を超えたら exit code を 0 以外にするか、アラートを出します。

### 3. DB と Redis を、2 つの処理がそれぞれ直接書き換えている（L34）
- **理由:**
  - 正のデータが DB か Redis か書かれていません。DB への書き込みだけ成功、Redis だけ失敗、といった片方だけの失敗をどう扱うかも書かれていません。
  - `ProductAdminService` が商品を廃番にして DB と Redis から消した直後に、`SyncBatch` が廃番前に取った在庫を書き込むことがあります。そうなると、消したはずの在庫が戻ってしまいます。
  - 同じデータを書き換える処理が複数あるのに、まとめて管理する場所がありません。
  - Redis のキーに有効期限（TTL）がありません。
- **代案:**
  - DB を正のデータと決めます。Redis はキャッシュと位置づけ、書き込みは `InventoryRepository` かそれをまとめるサービス 1 か所に集めます。
  - Redis への反映は「DB を更新したあとキャッシュを消す（または書く）」に揃えます。キーには TTL を付けます。
  - バッチは書き込む直前に廃番かどうかを見て、廃番なら書きません。または、廃番を論理削除で表すようにします。

## mid

### 4. 既存の `ProductAdminService` を変えるのに、スコープにも構成表にも載っていない（L7, L13-25, L34）
- **理由:** L7 では「単一バッチ + キャッシュ層の変更」として要約形式にしていますが、実際には既存の業務サービスにも手が入ります。その影響範囲がレビューの対象から漏れています。
- **代案:** `ProductAdminService` の変更を構成表とスコープに書き加えます。指摘 3 の対応で書き込みを 1 か所に集めれば、そもそも直接 Redis を消す処理は要らなくなります。

### 5. 全商品を 5 分ごとに取るのに、規模や処理時間の見積もりがない（L15, L22）
- **理由:** 商品数、WMS API のレート制限、1 回にかかる時間が書かれていません。処理が 5 分を超えると、次の回と同時に動いて二重実行になります。それを防ぐ仕組みもありません。
- **代案:** 件数と所要時間を見積もって書きます。二重実行はロックで防ぎます。WMS にまとめて取得する API や、差分だけ取る API があるかも確認します。

### 6. 監視が exit code と INFO ログだけ（L45）
- **理由:** 指摘 1・2 の問題も、データが更新されなくなる状態も見つけられません。
- **代案:** 最後に同期できた時刻を監視し、一定時間を超えたらアラートを出します。失敗件数と失敗率も監視対象にします。

### 7. ロールバックがジョブ定義の削除だけ（L44）
- **理由:** ジョブを止めても `StockApi`、`inventory` テーブル、`ProductAdminService` の変更は元に戻りません。すでに書き込んだデータの扱いや、デプロイの順番も書かれていません。
- **代案:** コンポーネントごとに戻し方を書きます。`StockApi` を以前の取得方法に戻すフラグを用意するなど、デプロイとロールバックの順番も決めます。

### 8. `StockApi` の振る舞いが決まっていない（L30, L34）
- **理由:**
  - 「サイト内部からのみ」を何で守るのか書かれていません。
  - 存在しない商品や、Redis にも DB にも無い商品に何を返すのか（404 か 0 か）が決まっていません。
  - キャッシュミスで DB を読んだあと、その値をキャッシュに入れるのかが不明です。
  - Redis が落ちたときの動きも書かれていません。
- **代案:** 応答の種類、キャッシュに入れるかどうか、Redis 障害時は DB に切り替える、といった点を書き足します。アクセス制限の方法も書きます。

### 9. 表示される在庫は最大 5 分遅れるのに、その扱いが書かれていない（L11, L16）
- **理由:** 表示上は在庫があるのに買えない、という食い違いが起きえます。その点を受け入れるのかどうかが書かれていません。
- **代案:** 「表示専用で、引当や購入可否の判定には使わない」と明記します。許容できる遅れも書きます。

## low

### 10. WMS が落ちているとみなす条件と、リトライの方針が書かれていない（L40）
- **理由:** 「5xx が連続したら」の回数が決まっていません。バッチの途中で失敗したときに、書き込み済みの商品をどう扱うかも不明です。
- **代案:** 何回続いたら失敗とするか、リトライ回数と待ち時間を書きます。途中で失敗した場合も、書き込み済みの分は正しいデータとして扱う、と明記します。

### 11. 目標とする数値が書かれていない（L11）
- **理由:** 「表示が遅い」がどれだけ良くなれば成功なのか判断できません。
- **代案:** 現在の値と目標値を書きます（例: p95 で ○ms 以下）。

### 12. `SyncResult` の中身が曖昧（L29）
- **理由:** 指摘 1・2 の直し方次第で、返す項目が変わります。
- **代案:** 成功件数、失敗件数、スキップ件数、取得できなかった件数を分けて定義します。

---

最優先は 1・2・3 です。どれも、誤った在庫が表示されても気づけないという同じ問題につながっています。設計書を直したら、実装に入る前に担当の方による再レビューをお勧めします。
