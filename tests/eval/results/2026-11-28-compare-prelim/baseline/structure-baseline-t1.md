# 週次利用レポート自動生成機能 設計書のレビュー

指示どおり、提示された本文だけを根拠にレビューしました。ファイルは読まず、ツールも使っていません。指摘は high 2件、mid 5件、low 4件です。

## high

**H1. 集計クエリを誰が発行するかが矛盾している（22行目と34行目）**
- **理由:** 22行目では、`ReportManager` が「利用イベントの収集クエリ発行」を担当するとしています。一方、34行目では呼び出し側が `usage_events` を SELECT して `raw_rows` として渡すことになっています。この矛盾のため、実装者によってクエリの置き場所が変わります。スケジューラと手動実行CLIの両方がクエリを書くと、集計期間の条件が2か所に分かれ、ずれるおそれもあります。
- **代案:** クエリは `ReportManager` 側（または専用の Repository）に一本化します。呼び出し側は集計期間だけを渡します。例: `generate(week_start: date)`。

**H2. インターフェースが内部実装を呼び出し側に押し付けている（33〜37行目）**
- **理由:** 次の3点が問題です。
  - `jinja2.Environment` と `smtplib.SMTP` を引数に取るため、テンプレートの構築とSMTP接続（認証を含む）の責務が、2つの呼び出し側にそれぞれ漏れています。
  - 「接続済み」SMTPクライアントを渡す方式では、リトライ中に接続が切れたとき誰が再接続するのか（49行目）が決まりません。
  - 戻り値が `None` のため、57行目の「送信件数ログ」をどこで出すのかが不明です。手動実行CLIも結果を確認できません。
- **代案:** 次のように変更します。
  - 引数は業務上の値（対象週、dry-run の有無など）だけにします。
  - テンプレートとメール送信は、`ReportRenderer` や `Mailer` などの抽象としてコンストラクタで注入します。
  - 戻り値は送信件数や対象期間を含む `ReportResult` にします。

## mid

**M1. `ReportManager` に責務が集中している（22行目、26行目）**
- **理由:** 1つのクラスが、取得、集計、整形、送信、スケジュール管理の5つを担っています。そのため単体テストではSMTPやDBのモックが常に必要になり、どの変更もこのクラスに及びます。26行目の「1ファイルで追える」という利点は、処理の流れを示す薄い統括関数でも得られます。
- **代案:** 集計（純粋関数）、整形、送信に分け、`ReportManager` は3つを順に呼ぶだけの統括役にします。

**M2. スケジュール管理が二重になっている（15行目、22行目、24行目、56行目）**
- **理由:** 56行目では、実行は既存バッチ基盤の cron が担います。それにもかかわらず、22行目では `ReportManager` が「cron設定の読み込みと次回実行時刻の管理」も担当し、24行目の yaml にも送信スケジュールがあります。実行時刻の正がどれなのかが曖昧で、yaml と cron 定義が食い違うおそれがあります。
- **代案:** スケジュールは cron のジョブ定義だけで管理し、yaml と `ReportManager` からは外します。15行目の「送信スケジュール管理」も「cron ジョブ定義の追加」に言い換えます。

**M3. 集計期間の定義がない（34行目、全体）**
- **理由:** 「週次」の境界が書かれていません。たとえば次の点が未定です。
  - 週の開始曜日
  - 何時に区切るか
  - タイムゾーン
  - 遅れて届いたイベントの扱い
  - 実行日がずれたときにどの週を対象にするか

  これらは手動実行（再送）のときに特に問題になります。
- **代案:** 期間の定義を明記し、手動実行CLIでは対象週を引数で指定できるようにします。

**M4. 再実行や部分送信のときに重複送信が起きる（49行目、56行目）**
- **理由:** 宛先が複数あり途中で失敗した場合、一部の宛先にはすでに送信済みです。そのため、再実行や手動実行で同じレポートが重複して届きます。リトライの間隔やバックオフ、リトライ対象とする例外の種類も書かれていません。
- **代案:** 次のいずれかを選び、設計書に明記します。
  - 全宛先を1通にまとめて送る（To/Bcc）。
  - 宛先ごとの送信済み記録を持つ。
  - 重複送信を許容する。

  あわせてリトライの間隔と対象例外も明記します。

**M5. レポートの中身（集計指標）が定義されていない（11行目、15行目）**
- **理由:** 何を集計するのかが書かれていないため、手作業の集計を置き換えられたかを確認できません。また、ユーザー単位のデータをメールに載せるかどうかが分からず、個人情報が含まれるか判断できません。
- **代案:** 現行の手作業レポートの項目を列挙し、集計の粒度（全体、部署、個人など）を明記します。

## low

**L1. 解決済みの「未定」記載が本文に残っている（40行目と61行目）**
- **理由:** 61行目で解決済みとしているのに、40行目の本文は「未定」のままです。40行目だけを読んだ人が誤解します。また、キャッシュはインターフェースとは関係のない話題です。
- **代案:** 40行目を「キャッシュは行わない（決定事項参照）」に書き換えるか、削除します。

**L2. 失敗の通知経路が2つ書かれている（48行目と57行目）**
- **理由:** 「cron の失敗通知」と「exit code をバッチ監視」が併記されており、どちらで検知するのかが曖昧です。
- **代案:** 既存のバッチ監視（exit code）に統一します。

**L3. ジョブが起動しなかったことを検知できない（57行目）**
- **理由:** exit code の監視では、ジョブが起動しなかった場合や cron 定義が消えた場合を検知できません。その結果、レポートが届かない状態に気づくのが遅れます。
- **代案:** 既存のバッチ基盤に未実行の検知があれば、それに乗せます。なければ、必要かどうかを判断した結果を設計書に書きます。

**L4. 宛先リストを yaml でリポジトリ管理している（24行目）**
- **理由:** 宛先を変えるたびにデプロイが必要になり、個人のメールアドレスがリポジトリに残ります。
- **代案:** メーリングリスト（グループアドレス）を1つだけ宛先にします。

---

最も優先度が高いのは、H1・H2・M2 の「責務の所在の矛盾」です。どれもインターフェースと構成表の書き直しで解消できます。
