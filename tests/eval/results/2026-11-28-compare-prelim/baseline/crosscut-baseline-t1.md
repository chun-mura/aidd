# 会員ポイント台帳サービス設計書のレビュー結果

指摘は全部で24件です（high 8件、mid 11件、low 5件）。根拠は提示された本文だけで、行番号は本文の左の数字です。

---

## high

### H1. 利用の際に、使えないはずの仮付与まで使っている
- **該当行**: 269, 270（関連: 51, 101, 116, 311）
- **理由**: 51行と101行では「仮付与は利用できない」としています。ところが269行の残高チェックは `confirmed_balance + pending_balance` で判定し、270行の引き当ても `status IN ('confirmed','pending')` を対象にしています。このため返品受付期間中のポイントが使えてしまいます。さらに311行は「仮付与は利用できないため、取消時に利用済みの分を考慮する必要はない」という前提で書かれています。仮付与から利用された後に返品されると、`remaining` だけが減算されて、利用済みの分は回収されません。目標の「返品時の回収漏れ0件」（23行）を満たせません。
- **代案**: 269行の判定を `confirmed_balance >= points` にし、270行の引き当て対象を `status = 'confirmed'` だけに限定します。あわせて、270行の「NULL の仮付与は最後」という記述を削除します。

### H2. 期限延長のルール（D2）が、確定・失効の処理に反映されていない
- **該当行**: 379（D2）と 261, 285–289, 154, 300, 122, 325
- **理由**: D2 は「付与が確定するたびに、保有する確定ポイント全体の有効期限を延長する」と決めています。しかし261行の確定処理では、確定した付与自身の `expires_at` しか設定していません。そのため、ExpireJob は付与ごとの古い期限で失効させてしまい、法務と合意した規約（第12条）に反します。さらに次の点も D2 と噛み合っていません。
  - 270行の「期限の早い順に引き当てる」
  - 122行・325行の「元の付与の期限を引き継ぎ、期限切れなら即時失効」
  - 154行・300行で、手動調整や移行が「獲得」に当たるか（期限を延長するか）が書かれていない
- **代案**: 期限は会員単位で持つ（例: `point_balances.expires_at`）のか、付与ごとに持って確定時に全付与を一括で UPDATE するのかを決め、確定・失効・返還・調整・移行の各処理に書き加えます。調整・移行が「獲得」に当たるかどうかは、規約の文言と合わせて法務に確認します。

### H3. DB書き込みに失敗したときに200を返し、後から非同期で記録している
- **該当行**: 319
- **理由**: 残高チェックも引き当ても行わずに成功として扱うため、次の問題が起きます。
  - 残高がマイナスになったり、同じポイントが二重に使われたりします。
  - `redemption_requests` に何も保存されないので、冪等性（同じ要求を何度送っても結果が1回分になる性質）が保てません。
  - 返す `redemption_id` が存在しないので、後で利用の返還ができません。
  
  320行にはすでに、アウトボックス（送信待ちの記録）からの再送で注文を保留する仕組みがあり、この方式は二重の仕組みにもなっています。
- **代案**: 書き込みに失敗したら 503 を返し、320行と同じ「ポイント処理待ち＋同じキーで再送」の経路に合流させます。`redemption_retry` キューと、それを監視する351行は削除します。

### H4. 冪等キーの保持期間（24時間）が、再送期間（72時間）より短い
- **該当行**: 361（関連: 320, 109）
- **理由**: 注文サービスは同じ `Idempotency-Key` で最大72時間再送します。一方、キーの記録は24時間で削除されます。タイムアウトの時点で実は処理が成功していた場合、24時間を過ぎてからの再送が新しい要求として扱われ、ポイントが二重に引き落とされます。
- **代案**: 保持期間を「再送期間の上限72時間＋余裕」（例: 7日）以上にします。2つの値の関係を決定事項として書き残し、どちらかを変えるときに連動して見直せるようにします。

### H5. CS 担当が `point_balances` を直接書き換える手順がある
- **該当行**: 367（関連: 246, 248, 37, 63）
- **理由**:
  - 「`point_balances` を書き換えるのは `PointLedgerService` だけ」（246行）と矛盾します。
  - 台帳に記録が残らないため、履歴の説明責任（13行、D1）が崩れます。
  - 03:00 の `BalanceReconcileJob` が台帳の値で上書きするので、修正自体も翌日には消えます。
  - スコープ（37行）に「残高編集」画面がありません。
- **代案**: 367行を削除し、残高の訂正も `POST /admin/v1/adjustments`（`CS_CORRECTION`）で行うよう統一します。

### H6. 旧列を削除した後は、注文サービス・会員サービスをロールバックできない
- **該当行**: 302, 339, 382（D5）
- **理由**: 手順4（302行）で `members.point_balance` 列を削除してから、手順5で新バージョンをデプロイしています。手順5や動作確認で問題が出て前バージョンに戻すと、前バージョンは削除済みの列を読み書きするため動きません。339行の「マイグレーションは戻さない」は、`point_db` 側だけを前提にした説明になっています。
- **代案**: 移行リリースでは列を残し、新しいコードからは参照しないようにします。あわせて、旧列への書き込みを止める措置（列の権限剥奪やトリガーでのエラー化）を入れます。列の削除は、安定を確認した後の別リリースで行います。D5 の理由（二重管理の防止）は、書き込み禁止の措置で満たせます。

### H7. 確定後に届いた返品は、自動で回収されない
- **該当行**: 313（関連: 254, 259, 309, 381）
- **理由**: 「確定は配送完了から15日後なので、確定後の返品は発生しない」としていますが、これは返品イベントが遅延なく届くことを前提にしています。14日目の深夜に受け付けた返品が、再配信のバックオフ（最大10回）や DLQ（失敗したメッセージを隔離するキュー）を経由すると、15日目 01:00 の確定に間に合いません。その場合 ERROR ログを出したうえで CS の手作業になり、目標の「回収漏れ0件」（23行）を満たせません。
- **代案**: 確定済みの付与に返品が届いた場合も自動で回収するよう定義します（`remaining` から `grant_cancel` し、不足分は残高のマイナスや回収待ちとして扱う）。あるいは、確定の前に注文サービスへ返品の有無を照会するか、確定日に余裕を持たせます。

### H8. 返品された注文で使われたポイントが返還されない
- **該当行**: 165–166, 278, 311
- **理由**: 返還の処理は `order.cancelled`（出荷前）にしかありません。`order.returned` には `redemption_id` が含まれず、返品時に利用分を返すかどうかが書かれていません。返品で代金を返金する一方で、ポイント利用分は会員に戻らないことになります。
- **代案**: `order.returned` を受けたときに、その注文の `active` な利用をすべて返還する処理を追加します。返品時に利用ポイントを戻すかどうかは返金ポリシーに関わるため、業務担当者に確認します。

## mid

### M1. 減算の手動調整で、どの付与から引くかが決まっていない
- **該当行**: 151–154
- **理由**: `adjust` で台帳と残高を減らしても、`point_grants.remaining` が減りません。そのため、後で ExpireJob が同じポイントをもう一度失効させ、残高と付与の合計が食い違います。
- **代案**: 減算の調整も利用と同じ引き当て処理（期限の早い順）で `remaining` を減らし、引き当て結果を記録します。誤付与の訂正のように特定の付与を取り消す場合は、`grant_id` を指定できるようにします。

### M2. 1つの注文に複数の利用があるのに、キャンセルイベントは1件分しか返還できない
- **該当行**: 166, 383（D6）
- **理由**: D6 は、1つの注文で「返還→再利用」が起きうることを認めています。しかし `order.cancelled` は `redemption_id` を1つしか持ちません。どの利用を返すのか曖昧で、取りこぼしも起きます。
- **代案**: イベントを `redemption_ids` の配列にします。あるいは、ポイント台帳側で `order_id` を使い、`active` な利用をすべて返還します。

### M3. 72時間タイムアウトして注文をキャンセルしたときに、利用ポイントが戻らない
- **該当行**: 320
- **理由**: 注文サービスはタイムアウトしたため `redemption_id` を受け取っていません。実際にはサーバー側で処理が成功していた場合、キャンセルイベントの `redemption_id` が null になり、ポイントが失われます。
- **代案**: キャンセル時に `Idempotency-Key` または `order_id` で利用を特定して返還する API を用意します。

### M4. 付与イベントが DLQ に入ったまま返品が先に処理されると、ポイントが付与されたままになる
- **該当行**: 309, 311–312
- **理由**: `order.delivered` が DLQ に滞留している間に `order.returned` が処理されると、付与がまだ無いため扱いが定義されていません。その後 DLQ から付与イベントを再投入すると、返品済みの注文に仮付与が作られ、確定まで進んでしまいます。
- **代案**: 付与が無い注文の返品を受けたら、`cancelled` の付与行（墓石）を INSERT します。後から付与イベントが来ても、一意制約によって何もしない（`DO NOTHING`）ようにします。

### M5. 移行の切り替え前後にまたがる注文の扱いが決まっていない
- **該当行**: 297–303
- **理由**:
  - 移行前に旧方式で配送完了の加算をした注文が、移行後に返品された場合: 付与行が無いため回収できません。
  - 移行前に旧方式で利用（列の減算）した注文が、移行後にキャンセルされた場合: `redemption_id` が null のため、ポイントが戻りません。
- **代案**: 返品受付期間内の注文と、キャンセルされうる注文を移行時に洗い出します。それぞれ移行用の付与・利用レコードを作るか、一定期間は手作業で対応するか、どちらにするかを決めて書きます。

### M6. 再計算ジョブが、通常の書き込みと競合する
- **該当行**: 248, 70
- **理由**: 台帳を集計してから上書きするまでの間に利用や付与がコミットされると、正しいキャッシュを古い値で上書きしてしまいます。また、自動で上書きすると不具合の痕跡が消えます。
- **代案**: 会員ごとに `point_balances` 行を `FOR UPDATE` でロックし、同じトランザクションの中で集計して上書きします。まず差分の検出だけを運用し、上書きは手順を経てから行うことも検討します。

### M7. `confirm` 行が points = 0 のため、台帳だけでは確定分と仮付与分を分けて再計算できない
- **該当行**: 248, 262, 220（D1）
- **理由**: D1 は「台帳から導出できるキャッシュ」としていますが、仮付与から確定への移動量が台帳に残りません。再計算には `point_grants` との結合と、状態を前提にした計算が必要になります。
- **代案**: 台帳に `confirmed_delta` と `pending_delta` の2列を持たせるか、再計算の式（どの表をどう結合するか）を設計書に明記します。

### M8. 日次ジョブと利用処理のロック順序が書かれていない
- **該当行**: 259–263, 285–289, 269
- **理由**: GrantConfirmJob と ExpireJob は `point_grants` と `point_balances` を更新しますが、ロックの取り方がありません。利用処理と並行して動くと、`remaining` の更新が失われたり（lost update）、デッドロックが起きたりします。
- **代案**: どの処理も、最初に `point_balances` の会員行を `FOR UPDATE` でロックするよう統一します。

### M9. 引き当てでポイントが足りなかったときの扱いが書かれていない
- **該当行**: 270, 291
- **理由**: 291行では「409 になる場合がある」としていますが、手順4には引き当てが不足したときの分岐がありません。要求ポイントの一部だけを引き当てたまま、全額を減算してコミットしてしまうおそれがあります。
- **代案**: 手順4に「引き当ての合計が要求ポイントに満たなければロールバックして 409」と明記します。

### M10. 移行したポイントが、全員同じ日に一斉に失効する
- **該当行**: 300, 379（D2 の不採用理由）
- **理由**: 移行したポイントの期限が全員「移行日＋365日」になるため、通知メールと問い合わせが1日に集中します。これは D2 が「年度末の一律失効」を不採用にした理由と同じ問題です（ただし D2 で期限が延長される会員は除きます）。
- **代案**: 集中を許容するかどうかを決定事項に追記します。避けるなら、最終購入日を起点にするなど、期限を分散させます。

### M11. 失効予定の通知が、ジョブが1日失敗しただけで送られなくなる
- **該当行**: 293, 331
- **理由**: 対象の条件が「ちょうど30日後」なので、ジョブが1日実行されないと、その日が期限のポイントは永久に通知されません。スコープの「失効予定の通知メール」（39行）を確実には満たせません。
- **代案**: 条件を「30日以内で、まだ通知していないもの」にし、通知済みのフラグを持たせます。

## low

### L1. 状態遷移の表に抜けがある
- **該当行**: 233–242
- **理由**: 325行の「`expired` の付与への返還→即時失効」が表にありません。また、`cancelled` と `expired` を「終端」とする記述と、325行で `remaining` を戻す処理が一見矛盾します。
- **代案**: 表に一時的な戻しの扱いを追記し、「状態は `expired` のまま」と明記します。

### L2. 確定日の基準があいまい
- **該当行**: 261, 330, 355
- **理由**: `expires_at` を「確定日＋365日」としています。ジョブを翌日に再実行すると、本来の `confirm_at` より1日遅い期限になります。
- **代案**: 期限を `confirm_at + 365日` にし、実行日には依存させないようにします。

### L3. 退会や会員の存在をどう判定するか、外部依存が書かれていない
- **該当行**: 103, 314
- **理由**: `point_db` には会員マスタが無いため、404 を返すことも退会済みを判定することもできません。会員サービスを呼ぶ経路や、その認証も定義されていません。退会した会員の残高をどうするかも書かれていません。
- **代案**: 会員サービスへの照会 API と、退会時に残高を失効させる処理を追記します。

### L4. 手動調整 API に冪等性が無い
- **該当行**: 145–154
- **理由**: ボタンの二度押しや再送で、調整が二重に記録されます。
- **代案**: `Idempotency-Key` を必須にします。

### L5. `note` に個人情報が入りやすく、10年間保持される
- **該当行**: 148, 204, 360
- **理由**: 自由記述欄で、問い合わせの内容などが書かれやすい欄です。
- **代案**: 入力の注意書きを画面に出し、`note` の参照権限を `point_admin` に絞ることを検討します。
