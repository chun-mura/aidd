# 会員ポイント台帳サービス 設計書のレビュー結果

いただいた本文だけを根拠にしています。指摘は全部で22件で、high が9件、mid が8件、low が5件です。深刻度の高い順に並べています。

## high

### H1. 有効期限の延長 (D2) が、確定の流れとデータモデルに反映されていない
- **該当行**: 379 (D2) と 186, 261, 285, 154, 300
- **理由**: D2 では、ポイントが確定するたびに、その会員の確定ポイント全体の期限が延びることになっています。しかし 261 行では、確定した付与1件の `expires_at` しか設定しません。また `ExpireJob` (285行) も付与ごとの `expires_at` で判定します。このままだと、継続して購入している会員でも、古い付与が規約に反して失効します。目標「改定後の規約どおりに失効させる」(22行) を満たせません。手動調整 (154行) や移行分 (300行) が延長のきっかけになるのかどうかも書かれていません。
- **代案**: 期限を会員単位で持つ方式にします。たとえば `point_balances.expires_at` を持ち、確定のたびに更新し、`ExpireJob` はこの値で判定します。付与単位のまま持つなら、確定のトランザクション内で、その会員の `confirmed` の付与すべての `expires_at` を更新すると書きます。あわせて、手動調整・移行・返還が期限の延長のきっかけになるかを決定事項に加えます。

### H2. 仮付与のポイントが利用できてしまう
- **該当行**: 269, 270 (51, 101 と矛盾)
- **理由**: 残高の確認に `confirmed_balance + pending_balance` を使い、引き当ての対象にも `pending` を含めています。しかし用語 (51行) と API (101行) では「仮付与は利用不可」と定義しています。さらに 311 行は「仮付与は利用されない」ことを前提に取消を組んでいます。その結果、仮付与を使ったあとに返品されると、付与の `remaining` と `pending_balance` がずれ、使ったポイントも回収できません。
- **代案**: 269 行は `confirmed_balance` だけで判定します。270 行は `status = 'confirmed'` だけを引き当ての対象にし、「NULL は最後」の記述を消します。

### H3. DB 障害時に 200 を返して、あとから記録する
- **該当行**: 319
- **理由**: 残高を確認しないまま利用を成立させるので、残高を超えて使えてしまいます (残高がマイナスになる)。あとから非同期で記録するときに残高が足りなければ、取り返す手段がありません。320 行の再送の仕組み (アウトボックスと Idempotency-Key) とも矛盾しています。また、`point_db` が書けない状態では `redemption_requests` にも保存できないため、冪等性も保てません。
- **代案**: 503 を返し、320 行と同じく注文サービスのアウトボックスから再送させます。`redemption_retry` キューとその監視 (351行) は削除します。

### H4. 冪等性キーの保持期間 (24時間) が、再送期間 (72時間) より短い
- **該当行**: 361 (320 と矛盾)
- **理由**: 注文サービスは同じキーで最大72時間再送します。24時間を過ぎてキーが消えたあとに再送が届くと、新しいリクエストとして扱われ、ポイントが二重に引かれます。
- **代案**: 保持期間を「最大再送期間 + 余裕」(例: 7日) にし、その関係を設計書に書きます。

### H5. CS が `point_balances` を直接書き換える手順がある
- **該当行**: 367 (246, 371, D1 と矛盾)
- **理由**: `point_balances` を書くのは `PointLedgerService` だけという原則 (246行) と、DB への直接接続の制限 (371行) に反します。台帳に記録が残らないので、目標の「台帳だけで説明できる」が崩れます。しかも 03:00 の `BalanceReconcileJob` が台帳の値で上書きし直すため、直しても元に戻ります。
- **代案**: この手順を削除し、「手動調整」(`POST /admin/v1/adjustments`, `reason_code=CS_CORRECTION`) に一本化します。

### H6. 台帳だけでは `confirmed` と `pending` の内訳を再計算できない
- **該当行**: 248, 262 (220 の D1「台帳から導出できる」)
- **理由**: `confirm` 行は points = 0 です (262行)。そのため台帳を合計しても総残高しか出ず、`confirmed_balance` と `pending_balance` の内訳は分かりません。`BalanceReconcileJob` が仕様どおりに作れません。
- **代案**: どちらかを選びます。
  - 再計算の元を `point_grants` の status ごとの `remaining` の合計にする
  - 台帳に「区分の移動」を表す列 (例: `pending_delta` / `confirmed_delta`) を持たせ、`confirm` 行に移動量を記録する

### H7. 列を削除するため、旧バージョンへのロールバックができない
- **該当行**: 302, 339, 382 (D5)
- **理由**: 339 行は「前のイメージを再デプロイすれば戻せる」としています。しかし前のバージョンの注文サービス・会員サービスは `members.point_balance` を参照しています。列は 302 行で削除済みなので、戻した直後から動きません。さらに、列の削除 (302行) は新しいサービスのデプロイ (303行) より前に行われるので、動作確認に失敗しても戻せません。
- **代案**: 列は後のリリースで削除する (expand/contract) 方式にします。誤った参照・更新を防ぐという D5 の狙いは、旧列への書き込み権限を外す、トリガーで更新を拒否する、といった方法で満たせます。

### H8. 移行の前に始まった注文の返品・キャンセルでポイントを回収・返還できない
- **該当行**: 299–303, 311–313, 278
- **理由**: 旧方式では配送完了時に残高へ直接加算しています (78行)。そのため、移行の時点で返品受付期間 (14日) 内にある注文には `point_grants` の行がありません。ここに `order.returned` が届いても、どう扱うかが定義されておらず、目標の「回収漏れ0件」を満たせません。同じように、旧方式でポイントを使った注文がキャンセルされると `redemption_id` が null なので、ポイントが返還されません。
- **代案**: 移行の対象と例外処理を書き足します。
  - 移行時に、直近14日以内に配送完了した注文の付与分を `migration` ではなく注文ごとの `purchase` の付与として作る
  - または、`order.returned` で付与が見つからないときは移行分から差し引く

  旧方式で利用した分の返還も同じように扱いを決めます。

### H9. マイナスの手動調整で、どの付与を減らすかが決まっていない
- **該当行**: 151–153
- **理由**: 台帳に `adjust` を書いて残高を減らしても、付与の `remaining` が減らなければ、あとで `ExpireJob` がその `remaining` を失効させます。その結果、二重に減算されて残高がマイナスになり、再計算 (H6) でも食い違いが出ます。
- **代案**: マイナスの調整も利用と同じ引き当ての規則 (期限の早い順) で付与の `remaining` を減らし、引き当ての内訳を記録すると書きます。

## mid

### M1. 返品された注文で使っていたポイントを返還する経路がない
- **該当行**: 165, 278
- **理由**: ポイントを返還するのは `order.cancelled` (出荷前) だけです。配送後に返品された注文で使っていたポイントが会員に戻りません。`order.returned` には `redemption_id` も含まれていません。
- **代案**: `order.returned` に `redemption_id` を加え、返品時にも返還を行います。返品時にポイントを戻さない方針なら、その旨を決定事項に書きます。

### M2. 確定後に返品イベントが届くケースを「発生しない」としている
- **該当行**: 313
- **理由**: 再配信 (最大10回の指数バックオフ) や DLQ からの再処理で、イベントが遅れて届くことがあります。その場合、受付が14日以内でも、イベントの処理が確定 (15日目の 01:00) より後になり得ます。このとき ERROR ログを出して CS が個別に対応するだけでは、回収漏れが残ります。
- **代案**: 確定済みの付与に対する取消処理を定義します。`remaining` から回収し、足りない分はマイナス残高として持つか、自動で調整します。あわせて `returned_at` が受付期間内かどうかを判定条件にします。

### M3. `item_amount` が場所によって違う意味で使われている
- **該当行**: 112, 117, 164
- **理由**: 利用 API (117行) では「送料を除く商品代金」で、ポイント利用分を含みます。一方、`order.delivered` (164行) ではポイント利用分を除いています。同じ名前なので実装を取り違えやすく、付与率 (D3) を誤るおそれがあります。
- **代案**: 名前を分けます (例: `item_amount` と `grantable_amount`)。

### M4. 照合ジョブが、実行中の更新を古い値で上書きするおそれがある
- **該当行**: 248
- **理由**: 再計算と上書きの間に利用などの処理がコミットされると、古い値で上書きしてしまい、新たなずれを作ります。また、自動で直すと不具合の原因が見えにくくなります。
- **代案**: 会員の行を `FOR UPDATE` でロックしてから再計算・上書きします。自動修正はやめて「検出と通知のみ」にし、修正は手動調整で行う方法も検討してください。

### M5. ロックを取る順番がジョブと API で違い、デッドロックが起きうる
- **該当行**: 259–263, 285–289, 269–270
- **理由**: 利用は `point_balances` → `point_grants` の順にロックします。一方、確定・失効ジョブは付与を更新してから `point_balances` を更新します。両者が同時に走ると逆順でロックを取り合います。
- **代案**: どのトランザクションでも、最初に `point_balances` の会員行をロックすると決めます。

### M6. 72時間後に注文をキャンセルしたとき、成立していた利用が取り残される
- **該当行**: 320
- **理由**: 最初の呼び出しがタイムアウトしても、サーバー側では成立していることがあります。その後の再送がすべて失敗して注文がキャンセルされると、注文サービスは `redemption_id` を知らないので、ポイントを返還できません。
- **代案**: `Idempotency-Key` か `order_id` を指定して返還できる API を用意し、キャンセル時に必ず呼びます。

### M7. 失効の直前 (00:00〜00:30) の利用で、残高確認後に引き当てが足りなくなった場合の扱いがない
- **該当行**: 291, 269–270
- **理由**: 手順3では残高が足りると判定され、手順4で引き当てが足りなくなります。この場合の扱いが定義されていません。「409 になる場合がある」とは書かれていますが、どの手順で返すのかが不明です。また、この時間帯は残高 API が利用できない分を表示します。
- **代案**: 引き当てが足りない場合は 409 を返す、と手順4に書きます。残高 API も、期限切れの分を除いて返すようにします。

### M8. 失効予定の通知が、ジョブ失敗や期限の延長に対応できない
- **該当行**: 293, 331
- **理由**: 「ちょうど30日後」という条件だと、ジョブが1日失敗しただけで、その日に該当する会員には永久に通知が届きません。また D2 の延長 (H1) が起きると、通知した期限日が実際とずれます。
- **代案**: 対象を「30日以内に失効し、まだ通知していない」とし、送信済みかどうかを記録します。

## low

### L1. 確定日を基準に期限を計算している
- **該当行**: 261
- **理由**: `expires_at = 確定日 + 365日` なので、ジョブを遅れて再実行すると期限がずれます。
- **代案**: `confirm_at + 365日` とします。

### L2. ID の型と例が一致しない
- **該当行**: 115, 134 / 200, 211
- **理由**: `redemption_id` は uuid 型と定義されていますが、例は `r_1` です。
- **代案**: 型か例のどちらかに揃えます。

### L3. 会員の存在や退会をどう判定するかが決まっていない
- **該当行**: 103, 314
- **理由**: `point_db` には会員の情報がないので、404 にするか、退会済みとして扱うかを判断する材料がありません。退会時に残高をどうするかもスコープに入っていません。
- **代案**: 会員サービスに問い合わせるのか、イベントで知るのかを決め、退会時の残高の扱いを「やる/やらない」に書きます。

### L4. エラーのレスポンスも冪等性キーで保存するのかが書かれていない
- **該当行**: 229, 272
- **理由**: 409 などのエラーも保存するかどうかで、再送したときの結果が変わります。
- **代案**: 保存するのは 200 だけとし、409 と 422 は保存しない、などと明記します。

### L5. 照合ジョブについて、アラートと手順が矛盾している
- **該当行**: 332, 350, 356
- **理由**: `BalanceReconcileJob` が失敗すると、「最終成功時刻が26時間以上前」でオンコールに通知が飛びます。しかし手順は「再実行しない」なので、通知を受けても対応することがありません。
- **代案**: このジョブは監視の対象から外すか、手動で再実行してよいことにします (M4 のロックを入れれば安全に再実行できます)。

---

まず直す必要があるのは H1〜H5 です。いずれも規約違反、ポイントの二重利用、台帳の信頼性に直結します。D2 の解釈 (H1) と移行前の注文の扱い (H8) は、法務・CS・経理と相談して決める内容なので、最終的な判断は担当者の方で行ってください。
