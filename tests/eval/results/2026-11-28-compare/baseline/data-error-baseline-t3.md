# 在庫数同期バッチ設計書のレビュー結果

指示どおり、提示された本文だけを根拠にしています。high 4件、mid 4件、low 4件です。

## high

### 1. タイムアウトした商品を在庫数 0 として書き込んでいる（L38）
- **理由**: 欠測を「在庫 0」という実在する値に置き換えています。WMS が一時的に遅いだけで、在庫がある商品が売り切れと表示され、販売機会を逃します。前回取り込んだ正しい値も 0 で上書きされます。また、この商品が失敗として数えられないため、問題が起きても気づけません。「ページ表示を壊さないため」という目的は、前回値を残すだけで達成できます。
- **代案**: タイムアウトした商品は書き込みをスキップして前回値を残し、`SyncResult` の失敗件数に数えます。必要なら「最終更新時刻」を一緒に保持し、古すぎる値の表示方法は `StockApi` 側で決めます。

### 2. 書き込み失敗を失敗件数に数えず、exit code 0 で終わる（L39、L29・L45 と関連）
- **理由**: L29 では `SyncResult` が失敗件数を返すと定義しているのに、L39 では書き込み失敗をそこに数えないとしており、矛盾しています。さらに監視の対象は exit code と同期件数の INFO ログだけです（L45）。そのため、全件の書き込みが失敗してもバッチは正常終了となり、障害を検知できません。
- **代案**: 書き込み失敗は失敗件数に数え、ERROR ログに商品ID と原因を出します。失敗件数または失敗率がしきい値を超えたら、非0で終了するかアラートを出します。L29 の失敗件数の定義も、L38・L39 と揃えて明記します。

### 3. DB と Redis に別々に書き込み、書き込み元も2つある（L34）
- **理由**:
  - `SyncBatch` は DB と Redis に別々に書き込むため、片方だけ成功すると両者の値がずれます。`StockApi` は Redis を優先して読むので、ずれた値がそのまま表示され続けます。
  - `ProductAdminService` も DB と Redis を直接削除するため、在庫データを書き換える処理が2か所にあります。たとえばバッチが WMS から取得した後に廃番による削除が走ると、その後のバッチの書き込みで廃番商品の行やキーが復活します。
  - Redis のキーに TTL（有効期限）を設定するかどうかが書かれておらず、ずれた値がいつまで残るか決まっていません。
- **代案**:
  - DB を正（信頼できる唯一の保存先）とし、Redis はキャッシュとして扱います。書き込みは DB だけに行い、その後 Redis のキーを削除するか、TTL 付きで再設定します。
  - 在庫データの更新・削除は `InventoryRepository` と `InventoryCache` を通す1つの経路にまとめ、`ProductAdminService` がデータを直接触らないようにします。
  - 廃番商品はバッチ側で書き込み対象から除外する（廃番フラグを確認する）か、DB の upsert に条件を付けて復活を防ぎます。

### 4. 監視から鮮度（最後に成功した時刻）が見えない（L45）
- **理由**: exit code だけを監視していると、バッチが起動しない、途中で止まる、異常に遅いといった状況では、データが古くなっていてもアラートが出ません。在庫数は古くなること自体が障害です。
- **代案**: 最後に成功した同期の時刻と処理件数をメトリクスとして記録し、たとえば「15分以上更新されていない」でアラートを出します。

## mid

### 5. 5分間隔で全商品を取得するが、処理時間と多重起動を検討していない（L15、L22）
- **理由**: 商品数が増えると1回の処理が5分を超え、次の実行と重なるおそれがあります。重なると同じ商品に古い値と新しい値が順不同で書き込まれます。WMS API のレート制限や、WMS 側にかかる負荷も書かれていません。
- **代案**: 想定する商品数と処理時間の見積もりを書き、多重起動を防ぐ方法（ジョブ基盤の設定かロック）を決めます。WMS が差分取得やページングに対応していれば、全件取得ではなくそちらを使います。

### 6. 許容する古さ（最大5分以上の遅れ）がサイト表示に与える影響を書いていない（L11、L16）
- **理由**: 「在庫ありと表示されたのに購入時に在庫切れ」という食い違いが起きる前提になりますが、それを受け入れるかどうかが書かれていません。表示の在庫数と購入時の引当（在庫の確保）の関係も不明です。
- **代案**: 許容する遅れ（例: 最大10分）を目標として明記します。購入時は引当ロジックで最終的に判定し、表示の在庫数は目安であることを書きます。

### 7. ロールバック手順が不十分（L44）
- **理由**: ジョブ定義を削除するだけでは、`StockApi`、`inventory` テーブル（新規作成ならマイグレーションが必要）、Redis のキー、サイト側の参照の切り替えが元に戻りません。ジョブを止めた後もデータは残り、古いまま配信され続けます。
- **代案**: デプロイの順番（テーブル → バッチ → `StockApi` → サイト側の参照切り替え）と、それぞれの戻し方を書きます。サイト側の参照はフラグなどで旧経路へ戻せるようにします。

### 8. 「遅い」原因と改善目標が書かれていない（L11）
- **理由**: 遅い原因が WMS の呼び出しだと特定されているのかが書かれていません。目標とするレイテンシもないため、この設計で目的を達成できたかを確認できません。
- **代案**: 現在の計測値（例: 応答時間の p95）と、目標値を書きます。

## low

### 9. 「サイト内部からのみ参照」をどう担保するか書かれていない（L30）
- **理由**: `/internal/` というパス名だけでは、外部からのアクセスを防げません。
- **代案**: ネットワークの制限（内部の経路のみ公開）や、サービス間の認証のどちらで担保するかを明記します。

### 10. バッチを失敗させる条件があいまい（L40）
- **理由**: 「5xx 連続」の回数や時間が定義されていません。そのため、どこまでを個別の失敗として扱い、どこからをバッチ全体の失敗とするかの境目が実装者によって変わります。
- **代案**: 連続回数、または失敗率のしきい値を数値で書きます。

### 11. キャッシュにも DB にもない商品で何を返すか書かれていない（L34）
- **理由**: 新しく登録された商品などで、404 を返すのか 0 を返すのかが決まっていません。
- **代案**: 返す値と、サイト側でどう表示するかを明記します。

### 12. 処理件数の出し方が不十分（L45）
- **理由**: 同期件数を INFO ログに出すだけでは、成功・スキップ・失敗の内訳が分からず、アラートの条件にも使えません。
- **代案**: 成功・失敗・スキップの件数をそれぞれ構造化ログまたはメトリクスとして出します（指摘2・4とまとめて対応できます）。

## 優先して直す箇所
指摘1〜3はデータが誤って表示されたり、データ同士がずれたりする問題で、指摘2と4はその問題が起きても気づけない問題です。この組み合わせが一番危険なので、L34・L38・L39・L45 を先に見直すことをおすすめします。
