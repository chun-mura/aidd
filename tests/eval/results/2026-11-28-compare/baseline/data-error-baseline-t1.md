# 在庫数同期バッチ設計書 レビュー結果

設計書の本文だけを根拠にしました。問題は13件で、high 4件、mid 6件、low 3件です。

## high

### 1. タイムアウトした商品の在庫を0として書き込んでいる
- **該当行**: L38
- **理由**: 在庫がある商品が「在庫切れ」と表示され、売り逃しにつながります。直前に取り込んだ正しい値も0で上書きされます。WMSの一部が遅くなっただけで多数の商品が0になるため、「ページ表示を壊さない」という目的と逆の結果になります。また、欠測した商品が `SyncResult` で成功・失敗のどちらに数えられるかも決まっていません。
- **代案**: タイムアウトした商品は書き込まず、前回の値を残します。その商品は失敗件数に数え、次回の同期で取り直します。古い値を出したくない場合は、`synced_at` などで鮮度を持たせ、表示側で「確認中」と出す案もあります。

### 2. 書き込みに失敗しても失敗件数に数えず、バッチは exit code 0 で終わる
- **該当行**: L39（L29、L45と関連）
- **理由**: 監視の対象は exit code と同期件数の INFO ログだけです（L45）。そのため、全商品の書き込みに失敗しても正常終了と区別がつきません。L29 で「失敗件数を返す」としていることとも矛盾します。
- **代案**: 書き込み失敗を `SyncResult` の失敗件数に数えます。失敗の割合が閾値（例: 5%）を超えたら exit code を0以外にし、失敗件数をメトリクスとして監視・アラートに載せます。

### 3. DB と Redis に別々に書き込み、どちらかだけ成功した場合の扱いがない
- **該当行**: L34
- **理由**: DB が成功して Redis が失敗すると、`StockApi` は Redis を先に読むので古い値を返し続けます。逆の順で失敗した場合は、DB と Redis で値が食い違います。Redis の TTL も決まっていないため、食い違いが自然に解消される保証がありません。
- **代案**: DB を唯一の正とし、Redis はキャッシュに徹します。書き込みは「DB を更新してから Redis のキーを削除する（または上書きする）」順に統一し、TTL（例: 同期間隔の2〜3倍）を必ず設定します。

### 4. 廃番処理と同期バッチが互いに競合し、削除した在庫が復活する
- **該当行**: L34
- **理由**: `ProductAdminService` が DB の行と Redis のキーを消した直後に、実行中の `SyncBatch` が同じ商品を書き戻すことがあります。WMS 側にまだその商品が残っていれば、廃番の商品に在庫が表示されます。在庫データを書き込む場所が2か所あり、整合性に責任を持つコンポーネントがありません。
- **代案**: 書き込みは `InventoryRepository` か新しい `InventoryService` の1か所にまとめ、`ProductAdminService` からはその経由でだけ操作します。`SyncBatch` は商品マスタで廃番になっている商品をスキップします。

## mid

### 5. 前回のバッチが5分以内に終わらなかったときの扱いがない
- **該当行**: L15、L22
- **理由**: 全商品の数、1回にかかる時間、WMS API のレート制限が書かれていません。前回の処理が終わらないうちに次が始まると、二重に書き込まれ、古い値で上書きされる恐れがあります。
- **代案**: 商品数と処理時間の見積もりを書き、同時に2本動かないよう排他します（ロックやジョブ基盤の同時実行禁止設定）。必要ならページングして並列度を決め、差分だけ取得することも検討します。

### 6. 在庫数が最大5分以上古くてもよいかが決まっていない
- **該当行**: L11、L15
- **理由**: 目的として「低レイテンシ」は書かれていますが、鮮度の要件がありません。在庫が残りわずかな商品では、古い在庫数を表示して注文を受け、後でトラブルになるリスクがあります。現状どのくらい遅く、何msを目標にするのかも数字がありません。
- **代案**: 現状のレイテンシ、目標値、許容できる鮮度（例: 最大10分遅れまで可）を明記します。在庫の引当は WMS 側で確定し、表示用の値は参考扱いと位置づけを書き分けます。

### 7. WMS が「全面的に落ちている」と判断する基準があいまい
- **該当行**: L40（L38と関連）
- **理由**: 「5xx連続」が何回なのか決まっていません。L38 の「個別にタイムアウトした」との境目もはっきりしないため、WMS が部分的に障害を起こしたときに大量の商品が0に書き換わる経路が残ります。
- **代案**: 判断基準を数字で決めます（例: 連続N回の5xx、またはタイムアウト率がX%超えたら中断）。中断したときは何も書き込まずに終了します。

### 8. 最後に同期が成功した時刻を監視していない
- **該当行**: L45
- **理由**: exit code だけを見ていると、ジョブが動かない・止まったまま、といった状態を見落とします。その間、データが古くなり続けていることに気づけません。
- **代案**: 最後に成功した時刻、処理件数、失敗件数をメトリクスとして出し、「最終成功から N 分経過」「失敗率が X% 超」でアラートを出します。

### 9. ロールバックの範囲が足りない
- **該当行**: L44
- **理由**: ジョブ定義を消しても、`StockApi`、サイト側の参照先、`ProductAdminService` の変更はそのまま残ります。データの更新だけが止まり、古い在庫数が表示され続けます。`inventory` テーブルの作成やマイグレーションの手順と、その戻し方も書かれていません。
- **代案**: サイト側の参照先をフィーチャーフラグで旧経路に戻せるようにします。DB マイグレーションの適用と戻しの手順、`ProductAdminService` の変更の戻し方も書き加えます。

### 10. 既存サービスを改修するのに、スコープと構成表に書かれていない
- **該当行**: L7、L13〜L25、L34
- **理由**: `ProductAdminService` を改修するのに、スコープにも構成表にも載っていません。影響範囲が見えず、レビューやテストの対象から漏れます。
- **代案**: スコープの「やる」と構成表に、既存サービスの改修として追記します。

## low

### 11. 内部エンドポイントへの外部アクセスをどう防ぐか書かれていない
- **該当行**: L30
- **理由**: 「サイト内部からのみ」をどう実現するか（ネットワークで制限するか、認証をかけるか）が不明です。
- **代案**: どの層で外部からのアクセスを遮断するか、認証方式は何かを明記します。

### 12. `StockApi` で存在しない商品や廃番の商品を指定したときの応答が決まっていない
- **該当行**: L30、L34
- **理由**: 404 を返すのか、在庫0を返すのかが決まっていません。Redis にも DB にも値がない商品が多数あると、毎回 DB へ問い合わせが届き、負荷が増える恐れもあります。
- **代案**: 応答の仕様を決めます。存在しない商品であることもキャッシュする（ネガティブキャッシュ）か検討します。

### 13. 要約形式にしている根拠が実態と合っていない
- **該当行**: L7
- **理由**: 「単一バッチ + キャッシュ層の変更」と書かれていますが、実際には新しい API、新しいテーブル、既存サービスの改修も含みます。
- **代案**: 規模の記述を実態に合わせて書き直すか、整合性の節を追加して詳しく書きます。

## 優先して直すべき点

まず #1〜#4 を直すのが先です。データが誤って0になる問題、失敗が監視から見えない問題、DB と Redis の食い違い、廃番の在庫が復活する問題で、どれも本番で誤った表示を出し、しかも気づけないものです。

#5〜#9 の多くは、「在庫データを書き込む場所を1か所にまとめ、鮮度と失敗を監視の対象にする」という方針を決めれば、まとめて解決します。

この指摘は観点を整理したたたき台です。設計を採用するかどうかの最終判断は、担当者とレビュアーで行ってください。
