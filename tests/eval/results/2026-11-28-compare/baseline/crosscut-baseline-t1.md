# 会員ポイント台帳サービス 設計書のレビュー結果

指摘は high 8件、mid 7件、low 9件です。根拠はご提示の本文だけです。

## high

### H1. 有効期限の決め方（D2）が、どの処理にも反映されていない
- **該当行**: 379（D2）、261、154、186、285、300
- **理由**: D2 では「確定するたびに、その会員の確定ポイント全体の期限が延びる」と決めています。しかし 261 行では、確定した付与1件の `expires_at` だけを設定しています。285 行の `ExpireJob` も付与ごとの `expires_at` で失効を判定します。このまま実装すると、規約の改定案（第12条）より早く失効します。規約違反のまま失効させると苦情や返還対応が発生し、目標「規約どおりに失効させる」（22行）も満たせません。さらに、次のことも決まっていません。
  - 手動調整の加算（154行）や移行（300行）が「獲得」として期限を延ばすのか
  - `next_expiry`（96行）や失効予定の通知（293行）を、期限の延長とどう整合させるのか
- **代案**:
  - 確定の流れに「同じ会員で `confirmed` の付与すべての `expires_at` を、確定日 + 365日に更新する」処理を加えます。
  - または、期限を会員単位の列（例: `point_balances.expires_at`）にまとめ、`ExpireJob` はその列で判定します。
  - どの付与の種類で期限を延ばすかは、法務と合意して決定事項に書きます。

### H2. 仮付与のポイントを利用に使えてしまう
- **該当行**: 269、270（51、101、311 と矛盾）
- **理由**: 269 行の残高チェックは `confirmed_balance + pending_balance`、270 行の引き当て対象は `status IN ('confirmed','pending')` です。用語定義（51行）と API の説明（101行）の「仮付与は利用できない」に反します。仮付与を利用した後に返品されると、311 行の「取消時に利用済みの分を考慮する必要はない」が成り立ちません。その結果、`remaining` を超える取消や残高のマイナスが起き、使われたポイントを回収できません。目標「回収漏れ0件」も崩れます。どちらの残高列から減らすのかも書かれていません。
- **代案**: 残高チェックは `confirmed_balance` だけ、引き当ては `status = 'confirmed' AND expires_at >= 当日` だけに直します。NULL や pending を扱う記述は削除します。

### H3. DB の書き込みに失敗しても 200 を返し、後から台帳に記録する
- **該当行**: 319
- **理由**: 残高を確認せず、台帳にも記録しないまま利用が成功したことになります。次の問題が起きます。
  - 後から非同期で記録するときに残高が足りなければ、ポイント分を値引きしたまま注文が確定してしまいます。
  - `redemption_requests` に保存されないので、同じキーで再送されると二重に利用されるおそれがあります。
  - 返す `redemption_id` が台帳に存在しないため、キャンセル時に返還できません。
  - 274 行の「2〜6 は1トランザクション」という保証と矛盾します。
- **代案**: 5xx（503 など）を返し、注文サービスはタイムアウトと同じ扱い（320行の「ポイント処理待ち」と、アウトボックスからの再送）にします。`redemption_retry` キューとその監視（351行）は削除します。

### H4. 冪等キーを24時間で消すが、再送は72時間続く
- **該当行**: 361 と 320
- **理由**: 注文サービスは、同じ `Idempotency-Key` で最大72時間再送します。24時間を過ぎて行が消えた後に再送が届くと、新しい要求として処理されて二重に利用されます。初回がタイムアウトしたが実際にはコミット済み、という場合に起きます。
- **代案**: 保持期間を「再送の上限72時間 + 余裕」（例: 7日）にし、両方の数字を相互に参照できるよう書きます。または、`point_redemptions` 側にも `idempotency_key` を一意制約付きで持たせ、永続的に重複を防ぎます。

### H5. CS が「残高編集」画面で `point_balances` を直接書き換える
- **該当行**: 367（246、63、70 と矛盾）
- **理由**: 246 行の「`point_balances` を書き換えるのは `PointLedgerService` だけ」に反します。台帳に記録が残らないので、増減の理由を説明できるという目的（13行、21行）が崩れます。さらに、翌日 03:00 に `BalanceReconcileJob` が台帳の値で上書きするため、修正自体が消えます。この画面の API と必要なロールも定義されていません。
- **代案**: この手順は削除し、残高の誤りも `POST /admin/v1/adjustments`（`CS_CORRECTION`）で直す、に統一します。

### H6. 旧列を同じリリースで削除するため、注文・会員サービスをロールバックできない
- **該当行**: 302、303、339、382（D5）
- **理由**:
  - 新サービスをデプロイする（303行の手順5）前に、手順4で `members.point_balance` を削除しています。
  - 339 行では「前バージョンのイメージを再デプロイする」とあります。しかし前バージョンは削除済みの列を読み書きするので、ロールバックすると注文確定もマイページも動かなくなります。
  - 339 行の「害はない」は `point_db` のことしか述べておらず、列の削除を見落としています。
  - 手順5の動作確認で不具合が見つかっても戻せません。
- **代案**: 次のどちらかにします。
  - 列はこのリリースでは残し、書き込み権限を外すかトリガで更新を禁止して二重管理を防ぎます。そのうえで、次のリリースで削除します。
  - 同じリリースで削除する場合は、「ロールバックできない」と明記し、前方修正だけで対応する運用にします。

### H7. 負の手動調整で、どの付与を減らすかが決まっていない
- **該当行**: 151〜154、197
- **理由**: 減算の調整でどの付与の `remaining` を減らすかが書かれていません。`point_balances` だけを減らすと、付与の `remaining` の合計と残高が食い違います。その付与は後で `ExpireJob` が失効させるので、同じポイントを二重に引くことになり、残高がマイナスになります。
- **代案**: 減算も利用と同じ引き当て（期限の早い順）で行い、引き当てた結果を記録します。例えば、`point_redemption_allocations` と同じ形の調整用の表を作ります。仮付与の誤りを訂正する手段も決めます。

### H8. 返品された注文で使われたポイントの扱いが決まっていない
- **該当行**: 66、165、166、278
- **理由**: 返還（`redeem_cancel`）が起きるのは、出荷前のキャンセル（`order.cancelled`）のときだけです。ポイントを使った注文が返品されたときに、ポイントを返すのか返金で清算するのかが書かれていません。`order.returned` には `redemption_id` も含まれていません。返品は本設計の中心の業務なので、決めておかないと CS 対応が手作業に戻ります。
- **代案**: 返品時に利用ポイントを返還するかどうかを決定事項に加えます。返還する場合は、`order.returned` に `redemption_id` を加え、返還の流れの対象にします。

## mid

### M1. 「確定後に返品イベントは来ない」という前提が、配信の遅延で崩れる
- **該当行**: 313、309、381（D4）
- **理由**: 14日目に受け付けた返品のイベントが、再配信（最大10回、指数バックオフ）やデッドレターキューで遅れると、その間に15日目の確定が走ります。そうなると取消ができず、確定したポイントが使われるおそれもあります。この場合の処理は ERROR ログを出して CS に任せるだけで、通知もないため、目標「回収漏れ0件」（23行）を満たせません。
- **代案**: 次の両方を行います。
  - 確定後の返品も `grant_cancel` で回収できるようにします（不足分は残高のマイナスとして持つ）。
  - `GrantConfirmJob` は、その注文にデッドレターキューの未処理分がないことを確認してから確定します。または、確定までの猶予を数日延ばします。

  ERROR ログには監視通知を付けます。

### M2. `confirm` 行の増減が0なので、台帳だけでは確定残高と仮残高を分けられない
- **該当行**: 248、262、197
- **理由**: `confirm` 行は増減0なので、台帳の行を足し合わせても `confirmed_balance` と `pending_balance` に分けられません。`BalanceReconcileJob` の「台帳から再計算」が成り立ちません。
- **代案**: 再計算の元を `point_grants`（状態ごとの `remaining`）にします。または、`confirm` 行に移した量を記録する列を加えます。

### M3. `BalanceReconcileJob` の上書きが、同時に走る更新と競合する
- **該当行**: 248
- **理由**: 集計してから上書きするまでの間に利用や付与がコミットされると、古い値で上書きしてしまいます。その結果、ジョブ自体が残高のずれを生みます。
- **代案**: 会員ごとに `point_balances` の行を `FOR UPDATE` でロックしてから、同じトランザクションで集計して比較します。自動で修正せず検知だけにすることも検討します。

### M4. タイムアウト後72時間で注文をキャンセルするとき、ポイントの返還経路がない
- **該当行**: 320、166
- **理由**: タイムアウトしても、実際には利用がコミットされている場合があります。注文サービスは `redemption_id` を受け取っていないので、`order.cancelled` で返還できません。
- **代案**: 次のどちらかにします。
  - キャンセルの前に、同じキーで最後の照会をして `redemption_id` を得ます。
  - `order_id` で返還できる経路を設けます。

  72時間も注文を保留することの業務上の影響（在庫の確保など）も確認します。

### M5. `item_amount` が API とイベントで別の意味になっている
- **該当行**: 117、164
- **理由**: 同じ項目名で、API（117行）では「送料を除く商品代金」、イベント（164行）では「送料・ポイント利用分を除く商品代金」です。実装時に取り違えると、付与ポイントを間違えます。
- **代案**: 項目名を分けます（例: `merchandise_amount` と `grant_base_amount`）。

### M6. 失効予定の通知が、ジョブの失敗や期限の延長で抜けたり誤ったりする
- **該当行**: 293、331、384（D7）
- **理由**:
  - 「ちょうど30日後」で判定するので、ジョブが1日止まるとその日の分は二度と送られません。
  - D2 の期限延長で、通知した後に失効日が変わることがあります。
  - 「通知は規約上の義務ではない」は、規約の改定案で確認できていません。
- **代案**: 判定を「30日以内で、まだ通知していない」にし、通知済みであることを記録します。通知が義務かどうかは法務に確認します。

### M7. `GrantConfirmJob` が遅れると、有効期限がずれる
- **該当行**: 261
- **理由**: `expires_at` を「確定日」から計算しているので、ジョブを再実行した日や遅延した日の分だけ期限が後ろにずれます。
- **代案**: `confirm_at + 365` を基準にします（D2 の修正と合わせて決めます）。

## low

### L1. 会員の存在や退会状態を、どこで判定するか書かれていない
- **該当行**: 103、314
- **理由**: `point-ledger` は会員の表を持っていないため、「会員が存在しない」「退会済み」を判定できません。
- **代案**: 会員サービスに問い合わせる、またはイベントに会員の状態を含める、のどちらにするかを明記します。

### L2. 冪等キーと要求の内容が結び付いていない
- **該当行**: 109
- **理由**: 同じキーで内容の違う要求が来ても、初回のレスポンスを返してしまいます。
- **代案**: 要求本文のハッシュを保存し、内容が違えば 422 を返します。

### L3. 409 のレスポンスを保存しない
- **該当行**: 269、272
- **理由**: 409 を返した後に同じキーで再送すると、結果が変わり得ます。
- **代案**: 409 も `redemption_requests` に保存するかどうかを明記します。

### L4. 残高チェックは通ったが、引き当てが足りない場合の動作が書かれていない
- **該当行**: 291
- **理由**: 291 行は「409 になる場合がある」と述べていますが、手順のどこで 409 を返すのかが手順に書かれていません。
- **代案**: 手順4に「引き当てた合計が足りなければロールバックして 409 を返す」を加えます。

### L5. `ON CONFLICT DO NOTHING` の後の処理を止める条件が書かれていない
- **該当行**: 255
- **理由**: INSERT が何もしなかった場合に、後続の台帳への追記と残高の加算を止める必要があります。その条件（影響行数が0なら中断）が書かれていません。
- **代案**: 影響行数が0のときは後続の処理をせずに ack する、と明記します。

### L6. 返還の経路が API とイベントの2つある
- **該当行**: 120〜126、278
- **理由**: キャンセル API（120〜126行）を誰がいつ呼ぶのかが書かれておらず、イベント経由の返還（278行）と経路が重なっています。
- **代案**: 呼び出し元を明記するか、使わない経路を削除します。

### L7. `delivered_at` を JST の日付に変換する規則がない
- **該当行**: 254、385（D8）
- **理由**: `delivered_at` を「配送完了日」に変換する規則が書かれていません。
- **代案**: 「`delivered_at` を JST に変換した日付」と明記します。

### L8. 管理画面の台帳 API にページングがない
- **該当行**: 158
- **理由**: 全行を返すため、10年保持（360行）で行が積み上がると、レスポンスが重くなります。
- **代案**: カーソル方式のページングを加えます。

### L9. 「`cs_member` 以上」の階層が定義されていない
- **該当行**: 74、372
- **理由**: ロールの上下関係が定義されていません。
- **代案**: ロールの一覧と、各画面で必要なロールを表にします。

H1（D2）と H8（返品時の利用ポイント）は、規約の解釈と業務方針に関わります。どう決めるかは法務・マーケティング・CS と合意してください。私の代案はたたき台です。
