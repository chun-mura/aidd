# 会員ポイント台帳サービス設計書のレビュー結果

本文だけを根拠にしています。high が7件、mid が9件、low が6件です。

## high

**H1. 有効期限の延長規則（D2）が、どこにも実装されていない**
- 該当行: 379, 261, 154, 300
- 理由: D2 では「付与が確定するたびに、その会員の確定ポイント全体の期限が延びる」と決めています。しかし確定の流れ（261行）は、その付与1件の `expires_at` を決めるだけです。他の付与の期限は延ばしていません。このままでは、毎月買っている会員でも古い付与が1年で失効し、改定後の規約に反します。目標（22行）も達成できません。
- 代案: 確定のトランザクションで、その会員の `status='confirmed'` の全付与の `expires_at` を「確定日＋1年」に UPDATE します。会員単位で期限を1つ持つ方式にしてもかまいません。あわせて、手動調整の加算（154行）と移行（300行）が「獲得」に当たり、期限を延ばすかどうかを明記してください。

**H2. 仮付与（pending）が利用に引き当てられている**
- 該当行: 269, 270（51, 101, 311 と矛盾）
- 理由: 用語の定義と API では「仮付与は利用できない」としています。ところが利用の流れは `confirmed_balance + pending_balance` で残高を判定し、`status IN ('confirmed','pending')` から引き当てます。この状態で仮付与を使った注文が返品されると、`grant_cancel` で回収されるのは残っている `remaining` 分だけです。使われたポイントは回収できません。そのうえ 311 行は「仮付与は利用できないため、利用済みの分を考慮する必要はない」としているので、回収漏れが仕組みとして起きます。
- 代案: 残高の判定は `confirmed_balance` だけで行い、引き当ての対象を `status='confirmed'` に限ります。

**H3. DB 書き込みに失敗しても 200 を返し、後から非同期で記録している**
- 該当行: 319
- 理由: 残高の確認、ロック、引き当てをせずに成功を返しています。そのため残高が足りなくても利用が通ってしまい、残高がマイナスになり得ます。`redemption_id` も返せません。冪等性レコードも残らないので、同じキーで再送されると初回と違うレスポンスになります。320行の「タイムアウト時に再送する」方針とも食い違っています。
- 代案: 503 を返します。注文サービスが既存のアウトボックスで同じ `Idempotency-Key` を使って再送する（320行の流れに乗せる）形にします。こうすれば `redemption_retry` キューと、それを見る監視（351行）は要らなくなります。

**H4. 冪等キーの保持期間（24時間）が再送期間（72時間）より短い**
- 該当行: 361（320 と矛盾）
- 理由: 実際にはコミット済みなのにタイムアウトした要求を、24時間を過ぎてから再送すると、キーがもう消えています。その結果、利用が二重に記録されます。D6 により `order_id` で重複を防ぐこともできません。
- 代案: 保持期間を再送の上限より十分長くします（例: 7日以上）。あわせて「再送期間 < 保持期間」を設計上の制約として書いておきます。

**H5. CS が `point_balances` を直接書き換える手順がある**
- 該当行: 367（246, 371, 248 と矛盾）
- 理由: 246 行の「`point_balances` は `PointLedgerService` だけが書き換える」原則に反します。台帳にも記録が残りません。さらに、翌日 03:00 の `BalanceReconcileJob` が台帳の値で上書きするので、修正が消えます。「残高編集」画面はスコープ（37行）にも API にも出てきません。
- 代案: 手順を削除し、残高の訂正も「手動調整」（`CS_CORRECTION`）で行うよう統一します。

**H6. 移行で旧列を先に削除するため、ロールバックできない**
- 該当行: 302, 303, 339, D5（382）
- 理由: 新サービスのデプロイ（手順5）より前に `members.point_balance` を削除しています。デプロイや動作確認で失敗すると、339行の「前イメージを再デプロイ」が成り立ちません。前バージョンは削除した列を参照するからです。仮に列が残っていても、リリース後に台帳へ記録された利用・付与は旧列に反映されないので、残高が食い違います。
- 代案: 旧列の削除は、安定稼働を確認した後の別リリースに分けます。D5 が心配する「二重管理」は、旧列への書き込み権限を外す・列名を変えるといった方法で防げます。ロールバック手順にも「どの時点まで戻せるか」を書いてください。

**H7. 移行の前後をまたぐ注文の扱いが決まっていない**
- 該当行: 295–303, 311–313, 166
- 理由:
  - 移行前に配送が完了し、旧方式でポイントを加算済みの注文が、移行後に返品されるケースがあります。この注文には `point_grants` の行がないので、311〜313 行のどの分岐にも当たりません。結果として回収漏れになり、目標（23行）に反します。
  - 移行前に旧列からポイントを減算した注文が、移行後にキャンセルされるケースもあります。`redemption_id` は null なので、ポイントが会員に返りません。
- 代案: 移行時点で返品受付期間内にある注文と、未出荷の注文を洗い出します。移行の際に、それぞれ仮付与・利用のレコードとして作り直すか、移行後14日間だけ手作業の手順を残すかを決めて明記してください。

## mid

**M1. 返品された注文で使われたポイントの扱いが書かれていない**
- 該当行: 165, 311
- 理由: `order.returned` には `redemption_id` がなく、返品時の流れは付与の取消だけです。返品時に利用分を返すかどうかが決まっておらず、手作業が残ります。
- 代案: 返品ポリシーとして返還の有無を決めます。返還する場合は、イベントに `redemption_id` を含めて返還の流れに乗せます。

**M2. 確定までの余裕が1日しかなく、イベントの遅延に弱い**
- 該当行: 313, D4（381）
- 理由: 14日目の深夜に受け付けた返品が、再配信のバックオフ（最大10回）や DLQ 経由で遅れて届くことがあります。その場合、01:00 の確定後に到着し、ERROR ログと手作業での対応になります。「このイベントは発生しない」という前提は成り立ちません。
- 代案: 確定日を十分後ろにずらす（例: 配送完了日＋21日）か、確定済みの付与を回収する処理（`grant_cancel` で残量から減らし、足りない分は負の調整）を用意します。

**M3. 返還処理が同時に動くと、二重に返還される**
- 該当行: 278–281, 122
- 理由: `cancel` API と `order.cancelled` イベントが同時に処理されると、どちらも `status` を `active` と判定して両方とも返還します。
- 代案: `UPDATE point_redemptions SET status='cancelled' WHERE redemption_id=? AND status='active'` の更新件数で判定するか、`FOR UPDATE` でロックします。

**M4. `BalanceReconcileJob` は台帳だけでは内訳を再計算できず、更新とも競合する**
- 該当行: 248
- 理由: `confirm` 行の増減は0なので、台帳を合計しても総額しか出ません。`confirmed` と `pending` の内訳は分かりません。また、ジョブの実行中に進む利用とロックせずに比べて上書きすると、正しい値を誤った値で上書きするおそれがあります。
- 代案: 総額は台帳の合計、内訳は `point_grants.remaining` の状態別の合計として、両者を突き合わせます。会員の行をロックしてから比較します。自動で上書きするのはやめ、検知と通知だけにすることも検討してください（不具合の痕跡を消さないため）。

**M5. 72時間の再送後に注文をキャンセルするとき、利用済みのポイントを返していない**
- 該当行: 320
- 理由: サーバ側ではコミット済みだったのに、再送がすべて失敗に見えた場合、注文はキャンセルされてもポイントは減ったままになります。
- 代案: キャンセルする前に、同じキーで記録があるかを照会し、あれば返還 API を呼ぶ手順を加えます。

**M6. 負の手動調整で、どの付与から差し引くかが決まっていない**
- 該当行: 151–154
- 理由: 減らした分をどの付与から引くかが書かれていないため、`point_grants.remaining` と残高がずれます。M4 のジョブでも整合が取れなくなります。
- 代案: 利用と同じく、期限の早い順に引き当て、内訳を記録すると明記します。

**M7. `exhausted` の付与が期限切れの後に返還されたケースが漏れている**
- 該当行: 239, 325
- 理由: 325 行が扱っているのは `expired` の付与だけです。期限切れで `exhausted` の付与に返還されると、`confirmed` に戻り、翌日 00:30 の失効までの間だけ残高に含まれます。また 242 行で `expired` を終端としているのに、325 行では `expired` の付与の `remaining` を戻しており、定義と食い違っています。
- 代案: 返還時に、戻し先の `expires_at` が当日より前なら状態に関係なく即時に失効させる、と統一します。

**M8. 失効予定の通知が、1日失敗すると二度と送られない**
- 該当行: 293, 331
- 理由: 抽出条件が「ちょうど30日後」なので、ジョブが失敗した日の対象者には二度と通知されません。また、通知の後に D2 で期限が延びると、通知の内容と実際が食い違います。
- 代案: 「30日以内で未通知のもの」を対象にし、通知済みのフラグを持たせます。

**M9. 返品・キャンセルされた注文で、付与やイベントが見つからないときの扱いがない**
- 該当行: 253, 311–313, 326
- 理由: 付与が0ポイントで作られなかった注文に `order.returned` が届いた場合の分岐がありません。例外として扱われると DLQ に入ってオンコールが呼ばれます。
- 代案: 「付与なし ⇒ INFO ログを出して ack」を明記します。

## low

**L1. 「1年」を「＋365日」として計算している**
- 該当行: 261, 300
- 理由: 2028年はうるう年なので、規約上の「1年」より1日早く失効します。
- 代案: 暦の上で1年を加算する方式に揃えます。

**L2. 付与ポイントの計算式が浮動小数点を前提にしているように読める**
- 該当行: 253
- 理由: `floor(item_amount × 0.01)` は浮動小数点の誤差が出るおそれがあります。
- 代案: 整数除算 `item_amount / 100` と明記します。

**L3. 監視と運用手順が食い違っている**
- 該当行: 332, 350, 356
- 理由: `BalanceReconcileJob` は「再実行しない」方針なのに、「最終成功時刻が26時間以上前」でオンコールを呼びます。呼ばれても取れる対応がありません。
- 代案: このジョブの通知先を運用チャンネルにするか、再実行してよいことにします。

**L4. 有効期限が、確定予定日ではなくジョブの実行日を起点にしている**
- 該当行: 261
- 理由: ジョブが遅れて再実行されると、期限がずれます。
- 代案: 起点を `confirm_at` にします。

**L5. 会員の存在・退会の判定方法が書かれていない**
- 該当行: 103, 314
- 理由: 会員サービスに問い合わせるのか、データを複製して持つのかが不明です。
- 代案: どちらの方式にするかと、問い合わせ先が障害のときの挙動を明記します。

**L6. 台帳の `note` に個人情報が入るおそれがある**
- 該当行: 148, 204, 360
- 理由: `note` は自由記述で、10年間保持されます。
- 代案: 個人情報を書かないという入力ルールを決め、画面にも注意書きを出します。

H1〜H7 は、どれも目標（失効・回収漏れ0）や整合性に直接関わります。実装に入る前に設計書へ反映することをお勧めします。
