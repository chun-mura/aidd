# 設計書レビュー結果（週次利用レポート自動生成機能）

指示どおり、ファイルを読まず、ツールも使わず、提示された本文だけを根拠にしています。深刻度の高い順に並べています。

## high

### 1. 誰がデータを取得するのかが節ごとに矛盾している（22行目と34行目）
- **理由**: 22行目では `ReportManager` が「収集クエリ発行」と「SMTP経由のメール送信」を担当するとしています。一方、34〜36行目では、呼び出し側が SELECT した `raw_rows` と接続済みの `smtp_client` を受け取る形になっています。このままでは、クエリと SMTP 接続を誰が持つのか実装者が決められません。
- **代案**: どちらかに統一してください。推奨は、呼び出し側が渡すのを「集計期間」だけにし、DB 接続・テンプレート・メール送信は `ReportManager` の生成時に注入する形です（2. の代案を参照）。

### 2. インターフェースが内部の実装をそのまま呼び出し側に出している（33〜37行目）
- **理由**:
  - 呼び出し側は2つ（スケジューラと手動CLI）あります。それぞれが SELECT 文、`jinja2.Environment` の構築、SMTP の接続を重複して書くことになります。
  - `list[dict]` には型の保証がないため、23行目の `models/usage_event.py` のスキーマが活かされません。
  - 戻り値が `None` なので、57行目の「送信件数を INFO ログに出す」に必要な情報を呼び出し側が受け取れません。
  - テンプレートエンジンや SMTP ライブラリを差し替えると、呼び出し側まで直す必要が出ます。
- **代案**: 例えば `generate(period: ReportPeriod) -> ReportResult` のようにします。`ReportResult` には集計件数・宛先数・送信成否を持たせます。依存するもの（リポジトリ、レンダラ、メーラ）はコンストラクタで受け取ります。

## mid

### 3. `ReportManager` に責務を集めすぎている（22行目、26行目）
- **理由**: 取得・集計・整形・送信・スケジュール管理という、変わる理由がそれぞれ違う5つの責務が1つのクラスに入っています。単体テストのたびに DB と SMTP の両方が必要になります。26行目の「1ファイルで追える」は、責務を分けない理由としては弱いです。
- **代案**: `UsageAggregator`（取得・集計）、`ReportRenderer`（HTML 整形）、`ReportMailer`（送信）に分けます。`ReportManager` はこれらを順に呼ぶだけの薄い役にします。全体像は、データフロー節に呼び出し順を書けば追えます。

### 4. スケジュール管理を2か所で持っている（15行目、22行目、24行目、56行目）
- **理由**: 56行目では既存のバッチ基盤の cron で起動するとしています。それなのに、`ReportManager` が「cron設定の読み込みと次回実行時刻の管理」を持ち、`report.yaml` にも送信スケジュールがあります。どちらが正しい設定なのかが曖昧で、2か所の設定がずれる原因になります。
- **代案**: スケジュールは cron のジョブ定義だけで持ちます。`ReportManager` と `report.yaml` からスケジュールの責務を外し、`report.yaml` は宛先リストだけにします。

### 5. 再送したときに二重送信になるおそれがある（49行目）
- **理由**:
  - 宛先が複数あると、一部の宛先にだけ届いた後に失敗し、リトライで届いた人に重複して送る可能性があります。
  - 失敗した後に手動CLIで再実行したときの扱いが書かれていません。
  - リトライの間隔、および恒久的なエラー（5xx）と一時的なエラー（4xx・接続断）を分けて扱うかどうかも決まっていません。
- **代案**: 次の3点を明記してください。
  - 1通で全宛先に送るのか、宛先ごとに送るのか
  - リトライは一時的なエラーのときだけ行い、指数バックオフをかけること
  - 同じ週のレポートを再送するときの方針（送信済みの記録を残して判定する、または CLI に `--force` を付けたときだけ再送する、など）

### 6. 集計期間の定義がない（15行目、34行目）
- **理由**: 「週次」の境界（何曜日の何時から始まるか、タイムゾーン）や、遅れて届いたイベントの扱いが書かれていません。手動で集計していたときと数値が合わない原因になります。
- **代案**: 例えば「JST の月曜0:00から日曜23:59:59まで、実行は月曜の朝」のように期間を明記し、インターフェースの引数として受け取るようにします。

### 7. イベントが0件のときなど、異常なデータの扱いが決まっていない（48〜52行目、57行目）
- **理由**: エラーになるのはクエリ・送信・整形の失敗だけです。収集側が止まって0件になっていても、「0件のレポート」が正常に送られてしまいます。52行目で避けたいとしている silent failure にあたります。
- **代案**: 0件のとき、または前の週から極端に減ったときに、WARN ログを出すか失敗扱いにするかを決めて記載します。

### 8. SMTP の認証情報をどう扱うかが書かれていない（36行目、56行目）
- **理由**: 「接続済みSMTPクライアント」を誰がどの認証情報で作るのか書かれていません。`report.yaml` に直接書かれてしまうおそれがあります。
- **代案**: 認証情報は既存のバッチ基盤のシークレット管理から読み込み、設定ファイルには含めないと明記します。

## low

### 9. 「未定」の記載が解決済みのまま残っている（40行目、61行目）
- **理由**: 61行目でキャッシュはしないと決まっていますが、40行目に「未定」の記載が残っています。読む人が混乱します。
- **代案**: 40行目を削除するか、「キャッシュはしない（決定事項 2026-07-01 を参照）」に書き換えます。

### 10. 「再集計すれば再取得できる」は成り立たない場合がある（44行目）
- **理由**: `usage_events` が後から追記されたり、保持期限で削除されたりすると、送ったときと同じ内容は再現できません。「先週のメールと数値が違う」という問い合わせが来たときに調べられません。
- **代案**: 送信した集計結果（数値のスナップショット）か HTML を一定期間残します。残さない場合は、再現できないことを受け入れると明記します。

### 11. 失敗の通知経路が2つ書かれている（48行目、57行目）
- **理由**: 「cron の失敗通知」と「exit code を既存のバッチ監視」が同じものを指すのか、別々の経路なのかがわかりません。
- **代案**: 既存のバッチ監視に一本化すると書きます。

### 12. 運用に移るときの検証手段が書かれていない（56行目）
- **理由**: 手動CLIで、送信せずに結果だけ確認する dry-run やテスト宛先への送信ができるかどうか書かれていません。手動集計の値と照合する移行期間も決まっていません。
- **代案**: CLI に `--dry-run` と `--to <テスト宛先>` を用意します。最初の1〜2週は手動集計と並行して数値を照合します。

## 総評
最も重要なのは 1〜4 です。データを誰が取得するかの矛盾、インターフェースの形、責務の集中、スケジュールの二重管理は、いずれも構成とインターフェースに関わります。実装の前に直すことをおすすめします。5〜8 は運用の品質に関わる詰め残しで、エラー処理と運用の節に追記すれば済みます。

なお、この指摘は観点を整理したたたき台です。設計を採用するかの最終判断は、担当者のレビューで行ってください。
