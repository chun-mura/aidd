# 設計書レビュー：週次利用レポート自動生成機能

一番大きな問題は、`ReportManager` の責務（22行目）とインターフェース（33〜37行目）が食い違っていることです。この食い違いが、エラー処理やスケジュール管理の曖昧さにもつながっています。

## 指摘一覧

### 1. [high] 責務とインターフェースが食い違っている（22行目 / 34〜36行目）
- **理由:**
  - 22行目では、`ReportManager` が「収集クエリ発行」と「SMTP経由のメール送信」を担当すると書かれています。
  - 一方、34行目では呼び出し側が SELECT して `raw_rows` を渡します。36行目では呼び出し側が接続済みの SMTP クライアントを渡します。
  - 「誰がクエリを発行し、誰が SMTP 接続を持つのか」が設計書の中で決まっていません。このため、48行目の「集計クエリ失敗」を誰が扱うのかも決まりません。
- **代案:** どちらの方針にするか決めて、もう一方の記述を直します。指摘2・3の理由から、`ReportManager` 側がクエリ発行と送信を持ち、呼び出し側には渡さない形を推奨します。

### 2. [high] スケジュール管理の持ち主が二重になっている（15行目 / 22行目 / 24行目 / 56行目）
- **理由:**
  - 22行目では、`ReportManager` が「cron設定の読み込みと次回実行時刻の管理」を担当します。24行目では `report.yaml` が送信スケジュールを持ちます。
  - しかし56行目では、既存バッチ基盤の cron ジョブとして起動されます。
  - 実行タイミングの正本が2か所（cron 定義と yaml）にあり、両者がずれたときにどちらが勝つのか書かれていません。
- **代案:** 起動タイミングは既存バッチ基盤の cron 定義だけを正本にします。`ReportManager` からスケジュール管理の責務を外し、yaml から送信スケジュールの項目を削除します。スコープ（15行目）の「送信スケジュール管理」も外します。

### 3. [mid] インターフェースが内部の実装を呼び出し側に漏らしている（33〜37行目）
- **理由:**
  - 呼び出し側（スケジューラと CLI の両方）が、`usage_events` の生レコード形式、`jinja2.Environment` の構築方法、SMTP 接続の手順をすべて知っている必要があります。
  - テーブル定義・テンプレート・送信手段のどれを変えても、呼び出し側の2か所に修正が広がります。
  - `list[dict]` では型の保証がなく、23行目の `models/usage_event.py` のスキーマが使われていません。
- **代案:** `generate_and_send(week: ISOWeek) -> SendResult` のように、「どの週か」だけを受け取る口にします。DB アクセス・テンプレート・SMTP は、内部で（またはコンストラクタで依存として注入して）扱います。

### 4. [mid] `ReportManager` に責務が集まりすぎている（22行目 / 26行目）
- **理由:**
  - 収集・集計・整形・送信・スケジュールという、変わる理由がそれぞれ違う5つの責務を1クラスに持たせています。
  - 「1ファイルで追える」という利点（26行目）よりも、集計ロジックを単体テストしにくいことや、変更の影響が広がることの方が大きいです。
- **代案:** 集計（純粋関数：入力がイベント列、出力が集計結果）、描画（入力が集計結果、出力が HTML）、送信の3つに分けます。全体の流れは、薄い `ReportJob` が上から順に呼ぶ形で追えるようにします。全体像の見通しは、この呼び出し順で保てます。

### 5. [mid] 集計期間の定義がない（33〜37行目 / 44行目）
- **理由:**
  - インターフェースに「対象週」の引数がありません。次の点が決まっていません。
    - 週の境界（何曜日に始まるか、タイムゾーン）
    - 遅れて届いたイベントの扱い
    - 過去の週を再送する方法
  - 44行目の「再取得は再集計で行う」は、期間を指定する手段がないと実行できません。
- **代案:** 対象週を引数にとり、週の境界とタイムゾーンを設計書に明記します。CLI からも過去の週を指定できるようにします。

### 6. [mid] SMTP リトライで二重送信が起こりうる（36行目 / 49行目）
- **理由:**
  - 宛先が複数あるので、一部の宛先に送れた後に失敗すると、リトライで同じメールが重複して届きます。
  - また、接続済みのクライアントを外から受け取る形なので、接続が切れたときに `ReportManager` が再接続できません。そのため、リトライが実質的に効かない可能性があります。
- **代案:** 次のどちらかの方式に決めて、設計書に明記します。
  - 宛先ごとに送信し、成功した宛先を記録して、失敗した宛先だけをリトライする。
  - 全宛先を1通の宛先リストで一度だけ送信する。

  あわせて、SMTP 接続は `ReportManager` 側（またはファクトリ経由）で作り、リトライのたびに張り直せるようにします。

### 7. [mid] 手動実行の CLI と cron の実行が重複した場合の扱いがない（30行目 / 56行目）
- **理由:** 同じ週について cron と手動 CLI の両方が動くと、関係者に二重に送信されます。これを防ぐ仕組みが書かれていません。
- **代案:** 次のどちらかを明記します。
  - 対象週ごとの送信済み記録を持ち、記録がある週は送らない。手動実行は `--force` を付けたときだけ再送する。
  - 「手動実行は再送用途であり、重複送信を許容する」と運用ルールとして書く。

### 8. [low] 未定の記載が本文に残っている（40行目 / 61行目）
- **理由:** 61行目で「解決済み」と決定していますが、40行目の本文は「未定」のままです。本文だけを読んだ人には、今どうなっているのかが分かりません。
- **代案:** 40行目を「集計結果はキャッシュしない（決定事項 2026-07-01 参照）」に書き換えます。

### 9. [low] 正常だが空の結果や異常値になる場合の扱いがない（44〜52行目）
- **理由:** その週のイベントが0件のとき、送るのか送らないのかが書かれていません。集計基盤側の障害で0件になった場合も、「失敗」ではなく「0件のレポート」として送られてしまい、52行目の「silent failure を作らない」に反する可能性があります。
- **代案:** 0件のときの扱いを決めます（例：送信はするが警告ログを出す、または前週比で急減したら失敗扱いにする）。

### 10. [low] 宛先リストの管理方法が書かれていない（24行目）
- **理由:**
  - 宛先は社員のメールアドレスなので、リポジトリの yaml に直接書くと個人情報がコード履歴に残ります。
  - 宛先を変更するときの手順（誰が承認するか、反映にデプロイが必要か）も書かれていません。
- **代案:** 配布リスト（メーリングリスト）のアドレス1件だけを設定に持ち、メンバーの管理はメーリングリスト側で行います。

### 11. [low] テスト方針がない（文書全体）
- **理由:** 集計ロジックの正しさと、二重送信を防ぐ仕組みをどう確認するかが書かれていません。
- **代案:** 指摘4のように分割したうえで、テスト方針を短く追記します。
  - 集計関数は、固定のイベント列を入力にした単体テストで確認する。
  - 送信部分は、SMTP をスタブにしたテストで確認する。

---

**優先して直すべき点:** 指摘1・2・3を先に解決してください。この3つで「誰が何を持つか」が決まれば、指摘5〜7（期間指定・リトライ・重複実行）は書くべき場所が自然に決まります。
