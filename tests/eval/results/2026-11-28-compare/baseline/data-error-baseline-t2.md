# 在庫数同期バッチ 設計書 レビュー結果

設計書の本文だけを根拠にしています。全部で11件、内訳は high 3件、mid 5件、low 3件です。

---

## high

### 1. タイムアウトした商品を在庫数0として書き込んでいる
- **該当行**: 38
- **理由**:
  - 「値が取れなかった」と「在庫が0」は別の事実ですが、この設計では同じ値になります。正しい直前値が0で上書きされ、在庫があるのに「在庫切れ」と表示されます。売上を直接失います。
  - WMS が遅くなると、多数の商品が一斉に在庫切れ表示になります。
  - 「ページ表示を壊さない」という目的に対して、表示内容が誤るという別の壊れ方を生んでいます。
  - 欠測も失敗件数に入らないため、監視からも見えません。
- **代案**:
  - タイムアウトした商品は書き込まず、直前値を保持する。
  - `last_synced_at` を持たせ、一定時間更新されない値は表示側で「在庫確認中」などに切り替える。
  - タイムアウトは `SyncResult` の失敗件数に数える。

### 2. 書き込み失敗を失敗件数に数えず、exit 0 で正常終了する
- **該当行**: 39(29、45 と矛盾)
- **理由**:
  - 29行目では `SyncResult` が失敗件数を返すと定義しているのに、書き込み失敗をそこに数えません。失敗件数が何を数えるのか、定義が成り立っていません。
  - 45行目の監視は exit code しか見ないため、DB や Redis への書き込みが全件失敗しても正常として扱われます。気づかないまま古い在庫が表示され続けます。
- **代案**:
  - 書き込み失敗は失敗件数に数え、商品IDと例外をログに出す(WARN 以上)。
  - 失敗率または失敗件数にしきい値を設け、超えたら exit code を非0にするか、アラートを出す。

### 3. DB と Redis を複数のコンポーネントがそれぞれ直接書いており、整合性の保証がない
- **該当行**: 34(22〜24)
- **理由**:
  - **部分失敗による乖離**: `SyncBatch` は DB と Redis に別々に書き込みます。片方だけ失敗すると両者の値がずれ、どちらが正しいのか決まりません。39行目の「スキップして続行」と組み合わさると、ずれは放置されます。
  - **廃番との競合**: `ProductAdminService` が廃番商品の行とキーを削除した後でも、実行中の `SyncBatch` が取得済みのデータを書き戻すことがあります。その結果、廃番商品の在庫が復活します。
  - **責務の分散**: キャッシュを書き換える主体が2つあり、どちらを正とするか(Single Source of Truth)が書かれていません。
- **代案**:
  - DB を正とし、Redis はキャッシュアサイド(読み込み時にミスしたら DB から補充する方式)にする。書き込みは DB 更新とキー削除のみとし、TTL を設定する。
  - DB と Redis への操作は、在庫サービスなど1つのコンポーネントに集約する。`ProductAdminService` はそのサービスを呼ぶ形にする。
  - `SyncBatch` は書き込み時に廃番フラグを確認するか、DB の条件付き更新で廃番商品を復活させないようにする。

## mid

### 4. 監視が exit code と INFO ログだけで、部分失敗と鮮度の劣化を検知できない
- **該当行**: 45
- **理由**: 指摘1・2の結果、部分失敗では exit code が常に0になります。また、バッチが起動しない・遅延するといった事態(5分間隔が守られない状態)も検知できません。
- **代案**:
  - 処理件数・失敗件数・欠測件数をメトリクスとして出し、それぞれアラートを設定する。
  - 最終成功時刻をメトリクスにし、例えば15分以上更新されなければアラートを出す。

### 5. 5分ごとに全商品を取得する前提で、実行時間・重複起動・API制限が検討されていない
- **該当行**: 15、22
- **理由**:
  - 商品数が増えて処理が5分を超えると、前回の実行が終わる前に次が起動し、2つの実行が並走します。古い取得結果が新しい値を上書きする可能性があります。
  - WMS API のレート制限、ページング、商品件数の想定が書かれていません。
- **代案**:
  - 重複起動を防ぐ排他制御(分散ロックなど)を入れる。
  - 想定件数と所要時間の見積もりを記載する。
  - WMS が差分取得(更新日時指定など)に対応しているなら、それを使う。

### 6. ロールバック手順が不十分
- **該当行**: 44
- **理由**:
  - ジョブ定義を削除しても、DB と Redis に残った値を `StockApi` が返し続けます。古い在庫がそのまま表示されます。
  - `inventory` テーブルの作成やマイグレーション、初回の全件投入、サイト側の参照先切り替えの手順が書かれていません。
- **代案**: 次の手順を明記する。
  - サイト側の参照を元の経路に戻す方法(フィーチャーフラグなど)
  - キャッシュの破棄
  - 初回投入の手順
  - スキーマのロールバック方針

### 7. 「全面的に落ちている」の判定基準が曖昧で、38行目との境界が決まらない
- **該当行**: 40(38)
- **理由**: 「5xx連続」が何回なのかが決まっていません。そのため、どこまでが個別タイムアウト(在庫0として扱う)で、どこからが全面障害(バッチを失敗させる)なのか判断できません。部分的な障害では、前者の扱いで大量の在庫0が書き込まれる恐れがあります。
- **代案**: 連続失敗の回数や失敗率のしきい値を数値で定義する。超えた時点で書き込まずに中断する。

### 8. キャッシュの TTL と、キャッシュミス時の補充方法が書かれていない
- **該当行**: 34
- **理由**: TTL がないと、指摘3の乖離や廃番キーの残骸が永続します。また、キャッシュミス時に DB から読んだ値を Redis に書き戻すのかどうかも分かりません。
- **代案**: TTL(例: 同期間隔の数倍)と、ミス時の補充の有無を明記する。

## low

### 9. `StockApi` の仕様と、アクセス制限の実現方法が書かれていない
- **該当行**: 30
- **理由**:
  - 存在しない商品や廃番商品を問い合わせたときの応答(404 か 0 か)が決まっていません。
  - 鮮度情報を返すかどうかも決まっていません。
  - 「サイト内部からのみ」をネットワーク制御で実現するのか、認証で実現するのかが書かれていません。
- **代案**: レスポンス形式(在庫数、`last_synced_at`)、エラー時の応答、アクセス制御の方式を記載する。

### 10. 目的に対する目標値と、許容する鮮度が書かれていない
- **該当行**: 11、16
- **理由**:
  - 「低レイテンシ」の目標値が数値で書かれていないため、達成したかどうか判断できません。
  - 表示される在庫は最大で5分以上古くなります。表示上は在庫ありでも、注文時には欠品していることがあり得ます。注文時の最終確認がどこで行われるのか(既存の引当処理で担保されるのか)が書かれていません。
- **代案**: レイテンシの目標(p95 など)と許容する鮮度を数値で記載する。注文時の確認は既存の引当処理で担保される、という前提を明記する。

### 11. 既存の `ProductAdminService` を変更するのに、構成表とスコープに載っていない
- **該当行**: 7、13〜25、34
- **理由**: 既存サービスの改修は影響範囲に含まれるはずですが、表にもスコープにもありません。「単一バッチ+キャッシュ層の変更」とする7行目の要約形式の前提と食い違います。
- **代案**: 構成表とスコープに `ProductAdminService` の変更を追加し、影響範囲を明記する。
