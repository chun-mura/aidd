# 週次利用レポート自動生成機能 設計書のレビュー結果

指摘は14件です（high 3件、mid 8件、low 3件）。

## high

### 1. `ReportManager` が担当する処理が多すぎる（L22, L26）
- **理由:** 1つのクラスが、収集クエリ、集計、HTML整形、SMTP送信、スケジュール管理の5つを受け持っています。L26 は「1ファイルで追える」ことを利点に挙げています。しかしこの構成だと、集計ロジックだけをテストすることも、送信先を Slack などに差し替えることもできません。テンプレートを変えるだけでも送信処理を含むクラスに手を入れることになります。
- **代案:** 次の4つに分けます。
  - `UsageAggregator`（集計結果を返す純粋な処理）
  - `ReportRenderer`（集計結果から HTML を作る）
  - `ReportSender`（送信）
  - これらを順に呼ぶ薄い `ReportJob`
  
  処理全体の流れは `ReportJob` を読めば追えるので、L26 の狙いも保てます。

### 2. 収集クエリを誰が発行するかが節によって食い違っている（L22 と L34）
- **理由:** L22 では `ReportManager` がクエリを発行することになっています。一方 L34 では、呼び出し側が SELECT して `raw_rows` を渡すことになっています。どちらで実装するかが決まりません。
- **代案:** クエリの発行は集計側（指摘1の `UsageAggregator`）に置き、呼び出し側には集計期間だけを渡させます。L22 と L34 をこの形にそろえます。

### 3. インターフェースが内部の実装を呼び出し側に背負わせている（L33–37）
- **理由:** 呼び出し側（スケジューラと手動実行 CLI）の両方が、生レコードの SELECT、`jinja2.Environment` の構築、SMTP の接続を自分で行う必要があります。同じ処理が2か所に重複し、食い違いが起きやすくなります。テンプレートエンジンや送信手段を変えると、すべての呼び出し側に影響します。
- **代案:** `generate(period: ReportPeriod) -> ReportResult` のように、業務上の入力だけを受け取る形にします。Jinja 環境や SMTP クライアントは、構築時に依存性注入で渡します（テストではモックに差し替えられます）。

## mid

### 4. スケジュールの管理が2か所にある（L15, L22, L56）
- **理由:** L15 と L22 では「送信スケジュール管理」と「次回実行時刻の管理」を `ReportManager` が担います。しかし L56 では、実行を既存バッチ基盤の cron に任せています。実行時刻の決め手が2つになり、`config/report.yaml` と cron 定義がずれる恐れがあります。
- **代案:** スケジュールは cron 定義だけで決めます。`ReportManager` のスケジュール責務と、yaml のスケジュール項目は削除します。

### 5. SMTP リトライで重複送信や再接続不能が起きる（L36, L49）
- **理由:**
  - 宛先が複数あると、一部に送れた後で失敗し、リトライで同じメールが二重に届く可能性があります。
  - 接続済みのクライアントを外から受け取る設計なので、接続が切れた場合にリトライしても再接続できません。
  - リトライの間隔（バックオフ）も決まっていません。
- **代案:** 送信単位（1通で全員に送るのか、宛先ごとに送るのか）と、どこまで送れたかの扱いを明記します。接続は送信側が自分で作り直せるようにし、バックオフ間隔も書きます。

### 6. 同じ週のレポートを二重に送るのを防ぐ仕組みがない（L30, L56）
- **理由:** 手動実行 CLI と cron が両方あり、失敗後の再実行もありえます。そのため、同じ週のレポートを二重に送ることが起こりえます。
- **代案:** 対象週ごとの送信済み記録（実行記録テーブルなど）を持ち、送信済みならスキップします。強制的に再送するときだけ `--force` を付ける形にします。

### 7. 集計期間の定義がない（L15, L44）
- **理由:** 「週次」の始まりの曜日、タイムゾーン、境界の時刻（例: 月曜 00:00 JST）、遅れて届いたイベントの扱いが書かれていません。手動集計と数字が合わない原因になります。
- **代案:** 集計期間を `[開始, 終了)` の形とタイムゾーン付きで明記し、インターフェースの引数にします。

### 8. レポートの中身（何を集計するか）が書かれていない（L11, L15）
- **理由:** 指標、集計の単位、HTML の構成が書かれておらず、これまでの手動レポートと同じ内容になるか検証できません。
- **代案:** 出力する指標の一覧と、手動レポートとの対応表を追加し、受け入れ条件として「手動集計と一致すること」を書きます。

### 9. ジョブが動かなかったことを検知できない（L57）
- **理由:** exit code の監視では「失敗した」ことしか分かりません。cron が実行されなかった場合や、ジョブ定義が消えた場合は何も通知されません。
- **代案:** 送信に成功した時刻を記録し、それが一定期間（例: 8日）更新されなければアラートを出します（dead man's switch 方式）。

### 10. 古い「未定」の記載が本文に残っている（L40 と L61）
- **理由:** L61 の決定事項で解決済みですが、L40 は「未定」のままです。L40 だけ読んだ人は、キャッシュの実装が必要だと誤解します。
- **代案:** L40 を削除するか、「キャッシュは行わない（決定事項 2026-07-01 参照）」に書き換えます。

### 11. 対象データが0件のときの動作が決まっていない（L48–52）
- **理由:** 対象週のイベントが0件の場合（集計の不具合や上流の停止も含む）に、空のレポートを送るのか、エラーにするのかが決まっていません。何も起きていないように見える失敗になるかもしれません。
- **代案:** 0件の場合（あるいは前週より大きく減った場合）は警告ログを出し、レポートにもその旨を明記するなど、方針を決めます。

## low

### 12. 宛先リストの管理方法（L24）
- **理由:** 宛先を `config/report.yaml` に持たせると、宛先を変えるたびにデプロイが必要です。また、個人のメールアドレスがリポジトリに残ります。
- **代案:** 配信用のメーリングリストを1つ宛先にするか、設定を外部で管理します。

### 13. 「十分速い」の根拠がない（L61）
- **理由:** データ量は「数万行」とありますが、処理時間を測った結果が書かれていません。また、L34 は全行を `list[dict]` でメモリに載せる前提です。
- **代案:** 処理時間の実測値を書き添えます。集計は SQL の GROUP BY で行い、受け取る行数を減らします。

### 14. 完了の基準が書かれていない（L11）
- **理由:** 「手作業をなくす」は目的としては分かりますが、何をもって完了とするかの判定基準がありません。
- **代案:** 「担当者の作業を0分にする（例外時の対応を除く）」「N週続けて自動送信に成功する」などの受け入れ条件を書きます。
