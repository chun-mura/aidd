## 経路

- **dispatch した agent**: `aidd:reviewer` を3つ、1つのメッセージで並列に起動した。
  - Agent 1（構造）
  - Agent 2（データとエラー）
  - Agent 3（実用性）
  - 各 agent には対象パス `cases/data-error.md` と担当観点だけを渡し、「このファイルだけをレビューする」と明示した。棄却済み一覧は「なし」として渡した。
- **起動しなかった agent**:
  - Agent 4（プロジェクト固有）: `.aidd/design-perspectives.md` が無いため。
  - Agent 5（source-verifier）: `--verify-sources` が無いため。
  - Agent 6（security-reviewer）: 条件に当たらないと判定したため（理由は最後の節）。
- **refuter**: 起動した（sonnet）。reviewer の指摘に high/mid があったため。3つの reviewer の指摘から重複をまとめた F1〜F10（high/mid）を渡した。low は規定どおり refuter に回していない。
- **arbiter**: 起動した（`aidd:design-arbiter`）。deep では、反証後も high/mid が残れば起動する規定で、今回は残った。reviewer 間で深刻度が食い違っていた（F3・F4・F9・F10）ことも理由の一つ。
- **小規模対象ショートカット**: 使っていない。対象は1ファイル・46行だが、指示に従い並列 dispatch した。
- **自分で判断したこと**: `/aidd:issue-split` は提案しなかった。対象は単一バッチ＋キャッシュ層の変更で、独立してマージできる単位が2つ以上あるとは読めないため。

#### 最優先で直すべき1点

**F1: タイムアウトした商品を在庫0として書き込む方針（L38）**

1. タイムアウトした商品は書き込まず、前回値を保持する。表示が壊れるのを防ぐという L38 の目的は、前回値で満たせる。
2. `SyncResult` に `timeout_count` を追加し、欠測と在庫0を型で区別する（F8 の一部を同時に解消）。
3. 欠測と失敗の合計が閾値（例: 対象件数の X%）を超えたら非0で終了し、L45 の既存監視に乗せる。
4. 前回値が古くなりすぎるのを防ぐため、商品ごとに最終同期時刻を持ち、F9 の鮮度メトリクスとして出す。
