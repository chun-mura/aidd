## 最終報告

> **design-review 結果: `cases/data-error.md` (在庫数同期バッチ 設計書)** — depth=standard、小規模対象のためメインで直接レビュー、refuter で検証済み、arbiter なし
>
> **high (2件)**
> 1. **タイムアウト時に在庫を 0 で上書きしている (L38)**: WMS が一時的に遅れるだけで、在庫のある商品が DB と Redis で 0 になる。売り切れと表示されて販売機会を失い、正しい値も消える。その件数も観測できない。→ タイムアウトした商品は書き込まずに前回の値を残す。タイムアウト件数を SyncResult とログに出す。`last_synced_at` で鮮度を管理する。
> 2. **書き込み失敗が監視から見えない (L39, L45)**: 書き込み失敗を失敗件数に数えずスキップし、exit code 0 で終わる。監視は exit code だけなので、大量に失敗しても気づけず、古い在庫が表示され続ける。→ 書き込み失敗を失敗件数に数え、商品 ID をログに出す。失敗率が閾値を超えたら exit code を非0にする。
>
> **mid (3件)**
> 3. **在庫の二重管理と競合 (L34)**: 在庫を DB と Redis に二重に持ち、SyncBatch と ProductAdminService が別々に書き込み・削除する。片方だけ成功したときの回復方法が無い。バッチの実行中に廃番削除が走ると、バッチが削除済みのデータを作り直す。→ DB を唯一の持ち主にし、Redis は TTL 付きの cache-aside にする。書き込みと無効化は InventoryRepository 経由に限る。廃番の商品は書き込みから除外する。
> 4. **全件取得の規模と多重起動 (L15, L22)**: 件数の想定、ページング、所要時間の上限が無い。5分を超えたときの排他も無い。→ 想定件数と上限を明記し、ページングで取得する。ジョブに排他をかける。
> 5. **観測できる項目が足りない (L45)**: 失敗件数、0埋めした件数、所要時間、最終成功時刻が観測できない。→ これらをメトリクスとして出し、鮮度と失敗率にアラートを設定する。
>
> **low (2件)**
> 6. 構成表にコード上の配置 (ディレクトリ・ファイル) が無い (L20-25)。→ 配置先の列を追加する。
> 7. キャッシュミス時に Redis へ書き戻すかどうかと TTL が書かれていない (L34)。→ 明記する (改善案)。
>
> **反証で棄却した指摘:** なし
> **棄却済みの指摘 (過去ラウンド):** なし
> **security-reviewer:** 起動していない (信頼境界を跨がず、機微情報も保存しないと判定したため)。`/security-review` の推奨は対象外。

## security-reviewer の起動

**no。** 次の理由で、SKILL.md の起動条件に当たらないと判定した。

- **外部公開エンドポイントが無い。** 公開されるのは `GET /internal/stock/{product_id}` だけで、L30 に「サイト内部からのみ参照」とある。
- **扱うデータは機微情報ではない。** 在庫数だけで、個人情報、プロンプト、認証情報をファイル・ログ・キャッシュに保存する記述は無い。
- **認証情報は境界になっていない。** WMS API には認証がある (L40 の「認証エラー」から読み取れる) が、設計書は認証情報の扱いを新しく決めていない。WMS からの取り込みは社内システム間のバッチで、SKILL.md が起動しない例に挙げる「バッチ処理」に当たる。

`--security` も `--no-security` も付いていないので、上の判定どおり起動しなかった。
