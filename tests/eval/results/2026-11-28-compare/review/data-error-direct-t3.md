## refuter の判定
- **F1: 反証失敗。** 在庫0を書き込み対象から外す記述も、本当の0と区別する仕組みも、失敗件数に数える記述も、文書のどこにもありません。後の節で解消されてもいません。
- **F2: 反証失敗。** インターフェース節（29行目）の「失敗件数を返す」と、エラー処理節（39行目）は矛盾しています。書き込み失敗を検知するログ・アラート・再試行の記述もありません。
- **F3: 反証失敗。** 書き込み順序・片方失敗時の扱い・排他の記述がありません。5分間隔で全商品を書き込むことと、削除済み商品を除外する規定がないことから、廃番商品の在庫が復活する手順を組み立てられます。Redis への SET でも復活します。書き込み失敗は握りつぶされるので、乖離も修復されません。
- **F4: 反証失敗。** バッチが失敗終了するのは WMS の全面障害（認証エラー・5xx 連続）のときだけです。部分失敗とタイムアウトは exit code の監視では拾えず、メトリクスの記述もありません。
- **L1〜L3**: low のため refuter には渡していません（規定どおり）。

## 最終報告
**design-review 結果: `cases/data-error.md`（在庫数同期バッチ 設計書）**

経路: standard、小規模対象ショートカット（メインが直接レビュー）。refuter を通した high/mid は4件で、すべて反証失敗（指摘として残る）。arbiter は起動していない（矛盾なし、Agent 5 なし）。

**high（1件）**
1. **タイムアウトした商品を在庫0として書き込む**（エラー処理）
   取れなかった値を本当の在庫0として DB と Redis に上書きするため、在庫がある商品が売り切れと表示されます。起きても検知できません。
   → タイムアウトした商品は書き込まず前回値を残し、タイムアウト件数を数える。最終同期時刻を持たせ、古さが閾値を超えたら「在庫確認中」と表示するかアラートを出す。

**mid（3件）**
2. **書き込み失敗を失敗件数に数えず、exit 0 で終わる**（エラー処理／インターフェース）
   `SyncResult` の「失敗件数を返す」という定義と矛盾し、silent failure になります。
   → 失敗件数に数え、ERROR ログに出す。閾値を超えたら0以外の終了コードかアラートにする。
3. **DB と Redis の二重管理で、書き手も2つある**（データフロー）
   書き込む順序・片方失敗時の扱い・同時実行時の整合が書かれていません。廃番削除と競合すると在庫が復活し、DB と Redis の乖離も解消されません。
   → DB を正とした cache-aside 方式にし、TTL を付ける。書き込みを1つのサービスに集め、廃番商品をバッチの書き込み対象から外す。
4. **監視が exit code だけで、部分失敗に気づけない**（運用）
   → 失敗件数・タイムアウト件数・最終成功時刻をメトリクスにして、アラートを設定する。

**low（3件）**
5. 全商品取得の件数の想定・ページング・処理時間の上限が書かれていない。
6. キャッシュミス時に DB から読んだ値をキャッシュに書き戻すか、その TTL が書かれていない。
7. ロールバック時に、残ったキャッシュ・テーブルと StockApi の扱いが書かれていない。

**反証成立により除外した指摘**: なし
**棄却済み指摘**: なし

件数: **high 1 / mid 3 / low 3**

`/security-review` の推奨: なし。Agent 6 を起動しない判定で、セキュリティの high/mid 指摘も出ていないためです。

## security-reviewer の起動
**no**

起動条件は「信頼境界を跨ぐデータフローを含む」か「機微情報をファイル・ログ・キャッシュに保存する」です。この設計はどちらにも当たらないと判断しました。
- StockApi は `/internal/stock/{product_id}` で、「サイト内部からのみ参照」と書かれています。外部に公開されたエンドポイントではありません。
- 認証・認可の設計は変えていません。WMS API 側の認証エラーは失敗の分類として書かれているだけです。
- Redis・DB・ログに保存するのは商品IDと在庫数だけで、個人情報や認証情報は含みません。
- 全体として社内バッチと内部キャッシュの設計です。

ただし、WMS との連携で使う認証情報をどう管理するかは、設計書に書かれていないため未確認です。
