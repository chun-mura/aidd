## 経路

- **dispatch した agent**: 1つのメッセージで4つを並列に起動した。
  - aidd:reviewer ×3（Agent 1 構造、Agent 2 データとエラー、Agent 3 実用性）
  - aidd:security-reviewer（Agent 6）
  - 各 agent には `cases/security.md` のパスと担当観点、「棄却済み指摘: なし」だけを渡し、このファイルだけをレビューするよう明示した。
- **起動しなかった agent**:
  - Agent 4: `.aidd/design-perspectives.md` が無いため。
  - Agent 5: `--verify-sources` を付けていないため。
- **小規模対象ショートカット**: 使わなかった。対象は1ファイル・46行で使える条件に当たるが、指示に従って並列 dispatch した。
- **refuter**: 起動した（aidd:refuter、sonnet）。high/mid の指摘があったため。重複をまとめた high/mid の12件（A〜L）と引用行を渡した。low は規定どおり refuter に回していない。
- **arbiter**: 起動しなかった。
  - standard では、arbiter を起動するのは agent 間に矛盾がある場合か Agent 5 がある場合だけ。
  - 署名付きURLのログ記録（指摘A）は、reviewer 3名が high、security-reviewer が mid と評価した。全員が「欠陥であること」と「直し方（署名トークンを記録しない）」で一致しており、違うのは深刻度だけなので、内容の矛盾には当たらないと判断した。
  - 深刻度はメインで決めた。理由は最終報告に書いた。
- **ユーザーへの質問**: していない。判断が要るところは、判断と理由をこの出力に書いて進めた。

## reviewer の生指摘

### Agent 1 — 構造（aidd:reviewer）
1. **high**（L45・L33）：保存しないはずの署名付きURLを `AccessLogger` がログに残しており、L33 と矛盾する。ログ閲覧者が有効期限の5分以内に契約書を取得できる。

2. **high**（L29・L15・L33）：認可を担うコンポーネントが無い。対象取引先IDとユーザーの所属取引先を照合する処理がどこにも割り当てられていない。
   - 代案: `FileAccessPolicy` を追加する。認可失敗時に 404 と 403 のどちらを返すかを明記する。
3. **mid**（L22）：`FileUploadApi` に検証・S3操作・DB操作が同居している。
   - 代案: `ContractFileStorage` と `ContractFileRepository` を切り出す。
4. **mid**（L20-24）：各コンポーネントのコード上の配置が書かれていない。
   - 代案: 表に「配置」列を足す。マイグレーションの配置も書く。
5. **mid**（L24・L45・L15）：`AccessLogger` の呼び出し方、記録対象の範囲、ログ失敗時の挙動が決まっていない。
   - 代案: `record(event)` のシグネチャを定義し、記録対象を「全試行」と明記する。失敗時に fail-open か fail-closed かを決める。
6. **mid**（L28・L35-39）：API仕様が足りない。POST のリクエスト項目、成功時のレスポンス、401/403 が書かれていない。

7. **low**（L7）：要約形式にしたため、配置とインターフェースの記述が抜けている。認可とログの節は要約扱いにしない。

### Agent 2 — データとエラー（aidd:reviewer）
1. **high**（L45）：署名付きURL全体を90日保管している。L33 と矛盾し、有効期限5分の意味もなくなる。期限切れ後は再現に使えないため、保管する理由も成り立たない。
   - 代案: クエリ文字列を除いて記録し、再現が必要なら再発行する。ログ出力時にマスクするフィルタを入れる。
2. **high**（L29・L33）：取引先間の認可が無い。認可失敗時の応答コードも決まっていない。
   - 代案: 対象取引先IDと照合し、不一致は 404 に統一する。
3. **mid**（L22・L38）：S3保存とDB登録の一方だけが失敗した場合（孤児オブジェクトや実体の無いレコード）の扱いが設計されていない。
   - 代案: S3→DB の順にし、DBで失敗したら S3 のオブジェクトを削除して 5xx を返す。孤児を掃除する仕組みも用意する。
4. **mid**（L24・L45）：監査ログの書き込みに失敗したときの挙動が決まっておらず、silent failure の余地がある。INFOログに混ぜているため、ログ設定の変更で欠落しうる。
   - 代案: fail-closed か fail-open かを明記し、監査ログを専用の出力先に分ける。
5. **mid**（L37・L39）：不正な形式の file_id、401/403、DB障害、S3のオブジェクト欠落の扱いが無い。
   - 代案: エラー表に追加し、S3のオブジェクト欠落は不整合として別にアラートを出す。
6. **low**（L33）：`contract_files` の検索経路の前提が書かれていない。一覧APIを足すときに `対象取引先ID` のインデックスを設計する。

### Agent 3 — 実用性（aidd:reviewer）
- YAGNI の観点では指摘なし。
1. **high**（L45）：署名トークンを含むURLをログに残しており、記録する内容が目的に対して多すぎる。
   - 代案: 時刻、request_id、ユーザーID、file_id、取引先ID、結果、オブジェクトキー、有効期限を記録する。監査ログは分離し、90日の根拠を明記する。
2. **mid**（L44）：監視が 4xx/5xx のレートだけで、レイテンシ、S3失敗、アップロード失敗の理由別件数、アラート条件が無い。
   - 代案: p95/p99、理由別の失敗数、S3呼び出しのメトリクス、502 のアラートを定義し、request_id を全ログに通す。
3. **mid**（L24・L45）：監査ログについて、404 や認可拒否も記録するか、失敗時に fail-open か fail-closed か、アップロードも記録するかが決まっていない。
   - 代案: 全リクエストを記録し、fail-closed を推奨。アップロードのイベントも記録する。
4. **mid**（L43）：「ルーティング追加のみ」と書かれているが、テーブル作成・S3バケット・IAM の準備と、ロールバック時のデータの扱いが無い。
   - 代案: マイグレーションを前方互換にし、IAM の手順を書く。フィーチャーフラグも検討する。
5. **low**（L38）：S3障害のログに、ログレベル、request_id、S3のエラーコードが明記されていない。

### Agent 6 — セキュリティ（aidd:security-reviewer、STRIDE）
1. **high**（EoP・情報漏えい、L29）：「認証済み」だけで署名付きURLを発行するため、他の取引先の file_id を入手すれば他社の契約書を取得できる。
   - 代案: 対象取引先IDと照合し、ロールモデルを定義する。認可拒否は 404 に統一する。
2. **mid**（情報漏えい、L45）：署名トークンをログに残すため、ログ閲覧権限が事実上契約書の閲覧権限になる。90日後の再現目的は、期限切れで成り立たない。
   - 代案: トークンを記録せず、再発行で足りると書く。ログ閲覧権限の範囲も明記する。
3. **mid**（否認、L24・L45）：拒否されたリクエストの記録、IP、S3側のアクセスログが無い。監査ログは INFO に混在しており、改ざん防止も無い。
   - 代案: 成功と拒否の両方を記録し、S3 のアクセスログか CloudTrail のデータイベントを有効にする。保管先は追記専用（Object Lock）に分ける。
4. **mid**（改ざん・なりすまし、L28）：Cookie 認証の multipart POST に CSRF 対策が無い。社内ロールがあれば任意の取引先IDに登録できる。
   - 代案: SameSite、CSRFトークン、Origin 検証のいずれかを使い、登録先の担当範囲を検証する。
5. **mid**（改ざん・情報漏えい、L28・L33）：悪意あるPDFはマジックバイト検証を通る。ファイル名の扱いも書かれていない。
   - 代案: 非同期のウイルススキャンを入れ、S3キーはサーバーで生成する。ファイル名は正規化し、`response-content-disposition: attachment` を付ける。
6. **low**（DoS、L28・L44）：レート制限が無い。同居する既存APIにも影響しうる。
7. **low**（情報漏えい、L29・L37）：Location ヘッダが履歴に残る。404 と 403 の違いから file_id の存在が分かる。
   - 代案: パブリックアクセスブロック、SSE、`Cache-Control: no-store` を明記する。

## security-reviewer の起動

**yes**。起動条件を満たすとメインループが判定した。理由は次の3つで、`--security` は付けていない。
- 外部公開のエンドポイント（`GET /api/files/{file_id}` を取引先ユーザーが使う）がある。
- 認証・認可の境界を跨ぐデータフロー（社内ユーザーと取引先ユーザーのロール）がある。
- 機微情報（署名トークン入りのURL、つまり契約書へのアクセス権に相当する値）をログに保存する設計になっている。
