## 経路

- **dispatch した agent**: `aidd:reviewer` 3体を1つのメッセージで並列に起動しました。Agent 1 が構造、Agent 2 がデータとエラー、Agent 3 が実用性の担当です。各 agent には対象のパス `cases/data-error.md` と担当観点だけを渡し、「このファイルだけをレビューする」と明示しました。棄却済み一覧は「なし」として渡しています。
- **起動しなかった agent**
  - Agent 4（プロジェクト固有）: `.aidd/design-perspectives.md` が無いため起動しませんでした。
  - Agent 5（source-verifier）: `--verify-sources` の指定が無いため起動しませんでした。
  - Agent 6（security-reviewer）: 判定の結果、起動しませんでした。理由は最後の節に書きます。
- **小規模対象ショートカット**: 使っていません。対象は1ファイル・46行なのでショートカットを使える大きさですが、指示に従って並列 dispatch しました。
- **`.aidd/review-dismissed.md`**: `.aidd/` が無いため、読み込みはしていません。
- **issue-split**: 提案していません。対象は単一バッチとキャッシュ層の変更で、独立してマージできる単位が2つ以上あるとは判断しませんでした。
- **refuter**: 起動しました（`aidd:refuter`、sonnet）。high/mid の指摘があったためです。重複をまとめた12件（F1〜F12）を渡しました。
- **arbiter**: 起動していません。standard では、arbiter を起動する条件は「agent 間の矛盾」または「Agent 5 がある」場合だけです。Agent 5 は起動していません。
  - reviewer 間の食い違いは深刻度の評価差だけでした。DB と Redis の二重管理を Agent 2 は high、Agent 1 と Agent 3 は mid とし、二重実行を Agent 2 は mid、Agent 3 は low としています。
  - 指摘の向き（問題があるかどうか）は一致しているため、矛盾には当たらないと判断しました。深刻度は refuter の補正案を参考にメインで決めました。

## 最終報告

> **design-review 結果: `cases/data-error.md`（在庫数同期バッチ 設計書）**  
> 経路は standard です。reviewer 3体を並列に起動し、high/mid は refuter を通しました。arbiter は起動していません（矛盾も Agent 5 も無いため）。
>
> **high（3件）**
> 1. **L38 タイムアウトした商品を在庫0として DB と Redis に書き込む**
>    - 問題: WMS のタイムアウトが一時的なものでも、実在庫のある商品が5分間「在庫なし」と表示されます。失敗として数えられないため、全件がタイムアウトしても L40 の判定にかからず、検知できません。L40 の「5xx連続」の閾値が無いことと、L38 との境界が不明なことも同じ根です。
>    - 代案:
>      - タイムアウトした商品は書き込まず、前回値を残す。件数はタイムアウト件数として数える。
>      - `updated_at` を持たせ、上限より古い値は `StockApi` が「在庫不明」と返す。
>      - 5xx連続とタイムアウト率に数値の閾値を決め、超えたらバッチを失敗させる。
> 2. **L39 書き込みの失敗を失敗件数に数えず、exit 0 で終了する（silent failure）**
>    - 問題: L29 の「失敗件数を返す」と矛盾します。監視は exit code だけを見るため（L45）、全件の書き込みに失敗しても検知できません。`SyncResult` の失敗件数が非0になる経路は、文書上にありません。
>    - 代案:
>      - `SyncResult` を `succeeded` / `write_failed` / `wms_timeout` に分けて定義する。
>      - 失敗した商品は product_id 付きで ERROR ログに出す。
>      - 失敗率の閾値を明記し、超えたら非0で終了する。
> 3. **L34 DB と Redis の二重管理で、正（source of truth）が決まっていない。廃番削除と競合する**
>    - 問題: 片側だけ成功した場合の扱いが書かれていません。また、「`SyncBatch` が取得 → `ProductAdminService` が廃番で削除 → `SyncBatch` が書き戻す」の順に動くと、廃番商品の在庫行とキーが復活します。
>    - 代案:
>      - DB を正、Redis を派生キャッシュと明記する。DB の更新後に Redis を更新または削除し、Redis には TTL を付ける。
>      - バッチは廃番商品を書き込まない（条件付き更新）。
>      - 在庫の読み書きと削除を担う窓口（例: `InventoryService`）を1つに絞り、`ProductAdminService` もそこを経由させる。
>
> **mid（7件）**
> 4. **L15, L44 二重実行の対策が無い**
>    - 問題: 前回のバッチが5分で終わらないと次の実行と重なり、古い取得結果が新しい結果を上書きする恐れがあります。
>    - 代案: 実行ロックをかける（または、基盤が多重起動を防ぐ仕様であることを明記する）。`fetched_at` が新しい場合だけ更新する条件付き更新にする。
> 5. **L22, L34 全件取得の性能前提が無い**
>    - 問題: 想定する商品数、WMS のレート、所要時間の記載がなく、5分間隔に収まる根拠がありません。`inventory.product_id` を PK またはユニークにする前提も書かれていません。
>    - 代案: これらの見積りと前提を追記する。
> 6. **L45 監視とログが不足している**
>    - 問題: 監視が exit code と成功件数の INFO ログだけで、障害調査や性能分析に必要な値を観測できません。
>    - 代案:
>      - 構造化ログに processed / failed / timeout / duration_ms を出す。
>      - last_success_timestamp、cache miss 率をメトリクスとして取る。
>      - 「最終成功から15分超」でアラートを出す。
> 7. **L44 ロールバックで、書き込み済みの誤データが残る**
>    - 問題: 「ジョブ定義の削除」だけでは、0 で上書きされた在庫などが DB と Redis に残ります。
>    - 代案: 再同期手順、Redis キーのフラッシュ手順、`StockApi` を DB の直接参照に切り替える手順を書く。
> 8. **L27-30 インターフェースの定義が不足している**
>    - 問題: Repository と Cache の公開メソッド、`StockApi` のレスポンスとエラー仕様（在庫行が無い商品や、DB と Redis の両方が失敗した場合）、Redis のキー形式と TTL が書かれていません。キー形式は `ProductAdminService` も使うため、外部との約束事（契約）になります。
>    - 代案: 上記を表にして追記する。
> 9. **L20-25, L34 配置と変更範囲が未記載**
>    - 問題: 既存の `ProductAdminService` の所在と、今回の変更範囲が書かれていません。
>    - 代案: 構成表に「配置」列を追加する。`ProductAdminService` の変更点を明記する。（要約形式なので、新規コンポーネントの配置は簡潔でかまいません。）

>     - 問題と代案: 1件目にまとめて書きました。refuter も、F1 と根が同じと判定しています。独立した mid として数えています。

> 11. **L22 `SyncBatch` が、WMS の呼び出し・永続化の調整・集計を兼ねている**
>     - 代案: `WmsClient` を分離し、WMS の仕様変更が `SyncBatch` に波及しないようにする。（refuter の補正案に従い、mid から low に下げました。）

## security-reviewer の起動

**no**

理由: 次の判断から、信頼境界を跨ぐデータフローにも、機微情報の保存にも当たらないと判定しました。

- `StockApi` はサイトの内部からだけ参照するエンドポイントで（L30）、外部に公開されていません。
- 扱うデータは商品ごとの在庫数で、個人情報・プロンプト・認証情報をファイル・ログ・キャッシュに保存する記述はありません。
- WMS API の呼び出しには認証が伴います（L40 の「認証エラー」）。ただし、設計書は秘密情報の保管や受け渡しを設計の対象にしていません。
- 全体として、社内システム間で非機微なデータを同期するバッチ処理です。

`--security` / `--no-security` の指定はありません。Agent 6 を起動しておらず、信頼境界を跨ぐ設計でもないと判定したため、`/security-review` の推奨は付けていません。
