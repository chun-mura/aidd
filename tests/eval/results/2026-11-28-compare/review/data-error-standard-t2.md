## 経路

- **dispatch した agent**: `aidd:reviewer` を3つ、1つのメッセージで並列に起動した。
  - Agent 1(構造)
  - Agent 2(データとエラー)
  - Agent 3(実用性)
  
  各 agent には、対象パス `cases/data-error.md` と担当観点、棄却済み一覧(なし)だけを渡した。「このファイルだけをレビューする」とも明示した。
- **起動しなかった agent**:
  - Agent 4: `.aidd/design-perspectives.md` が無いため起動しない。
  - Agent 5: `--verify-sources` の指定が無いため起動しない。
  - Agent 6: 起動しない。理由は下の「security-reviewer の起動」に書いた。
- **小規模対象ショートカット**: 使っていない。対象は1ファイル・46行で条件には当たるが、評価の指示に従って並列 dispatch した。
- **`.aidd/review-dismissed.md`**: `.aidd/` が無いため読み込んでいない。棄却済み指摘はなし。
- **issue-split の提案**: しない。対象はバッチ・キャッシュ・参照 API の1つの変更で、独立してマージできる単位が2つ以上あるとは判断しなかった。
- **refuter**: 起動した(`aidd:refuter`、sonnet)。high/mid の指摘があったため。3つの agent の指摘をメインで重複排除して F1〜F9 の9件にまとめ、対象パスと一緒に渡した。
- **arbiter**: 起動していない。standard の条件は「agent 間の矛盾 または Agent 5 がある場合」で、どちらも無かった。
  - F3 では深刻度が分かれた(Agent 1 は mid、Agent 2 は high)。ただし指摘の方向と代案(在庫の正本を1つにし、書き込みを1か所に集める)は両立する。そのため矛盾ではないと判断した。深刻度は refuter の判定(high が妥当)に合わせた。
- **最終報告の作り方**: 反証を通った high/mid をメインがそのまま並べた。

### Agent 2 — データとエラー
1. **[high] L38**: 取得できなかった値を、実在庫の0として DB と Redis に書き込む。
   - 在庫がある商品が売り切れ表示になる。検知する手段も無い。

2. **[high] L39**: 書き込みの失敗を件数に数えず、exit code 0 で終える。L29 とも食い違う。
   - 全件の書き込みに失敗しても、監視は検知できない。
   - 代案: `failed_count` に数える。product_id 付きで WARN/ERROR ログを出す。失敗率が閾値を超えたら非0で終了する。
3. **[high] L34**: DB と Redis の二重管理で、書き手が2者いる。どちらも非原子的に書く。

   - 代案: DB を正本にする。書き込み順を「DB → Redis」に固定する。廃番は論理削除にする。排他ロックをかける。UPSERT にする。TTL を設定する。
4. **[mid] L22 / L34**: 全商品を毎回取得するが、規模の見積もりが無い。
   - 5分に収まる根拠、ページング、`inventory` の主キーとインデックスも書かれていない。
   - 代案: `product_id` を主キーにすると明記する。件数と所要時間を見積もる。ページングとバルク取得を書く。

- ロールバックの復旧手順

1. **[high] L39 / L45**: 失敗を観測する経路が無い。L29 とも食い違う。

## 最終報告

> # design-review 結果: `cases/data-error.md`(在庫数同期バッチ 設計書)
>
> 経路: standard。reviewer 3つを並列に起動し、high/mid を refuter で反証した。arbiter は条件に当たらないため起動していない。security-reviewer は起動していない。
>
> ## high(3件)
>
> **H1. タイムアウトした商品に在庫0を書き込む(L38)**
> - 取得できなかった値を実在庫の0として DB と Redis に書くため、在庫がある商品が WMS の一時的な遅れだけで売り切れ表示になる。
> - タイムアウト件数はどこにも記録されず、実在庫の0と区別できない。
> - 代案:
>   - タイムアウトした商品は書き込まず、前回値を残す。
>   - `SyncResult` に `timeout_count` を加え、ログとメトリクスに出す。
>   - タイムアウト率が閾値を超えたら、バッチを失敗扱いにする。
>   - 表示の都合で値が要るなら、0 とは別に「在庫不明」の状態を設ける。
>
> **H2. 個別の書き込み失敗を数えず、exit code 0 で終える(L39、L29 と食い違う)**
> - L29 は「失敗件数を返す」、L39 は「失敗件数には数えない」で、仕様が食い違っている。
> - 監視は exit code と同期件数の INFO ログだけ(L45)。DB や Redis の障害で全件失敗しても検知できない(silent failure)。
> - 代案:
>   - 書き込み失敗を `SyncResult.failed` に数える。
>   - product_id と原因を WARN/ERROR ログに出す。
>   - 失敗率が閾値を超えたら非0で終了する。閾値は設計書で決める。
>   - 失敗件数と失敗率を監視対象に加える。
>
> **H3. 在庫を DB と Redis で二重管理し、書き手が2者いる(L34)**
> - `SyncBatch` と、既存の `ProductAdminService` が、それぞれ DB と Redis を直接書き換える。
> - 次が書かれていない: 書き込み順、片方だけ失敗したときの扱い、排他、TTL。
> - そのため、廃番の削除直後に同期が書き戻すと、廃番商品の在庫が復活しうる。WMS が廃番商品を返す場合に起きる。
> - 代案:
>   - DB を正本、Redis を導出キャッシュとする。
>   - 書き込み・削除・読み出しを1つのコンポーネント(例: `InventoryStore`)に集める。順序(DB → Redis)と失敗時の扱いはそこだけで決める。
>   - Redis には TTL を設定する。
>   - `SyncBatch` は廃番商品を除外し、UPSERT で冪等にする。
>   - `ProductAdminService` を変更することを、スコープと構成の表に書く。
>
> ## mid(5件)
>
> **M1. 規模とインデックスの前提が無い(L22 / L34)**
> - 全商品を5分ごとに取得するが、次が書かれていない: 件数の想定、所要時間の見積もり、WMS のレート制限とページング、`inventory` の主キーとインデックス。
> - 代案:
>   - `inventory(product_id PK, quantity, synced_at)` のように定義を書く。
>   - 件数と所要時間を見積もる。
>   - バルク取得とページングを書く。
>
> **M2. インターフェースが足りない(L29-30)**
> - 次が決まっていない: `SyncResult` のフィールド、`StockApi` のレスポンス形式、未登録の `product_id` での挙動(404 か 0 か)、Repository と Cache のメソッド。
> - 代案: シグネチャとレスポンス例を書き、未登録時のステータスコードを決める。
>
> **M3. ログとメトリクスでは障害調査・性能分析ができない。多重起動の扱いも無い(L45)**
> - 次が無い: 所要時間、WMS のエラー数、最終成功時刻、キャッシュヒット率。
> - 5分の間隔を超えて実行したときの多重起動の扱いが無い。多重起動は H3 の競合を悪化させる。
> - 代案:
>   - 1回の実行ごとにサマリーログを1行出す。項目は start/end、duration、処理・失敗・timeout の件数、WMS エラー数。
>   - 「最終成功時刻が N 分以上前」でアラートを出す。
>   - 多重起動を防ぐ方法(ロック、またはスキップ)を明記する。
>
> **M4. ロールバックしても状態が戻らない(L44)**
> - ジョブ定義を削除しても、書き込み済みの DB と Redis の値は戻らない。
> - StockApi と Redis 層をロールバックする手段も、TTL も無い。
> - 代案:
>   - Redis に TTL を設定する。
>   - StockApi を DB 直読みに切り替えるフラグを用意する。
>   - WMS から取り込み直して上書きする復旧手順を書く。
>
> **M5. コンポーネントのコード上の配置が書かれていない(L20-25)**
> - 代案: 表に「配置」列を足し、既存の層構造に沿ったパスを書く。既存と異なる配置にするときだけ理由を添える。
>
> ## low(3件)
>
> - **L1.** `StockApi` が、キャッシュミス時に DB を読む方針まで持っている(L25 / L34)。H3 の Store に移すと解消する(refuter の判定で mid から下げた)。
> - **L2.** 廃番の削除に失敗したときのログが無い(L34)。
> - **L3.** L7 の「要約形式」という規模の記載が、実態と合っているか見直す。実際には既存の `ProductAdminService` の変更を含み、コンポーネントも4つある。
>
> ## 反証で棄却した指摘
> なし

## security-reviewer の起動

**no**

この設計は、信頼境界をまたぐデータフローと、機微情報の保存のどちらにも当たらないと判断した。`--security` と `--no-security` の指定も無い。

- **外部公開エンドポイントが無い**: 参照 API は `/internal/stock/{product_id}`(L30)で、「サイト内部からのみ参照」と書かれている。
- **外部から入ってくるデータは在庫数だけ**: WMS は社内の倉庫管理システムからの取り込みで、入ってくるのは在庫数という数値だけである。L40 に「認証エラー」とあるが、秘密情報の扱いは設計の主題ではない。
- **保存するのは在庫数だけ**: DB と Redis に保存するのは在庫数で、個人情報・プロンプト・認証情報は含まない。

Agent 6 を起動しておらず、`--no-security` で起動を止めた場合にも当たらない。そのため、実装後に `/security-review` を推奨する記載は付けていない。
