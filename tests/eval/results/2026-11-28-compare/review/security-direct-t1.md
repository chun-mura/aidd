## 最終報告

> **design-review 結果: 契約書ファイル共有API 設計書（`cases/security.md`、depth=standard）**
>
> **high（2件）**
> 1. **ダウンロード API に認可が無い**（インターフェース `GET /api/files/{file_id}`）
>    - 「認証済みユーザーであれば」署名付きURLを発行しており、`contract_files.対象取引先ID` との照合がありません。
>    - 取引先A のユーザーが取引先B の file_id を手に入れれば、B の契約書を取得できます。UUIDv4 は認可の代わりになりません。
>    - 代案: 要求したユーザーの所属取引先IDと一致する場合だけ発行する。社内ユーザーはロールと担当範囲で判定する。一致しなければ 404 に統一し、拒否も監査ログに記録する。
> 2. **署名トークンを含む署名付きURLを INFO ログに 90日保管**（運用 > 監査ログ）
>    - ログを読める人やログの転送先が、発行後5分以内なら認証なしで契約書を取得できます。
>    - 期限切れの URL は再現に使えないので、記録する理由も成り立ちません。
>    - 代案: URL とクエリ文字列は記録しない。記録するのは時刻・ユーザーID・file_id・取引先ID・結果・リクエストIDに限る。調査はリクエストIDと S3 のアクセスログ（または CloudTrail データイベント）を突き合わせて行う。
>
> **mid（4件）**
> 3. **監査ログの書き込みに失敗したときの挙動が決まっていない**（AccessLogger）
>    - fail-open か fail-closed かが書かれておらず、監査が漏れても気づけません。
>    - 代案: 失敗時の挙動とアラートを明記する。
> 4. **アップロードで一方だけ失敗した場合の扱いが無い**（FileUploadApi）
>    - S3 への保存と DB への登録の片方だけが失敗すると、S3 にだけファイルが残るか、実体の無いメタデータが残ります。
>    - 代案: 保存の順序、補償削除、定期クリーンアップを明記する。
> 5. **監査ログの網羅性と改ざん耐性**
>    - 拒否・404・アップロードが記録されません。保存先は通常の INFO ログです。
>    - 代案: 記録対象を広げ、追記専用の別権限ログ領域に置く。90日で監査要件を満たすか確認する。
> 6. **アップロードの検証と保存の設計が足りない**（POST /api/files）
>    - 取引先IDを指定する権限と、その存在検証が書かれていません。
>    - ファイル名のサニタイズ（S3 キー、Content-Disposition）が書かれていません。
>    - 受信中の段階でのサイズ制限、S3 の公開ブロックと暗号化、マルウェアスキャンの方針が書かれていません。
>    - 代案: S3 キーはサーバーが生成する UUID にし、それぞれの方針を明記する。
>
> **low（3件）**
> 7. 背景に挙げた「版管理の混乱」への対策が設計にありません。スコープに入れるか「やらない」に明記してください。
> 8. 403/404 の急増（総当たり）や取引先ごとのダウンロード数を観測する手段がありません。拒否件数のメトリクスとアラートを追加してください。
> 9. 取引先アカウントの認証要件（MFA）とレート制限が書かれていません。

## security-reviewer の起動

**yes。** `--security` も `--no-security` も付いていないので、内容から判定しました。この設計には、取引先が使う外部公開エンドポイント（POST / GET `/api/files`）、認証・認可、署名付きURLという秘密情報が含まれ、信頼境界を跨ぐデータフローがあります。さらに、署名トークンという機微情報を INFO ログに 90日保管しています。起動条件の2つ（信頼境界を跨ぐデータフロー、機微情報のログ保存）の両方に当たるため、起動しました。
