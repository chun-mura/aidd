1. **high** L45・L24：署名付きURL全体をログに記録している（情報漏えい・権限昇格・否認：STRIDE の I/E/R）。ログを読める人が5分以内に使えば、認証なしでダウンロードできる。監査上の実行者も実際の取得者と一致しなくなる。
   - 代案：署名クエリ（`X-Amz-Signature` など）はログに出さないと明記する。記録は再発行に必要な入力値に限り、専用の監査ログに分ける。
2. **high** L29・L33：IDOR。認可がオブジェクト単位になっていない（E/I）。UUIDv4 は推測しにくいだけで、認可の代わりにはならない。
   - 代案：所属取引先IDと contract_files の取引先IDの一致を必須とし、不一致は 404 にする。
3. **mid** L15・L28-29：取引先ユーザーのロール定義、アカウント無効化時のセッション失効、CSRF 方針が無い（S/E）。
   - 代案：必要ロールを明記し、無効化時はセッションを即時失効させ、CSRF トークンか SameSite の方針を書く。
4. **mid** L22・L28：アップロードの悪用対策が無い（T/D）。細工されたPDF、レート制限、ファイル名の扱い、バケット設定が書かれていない。
   - 代案：S3 キーはサーバー生成にし、Content-Disposition はサニタイズする。レート制限とスキャン方針を書き、Block Public Access・SSE・GetObject のみの最小権限を設定する。
5. **mid** L15・L24：アップロード・変更・削除・認可失敗の監査が無い（R）。
   - 代案：これらも同じ監査ログに追記専用で記録する。
6. **low** L29：302 応答に Cache-Control と Referrer-Policy が無い。レート制限と 404 連打の検知も無い。
7. **low** L37・L39：権限なしと不存在で応答が異なると、ファイルの存在を確かめられる。
   - 代案：どちらも 404 に揃え、失敗理由は固定のエラーコードにする。

### design-review 結果：`cases/security.md`（--depth=deep）

**矛盾の裁定（H2 の代案：403 か 404 か）**
セキュリティ agent の案を採ります。対象取引先が一致しない GET には 404 を返し、存在しない場合と区別させません。
- L37 は「存在有無以外の内部情報を含めない」方針です。ここで 403 を返すと、ファイルの存在が分かってしまいます。
- 中身が契約書なので、別の取引先のファイルが存在するという事実そのものが秘匿対象です。
- 403 は、ロールの不一致がはっきりしているケースに限って使います（例：取引先ユーザーが POST した場合）。

**セキュリティ / 認可**
- **[high] H2（L29/L33）**：GET の認可が「認証済みであること」だけで、`contract_files.対象取引先ID` との照合がありません（M1 のうち「ダウンロード側のロール未定義」はここに統合）。
- **[high] H1（L45）**：署名付きURLを署名トークンごと INFO ログに書き、90日保管しています。URL は5分で失効するので、「URL を再現する」という理由も成り立ちません。3つの agent が独立に指摘しています。
- **[high・横断] H1 と H2 が重なると、被害が5分で終わりません**：ログに残る file_id を拾えば、照合が無いため、自分のアカウントで署名付きURLを何度でも取り直せます。根本原因は H2 です。
- **[mid] M1 の残り**：アカウント無効化時のセッション失効方針と、POST の CSRF 方針がありません。
- **[mid] M2（L22/L28）**：アップロード悪用への対策がありません。具体的には、細工されたPDF、レート制限、ファイル名の扱い（S3 キーに使わない、Content-Disposition のエスケープ）、バケットの非公開・SSE・IAM の最小権限です。
- **[low]**：302 応答に Cache-Control と Referrer-Policy が無く、ダウンロード側のレート制限もありません。

**監査**
- **[mid] M3（L15/L24/L45）**：監査対象がダウンロードだけです。アップロード・削除・拒否（404 を含む）を記録せず、改ざん防止と閲覧制御もありません。
- **[mid] M11（L24/L45）**：AccessLogger の書き込みが失敗したときに、ダウンロードを通すのか止めるのか（fail-open / fail-closed）が決まっていません。

**インターフェース / エラー処理**
- **[mid] M6＋M9（L28/L35-39）**：POST の入力項目（対象取引先IDの必須指定と、その値の検証）とレスポンスが未定義です。401/403/404 の使い分け、DB 障害時の応答、502 がどちらの経路で起きるのかも書かれていません。
- **[low]**：失敗理由をエラーコードとして固定していません。S3 のリトライとタイムアウトも未定義です。

**構造 / データ**
- **[mid] M5＋M10（L22/L33）**：FileUploadApi が S3 保存と DB 登録の両方を担っています。
  - S3 は成功して DB が失敗すると、孤立したオブジェクトが残ります。その扱いが書かれていません。
  - 逆に DB にあって S3 にない場合は、存在確認をせずに URL を発行するため、黙って失敗します。
- **[low] M4（L20-24）**：コード配置が書かれていません。要約形式（L7）なので深刻度を下げました。
- **[low]**：file_id を主キーにする前提と、対象取引先IDのインデックスが書かれていません。背景（L11）で挙げた版管理に対応するデータもありません。

**運用**
- **[mid] M7（L43）**：「ルーティング追加のみ」とありますが、実際にはテーブル・S3 バケット・IAM も追加します。マイグレーション手順と、revert したときのデータとバケットの扱いが書かれていません。
- **[low] M8（L44）**：監視が 4xx/5xx のレートだけで、404 の急増や S3 起因の 502 を見分けられません。

**最優先で直すべき1点：H2。GET /api/files/{file_id} に対象取引先との認可照合を入れる（L29/L33/L37）**
- 理由：「取引先ごとに契約書を出し分ける」という目的を直接崩す欠陥で、H1 の被害を時間の制限なしに広げる原因でもあります。
- 代案：
  - 所属取引先IDと `contract_files.対象取引先ID` が一致する場合だけ、署名付きURL（5分）を発行して 302 で返す。
  - 社内ユーザーは、自分がアップロードしたファイルか担当範囲のファイルに限る（範囲は別途定義する）。
  - 一致しない場合と存在しない場合は、どちらも同じ 404 を返す。本文・ヘッダー・応答時間でも区別できないようにする。
  - 照合は `WHERE file_id = ? AND 対象取引先ID = ?` の1クエリで行う。拒否したことは AccessLogger に記録する。
  - あわせて L45 の記録項目から署名付きURL全体を削り、オブジェクトキーと有効期限だけにする（小さい作業なので同じ修正に含めることを推奨）。

**棄却（反証成立）した指摘**：なし

**推奨**：Agent 6（セキュリティ）が high/mid の指摘を出したため、実装後に `/security-review` を実行してください。

**注記**：この裁定は設計レビューのたたき台です。セキュリティ方針として確定させたり設計書に反映したりする前に、担当者が事実とセキュリティ面を確認してください。

## security-reviewer の起動

**yes**

理由：起動条件に意味のうえで当たると判定しました（`--security` は付けていません）。
- 設計に信頼境界をまたぐデータフローがある。公開 API エンドポイント2本、社外の取引先ユーザーの認証認可、外部からの multipart 入力。
- 機微情報をログに保存する。L45 で、資格情報に相当する署名トークンを含む URL を INFO ログに90日保管している。
