## 経路

- **小規模対象ショートカット**: 使った。対象は1ファイル・46行で、条件（1ファイル・100行未満）に当てはまる。`--verify-sources` も付いていない。そのため Agent 1〜3（aidd:reviewer）は dispatch せず、メインが構造・データとエラー・実用性の観点で直接レビューした。
- **Agent 4（プロジェクト固有の観点）**: 起動していない。`.aidd/design-perspectives.md` が無いため。
- **Agent 5（source-verifier）**: 起動していない。`--verify-sources` が付いていないため。
- **Agent 6（aidd:security-reviewer）**: 起動した。ショートカットが Agent 6 も省くかどうかは SKILL.md から一意に読めないため、次のように判断した。
  - SKILL.md の例外規定は Agent 5 についてしか書いていない。
  - 一方で Agent 6 は「メインループが対象の内容から判定する」と、独立した条件として書かれている。
  - 小規模対象ショートカットが置き換えるのは標準の3グループの reviewer だと解釈した。条件を満たす Agent 6 は別に起動した。
- **refuter（aidd:refuter）**: 起動した。high/mid の指摘が7件あったため。渡したのは指摘・引用箇所・対象ファイルのパスだけ。
- **arbiter**: 起動していない。standard では、agent 間で矛盾がある場合か Agent 5 がある場合にだけ起動する。今回はどちらにも当たらない。M2 と S3 はどちらも監査ログを扱うが、M2 は書き込みに失敗したときの経路、S3 は記録する範囲と改ざん耐性の話で、矛盾ではない。

## reviewer の生指摘

### メインの直接レビュー（構造・データとエラー・実用性）

- **M1 (mid)**
  - 引用箇所: 構成と責務 `FileUploadApi`「S3への保存、メタデータのDB登録」、エラー処理
  - 指摘: S3 への保存と DB への登録のうち、片方だけが成功した場合の扱いが設計されていない。
    - S3 だけ成功すると、DB から参照されないオブジェクトが残る。
    - DB だけ成功すると、メタデータはあるのに実体が無い状態になる。
  - 代案: 次の3点を設計書に書く。
    - 処理の順序: S3 に保存してから DB に登録する。
    - DB 登録に失敗したら、S3 のオブジェクトを削除する。
    - 参照されないオブジェクトを定期的に掃除する（または S3 のライフサイクルで消す）。
- **M2 (mid)**
  - 引用箇所: `AccessLogger`、エラー処理
  - 指摘（2点）:
    - 監査ログの書き込みに失敗したとき、署名付きURLを発行するかどうか（fail-open か fail-closed か）が書かれていない。監査ログが黙って欠ける余地がある。
    - DB にメタデータはあるが S3 に実体が無い場合の応答（404 か 502 か）が決まっていない。
  - 代案:
    - 監査ログの書き込みに失敗したら URL を発行せず 503 を返す（fail-closed）と明記する。
    - 書き込み失敗の件数をメトリクスとして監視に乗せる。
    - 実体が無い場合は 502 を返し、ERROR ログを出すと決める。
- **L1 (low)**
  - 引用箇所: 構成と責務
  - 指摘: 各コンポーネントをコード上のどこ（ディレクトリ・ファイル）に置くかが書かれていない。
  - 代案: 既存の API サーバーの中での配置先を表に書き足す。

### security-reviewer（STRIDE）

- **S1 (high)**
  - 引用箇所: インターフェース `GET /api/files/{file_id}`「認証済みユーザーであれば」
  - STRIDE: 権限昇格（Elevation of Privilege）、情報漏えい（Information Disclosure）
  - 指摘: 取引先ID との照合をしていない。取引先A のユーザーが、取引先B 宛ての `file_id` をメール転送などで入手すれば、他社の契約書を取得できる（IDOR）。UUIDv4 は推測しにくいだけで、認可の代わりにはならない。
  - 代案: URL を発行する前にサーバー側で次の認可を行うと明記する。
    - 許可条件: セッションユーザーの所属取引先ID が `contract_files` の対象取引先ID と一致する場合、または社内ユーザーロールを持つ場合。
    - 一致しない場合は、存在しない `file_id` と同じ 404 を返す。
- **S2 (mid)**
  - 引用箇所: 運用「署名付きURL全体…INFO ログ…90日保管」
  - STRIDE: 情報漏えい（Information Disclosure）
  - 指摘: ログを閲覧できる人は、URL の有効期間（5分）の間なら、認証なしで S3 から契約書を取得できる。しかも URL は5分で失効するので、「障害調査で URL を再現する」という目的も成り立たない。
  - 代案:
    - URL もクエリ文字列もログに残さない。記録するのは `file_id`、ユーザーID、取引先ID、時刻、署名の有効期限だけにする。
    - ログを誰が閲覧できるかを設計書に書く。
- **S3 (mid)**
  - 引用箇所: `AccessLogger`、運用
  - STRIDE: 否認（Repudiation）
  - 指摘（2点）:
    - アップロード、認可の拒否、404 が記録されない。
    - 監査ログを通常の INFO ログに置くので、改ざんを防げない。
  - 代案:
    - アップロード・認可拒否・404 も記録対象に加える。
    - 追記専用の保管先に置く。
    - S3 のアクセスログ、または CloudTrail のデータイベントを有効にする。
- **S4 (mid)**
  - 引用箇所: `POST /api/files`
  - STRIDE: 改ざん（Tampering）、権限昇格（Elevation of Privilege）
  - 指摘: 次の3点が書かれていない。
    - 指定された取引先ID が、アップロードする人に許可されたものかの検証。
    - S3 のキーの作り方。
    - ファイル名のサニタイズ。
  - 代案:
    - 取引先ID がアップロード者に許可されたものかを検証すると書く。
    - S3 のキーはサーバーが UUID で作り、利用者が指定したファイル名は使わない。
    - `Content-Disposition` は決まった形式で返す。
    - マルウェアスキャンをするかどうかの方針を決める。
    - S3 バケットは Block Public Access と SSE を有効にする方針を書く。
- **S5 (mid)**
  - 引用箇所: `POST /api/files`「既存のセッション認証」
  - STRIDE: なりすまし（Spoofing）、改ざん（Tampering）
  - 指摘: CSRF 対策が書かれていない。対策が無ければ、攻撃者のページから偽の契約書を登録させられる。
  - 代案: 既存の基盤で CSRF トークン、または SameSite と Origin の検証が効いていることを明記する。
- **S6 (low)**
  - 引用箇所: インターフェース、運用
  - STRIDE: サービス妨害（DoS）
  - 指摘: レート制限が無い。認証済みユーザーが大量に GET したり、20MB のファイルを並行してアップロードしたりできる。
  - 代案: ユーザーごとのレート制限と、アップロードの同時実行数の上限を設計書に書く。
- **S7 (low)**
  - 引用箇所: GET の 302 応答
  - STRIDE: 情報漏えい（Information Disclosure）
  - 指摘: `Location` に入った署名付きURL が、ブラウザの履歴・プロキシのログ・Referer から漏れうる。
  - 代案: `Referrer-Policy: no-referrer` と `Cache-Control: no-store` を付ける。

## 最終報告

> **design-review 結果: `cases/security.md`（契約書ファイル共有API）**
>
> 経路: standard、小規模対象ショートカット（メインが直接レビュー）、security-reviewer（条件判定で起動）、refuter（high/mid の7件をすべて検証し、すべて反証失敗）。arbiter は矛盾が無いため起動していない。
>
> **high（1件）**
> 1. **ダウンロード時に取引先の認可が無い（IDOR）**。`GET /api/files/{file_id}` は、認証済みであれば誰にでも署名付きURL を発行する。他社宛ての `file_id` を入手した取引先ユーザーが、その契約書を取得できる。
>    → URL を発行する前に、「セッションユーザーの所属取引先ID が対象取引先ID と一致する、または社内ロールを持つ」ことを確かめる。一致しない場合は 404 を返す。
>
> **mid（6件）**
> 2. **監査ログに署名付きURL 全体を記録している**。ログを閲覧できる人が5分以内なら認証なしで取得できる。「URL を再現する」という目的も失効するため成り立たない。
>    → URL やトークンは記録しない。`file_id`・ユーザー・取引先・時刻・有効期限だけを残す。ログの閲覧権限を設計書に書く。
> 3. **監査ログの範囲と改ざん耐性が足りない**。アップロード・認可拒否・404 が記録されず、ログは通常の INFO ログに置かれる。
>    → 記録対象を広げる。追記専用の保管先に置く。S3 アクセスログまたは CloudTrail を有効にする。
> 4. **アップロードの入力検証が足りない**。取引先ID の権限検証、S3 キーの作り方、ファイル名のサニタイズが書かれていない。
>    → 取引先ID を検証する。キーはサーバー生成の UUID にする。`Content-Disposition` は決まった形式で返す。マルウェアスキャン、Block Public Access、SSE の方針を書く。
> 5. **POST の CSRF 対策が書かれていない**。
>    → 既存の基盤で CSRF トークン、または SameSite と Origin の検証が効いていることを明記する。
> 6. **S3 と DB の書き込みの一方だけが成功した場合の扱いが無い**。
>    → 順序（S3 → DB）、失敗したときに S3 のオブジェクトを削除すること、参照されないオブジェクトの定期的な掃除を書く。
> 7. **監査ログの書き込みに失敗したとき、黙って欠ける余地がある**。メタデータはあるが実体が無い場合の応答も決まっていない。
>    → 書き込みに失敗したら URL を発行しない（fail-closed）。失敗件数を監視する。実体が無い場合は 502 を返し ERROR ログを出す。
>
> **low（3件）**
> - コンポーネントをコード上のどこに置くかが書かれていない。
> - レート制限・アップロードの同時実行数の上限が無い。
> - 302 で返す URL が漏れないよう、`Referrer-Policy: no-referrer` と `Cache-Control: no-store` を付ける。
>
> **要確認**: 取引先ユーザーと社内ユーザーのロールの分け方と、取引先アカウントの所属取引先ID をどう持つかが設計書に出てこない。これは high の1件目と mid の4件目の対策の前提になる。
>
> **反証で棄却した指摘**: なし
>
> **推奨**: セキュリティの high/mid が出ているため、実装した後で `/security-review` を実行してください。

## security-reviewer の起動

yes。設計に、取引先ユーザーが外部から呼べる公開 API（認証・認可を含む）がある。さらに、秘密情報にあたる署名トークン入りの URL をログに90日保存する。SKILL.md の起動条件（信頼境界を跨ぐデータフロー、または機微情報のログ保存）を、両方とも内容の上で満たしている。
