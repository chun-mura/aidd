## 最終報告

> **design-review 結果: `cases/crosscut.md`（会員ポイント台帳サービス 設計書）— depth=deep**
>
> 対象は横断的な変更（新サービス＋既存2サービスの改修＋移行）で、独立してマージできる単位に分けられないため、分割せずにレビューした。
>
> **最優先の修正: F2 — 利用の引き当てを確定ポイントに限定する**
> - 誰でも毎日の主経路で再現できる回収漏れであり、目標「回収漏れ0件」(L23)、D4、L311 の前提が同時に崩れるため、最優先とした。
> - L269 は残高判定を `confirmed_balance >= 要求ポイント` にする。
> - L270 は対象を `status = 'confirmed' AND expires_at >= 当日` にし、「または NULL」と「NULL の仮付与は最後」を削除する。
> - L116 と L100 の「利用可能残高」の表現を揃える。
>
> **矛盾の裁定**
> - F5 は high とする。D6 で order_id に一意制約が無く、Idempotency-Key だけが二重利用を防いでいるため。
> - F6 は high とする。リリース時に必ず通る経路で、戻す手段が無いため。
> - F5 の直し方は F18 を採る（point_redemptions に `idempotency_key uuid UNIQUE` を持たせ、redemption_requests を廃止する）。保持期間を延ばす案は、別サービスの数値と合わせ続ける必要があり再発しうるため採らない。L109 を満たすために confirmed_balance_after も保存し、失敗レスポンスは保存しない方針も明記する。
> - F4 は 503 を返し、注文サービスのアウトボックス再送に一本化する。L319、redemption_retry キュー、L351 の監視項目は削除する。
> - F4 と F5 は、唯一の防御である冪等キーをどちらも破るので、同時に直すこと。
>
> **high（7件）**
> - F1: L367 の「残高編集」が L246・L371 と矛盾し、台帳に残らず、Reconcile で消える → 削除して `POST /admin/v1/adjustments` に一本化する
> - F2: 仮付与が引き当てられ、返品時に回収されない → 上記のとおり
> - F3: D2 の期限延長が確定処理 (L261) に反映されておらず、規約に反して失効させる → 確定時に会員の confirmed の付与全体の期限を更新する。延長を台帳でどう説明するか、L325、通知後に期限が延びた場合の扱いも決める
> - F4: DB 失敗時に 200 を返す → 503 にしてアウトボックス再送に一本化する
> - F5: 冪等キーの保持 24h < 再送 72h → F18 で解消する
> - F6: 列を削除した後はロールバックが成立しない → D5 の列削除を、安定稼働を確認した後の別リリースに分ける
> - F22（mid から high に上げた）: 返還の API とイベントが同じキャンセルで並走し、ロックが無いので二重返還が起きる → 入口を1つにする、または point_redemptions を FOR UPDATE でロックする
>
> **mid（16件）**

## security-reviewer の起動

**yes**。設計書が次の内容を含み、信頼境界を跨ぐデータフローがあると、意味から判定した。

- **認証認可**
  - PointApi を mTLS で呼び出し元サービス単位に認証している（L85）。
  - PointAdminApi を VPN と社内 SSO で守り、`point_admin`/`cs_member` のロールで認可している（L74）。
- **外部からの入力**
  - メッセージブローカーのイベントを受けて付与している（L160-168）。
- **機微情報の永続化**
  - 会員 ID に紐づく台帳と自由記述の note を10年保持している（L204, L360）。

`--security` も `--no-security` も指定していないので、この判定で起動した。
