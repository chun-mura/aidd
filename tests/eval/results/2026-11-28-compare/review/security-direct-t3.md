## 経路

- **小規模対象ショートカット**: 使った。対象は `cases/security.md` の1ファイル45行で、SKILL.md の条件「1ファイル・100行未満」に当てはまる。Agent 1〜3（構造・データとエラー・実用性）は dispatch せず、メインが直接レビューした。
- **Agent 4（プロジェクト固有観点）**: 起動していない。`.aidd/design-perspectives.md` が無いため。
- **Agent 5（source-verifier）**: 起動していない。`--verify-sources` を付けていないため。
- **Agent 6（aidd:security-reviewer）**: dispatch した。
  - 判断: ショートカットで省けるのは Agent 1〜3 の dispatch だけと解釈した。Agent 6 の起動条件はショートカットとは別に判定する。
  - 理由: この設計は外部公開エンドポイント、取引先という外部ユーザー、認証認可、署名トークン（秘密情報）のログ保存を含み、条件を満たす。
- **refuter（aidd:refuter, sonnet）**: 起動した。high 1件・mid 5件があったため。セキュリティ関連の指摘（S1〜S4）にはセキュリティ反証規則を適用するよう指示した。low は refuter に回していない。
- **arbiter**: 起動していない。standard では、agent 間の矛盾があるか Agent 5 を使った場合だけ起動する。今回は Agent 5 を使っておらず、矛盾も無かった。
  - 補足: M2 と S2・S3 はどれも監査ログを扱うが、M2 は記録失敗時の扱い、S2 はログに書く内容、S3 は記録の対象範囲を問うもので、互いに食い違ってはいない。

## 最終報告

> **design-review 結果: `cases/security.md`（契約書ファイル共有API 設計書）**
> depth=standard。小規模対象のため、構造・データとエラー・実用性はメインが直接レビューした。信頼境界を跨ぐ設計のため security-reviewer を起動した。high と mid は refuter の反証を通過している。
>
> **high（1件）**
> 1. **[S1] ダウンロードの認可が無い**: `GET /api/files/{file_id}` は「認証済みなら」署名付きURLを発行するので、別の取引先のユーザーでも file_id を入手すれば他社の契約書を取得できる。→ 所属取引先ID と `contract_files.対象取引先ID` の一致を必須にし、不一致なら 404 を返す。取引先ロールの持ち方も設計に書く。**リリース前に必ず直すこと。**
>
> **mid（5件）**
> 2. **[S2] 署名トークンをログに保存している**: 署名付きURLを丸ごと INFO ログに90日保管している。有効期間内ならログ閲覧者が認証なしで取得でき、失効後は再現にも使えない。→ トークンは記録せず、file_id・ユーザー・判定結果・リクエストIDなどを記録する。
> 3. **[S3] 監査の対象範囲が足りない**: アップロードと認可拒否が監査対象外。→ 監査対象に加え、ログを改ざんできないようにし、S3 のバージョニングとアクセスログを有効にする。（削除・メタデータ変更の API は今回の範囲外なので対象から除く。）
> 4. **[S4] アップロード経路の防御が書かれていない**: CSRF 対策、S3 キーのサーバー生成、ファイル名のエスケープ、悪性 PDF のスキャン、上書き禁止が書かれていない。
> 5. **[M1] アップロードの整合性**: S3 保存と DB 登録の順序と、片方だけ失敗したときの扱いが無い。→ 「S3 保存の後に DB 登録し、DB 登録に失敗したら S3 オブジェクトを削除する。削除にも失敗したものは定期ジョブで回収する」と、アップロード側のエラー応答を書く。
> 6. **[M2] 監査ログの記録失敗が見えない**: 記録に失敗したときにダウンロードを続けるのか拒否するのかが決まっていない。→ fail-closed にするか、欠落を検知してアラートを出す。
>
> **low（3件）**
> 7. [L1] コンポーネントをコード上のどこに置くか（既存APIサーバー内のディレクトリ）が書かれていない。
> 8. [S5] アップロードと署名付きURL発行にレート制限・同時実行数の上限が無い。
> 9. [S6] バケットの暗号化・非公開化・IAM の最小権限・400 で返す理由の範囲が書かれていない。
>
> **反証で棄却した指摘**: なし
>
> **推奨**: security-reviewer が high と mid のセキュリティ指摘を出したため、実装後に `/security-review` で実コードのセキュリティ監査を行うことを推奨する。

件数: **high 1／mid 5／low 3**

## security-reviewer の起動

**yes**。この設計は次の点で信頼境界を跨ぐ。

- 外部公開の API エンドポイント
- 取引先という外部ユーザーによるアクセス
- 認証と認可
- 署名トークン（秘密情報）をログに保存する

SKILL.md の Agent 6 の起動条件（信頼境界を跨ぐデータフロー、または機微情報をログに保存する）を満たすので、条件判定で起動した。`--security` と `--no-security` はどちらも付けていない。
