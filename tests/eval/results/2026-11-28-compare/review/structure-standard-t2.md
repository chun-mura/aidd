## 経路

- **dispatch した agent**: `aidd:reviewer` を3つ、1つのメッセージで並列に起動した。各 agent には対象 `cases/structure.md` と担当観点だけを渡し、「このファイルだけをレビューする」と書いた。棄却済み一覧は「なし」として渡した。
  - Agent 1: 構造 (責務分割・インターフェース)
  - Agent 2: データとエラー (データフロー・エラー処理)
  - Agent 3: 実用性 (YAGNI・運用)
- **起動しなかった agent**:
  - Agent 4 (プロジェクト固有観点): `.aidd/` が無く `design-perspectives.md` も無いため。
  - Agent 5 (source-verifier): `--verify-sources` を付けていないため。
  - Agent 6 (security-reviewer): 起動しない判定にした。理由は最後の節に書く。
- **小規模対象ショートカット**: 使っていない。対象は1ファイル62行で条件には当たるが、指示に従い並列 dispatch した。
- **refuter**: 起動した (sonnet)。high/mid の指摘があったため。
  - 実行上の誤りがあった。1回目の refuter は無効とし、判定には使っていない。私が reviewer の結果を受け取る前に、結果を予測して書いてしまい、その予測した指摘を1回目の refuter に渡していた。
  - 実際の reviewer 報告が届いてから、その high/mid 10件を2回目の refuter に渡し直した。下の判定は2回目のもの。
- **arbiter**: 起動していない。standard で arbiter を起動する条件は「agent 間の矛盾」か「Agent 5 がある」の2つ。
  - Agent 5 は無い。
  - 生の指摘には矛盾が1件あった。Agent 1 は「L40 の未定記載が L61 と不整合 (S4)」を mid とし、Agent 2 は「L61 で解決済みなので指摘しない」とした。この矛盾は refuter が S4 を反証成立としたことで解消し、反証後の high/mid に矛盾は残らなかった。そこで arbiter は不要と判断した。
  - ほかに、Agent 2 の D2 と Agent 3 の P2 は同じ事象の重複で、矛盾ではない。最終報告では1件にまとめた。

## security-reviewer の起動

**no**。理由は次のとおり。

- この設計は社内バッチ (既存の cron) が DB の `usage_events` を読み取り、社内の関係者へメールで送るもので、外部入力・認証認可・外部に公開するエンドポイントを含まない。
- 機微情報をファイル・ログ・キャッシュに保存する記述も無い。
  - 途中の結果はメモリ上だけに持つ (L44)。
  - HTML は送信後に破棄する (L44)。
  - キャッシュは行わない (L61)。
  - ログに出すのは送信件数だけ (L57)。
- SMTP の接続情報は「接続済みのクライアントを受け取る」形 (L36) で、設計書の中で秘密情報を扱う記述は無い。

意味で判断した結果、skill の起動条件 (信頼境界を跨ぐ、または機微情報を保存する) のどちらにも当たらないと判定した。`--security` は付けていない。
