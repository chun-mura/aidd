## 経路

- **dispatch した agent**: `aidd:reviewer` を3体、1つのメッセージで並列に起動した。
  - Agent 1: 構造（責務分割・インターフェース）
  - Agent 2: データとエラー（データフロー・エラー処理）
  - Agent 3: 実用性（YAGNI・運用）
  - 各 agent には対象パス `cases/structure.md` と担当観点だけを渡し、「このファイルだけをレビューする」と明示した。棄却済み指摘は「なし」として渡した。
- **Agent 4（プロジェクト固有）**: 起動していない。作業ディレクトリに `.aidd/` が無く、`.aidd/design-perspectives.md` も存在しないため。
- **Agent 5（source-verifier）**: 起動していない。`--verify-sources` が指定されていないため。
- **Agent 6（security-reviewer）**: 起動していない。理由は後の節に書く。
- **refuter**: 起動した（`aidd:refuter`、sonnet）。reviewer から high/mid が11件（high 2件・mid 9件）出ており、SKILL.md は「high/mid がある場合だけ起動する」と定めているため。low は規定どおり refuter に回していない。
- **arbiter**: 起動した（`aidd:design-arbiter`）。理由は2つある。
  - deep では、反証を通過した high/mid が残る場合に arbiter を起動する規定になっている。今回は11件すべてが反証を通過した。
  - agent 間に矛盾があった。Agent 1 の S1 は「ReportManager に責務を集めすぎているので分割すべき（high）」とし、Agent 3 の P4 は「YAGNI の観点では集約で妥当（low）」としている。
- **小規模対象ショートカット**: 使っていない。対象は1ファイル62行でショートカットの条件に当たるが、評価の指示に従い、並列 dispatch → refuter → arbiter の完全経路で実行した。
- **issue-split の提案**: していない。対象は単一サービス内の新規モジュール1つで、独立してマージできる単位を2つ以上含まないと判断したため。

### 矛盾の裁定: S1（high: 分割すべき）と P4（low: YAGNI 上は集約で妥当）

**どちらも部分的に正しい。S1 は mid に下げ、論点を「クラスを分けるか」から「責務の線引きが誤っている」に置き換える。**
- 規模は小さい。L7 は単一サービス内の新規モジュール、L61 は数万行、L44 は永続化しないとしている。1つのモジュールにまとめること自体は過剰ではなく、この点は P4 が正しい。
- ただし責務表（L22）は文書の他の箇所と2点で食い違っており、この点は S1 が正しい。
  1. 表は「収集クエリ発行」を `ReportManager` の責務としているが、L34 では呼び出し側が SELECT する。
  2. 表は「cron 設定読込・次回時刻管理」を持たせているが、L56 では cron ジョブとして起動する。
- 直し方は「クエリと期間の決定を内側に寄せ、スケジュール管理を外す」で足りる。5クラスへの分割までは求めない。

### high（1件）

**H1. 公開インターフェースが実装の詳細を呼び出し側に漏らしており、責務表とも矛盾している**（S3・P3・D3 を統合。L22、L30-37、L34、L48）
- `generate(raw_rows, jinja_env, smtp_client) -> None` のままだと、スケジューラと CLI の両方が SELECT、Jinja 環境の構築、SMTP 接続、対象期間（週の境界・TZ）の決定を自前で持つことになる。
- その結果、構築コードが重複し、クエリと期間の担当がわからなくなる。戻り値が None なので、結果も呼び出し側に返らない。
- このインターフェースが M2・M3・M4 を解決できない根本原因になっているため high とする。

### mid（4件）

- **M1. スケジュールを2か所で管理している**（S4・D4、S1/P4 の裁定を統合。L15、L22、L24、L56）
  - 起動するのは cron である。L15 を「既存バッチ cron への登録」に改め、`ReportManager` からスケジュールの責務を削り、`report.yaml` は宛先だけにする。
- **M2. 同じ週を二重に送れ、冪等性と再実行方針が無い**（D1・P2 と、D2 の重複送信部分を統合。L30、L44、L49、L56）
  - 重複の経路は、スケジューラ、手動 CLI、SMTP の全体リトライの3つ。送ったメールは取り消せない。
  - 送信済みを `week_start` 単位で記録する。送信済みの週は既定でスキップし、CLI に `--force` を付けたときだけ再送する。
- **M3. 「silent failure を作らない」（L52）という保証が2つの経路で崩れている**（D2 の部分失敗と D5 を統合。L46-52）
  - 経路1: `smtplib.sendmail` は一部の宛先が拒否されても例外を上げない。
  - 経路2: 0件のとき、上流で障害が起きていても空のレポートが正常に送られる。
  - 拒否された宛先の dict が空でなければ失敗とする。0件のときは警告を出して失敗終了させる。どちらの判定結果も H1 の戻り値に載せる。
- **M4. 失敗した段階・所要時間・行数のログが無く、cron が起動しなかったことも検知できない**（P1・D7 を統合。L52、L57）

### 最優先で直す1点

H1 として、`generate` を「対象週を受け取り、結果を返す」形に改める。

```python
@dataclass
class ReportResult:
    week_start: date
    row_count: int
    sent_to: list[str]
    rejected: dict[str, tuple[int, bytes]]   # sendmail の戻り値
    skipped_reason: str | None               # 送信済み / 0件 など

def run_weekly_report(week_start: date, *, force: bool = False, dry_run: bool = False) -> ReportResult
```

- 週の境界は設計書で1つに決める（例: JST の月曜 0:00 から翌月曜 0:00 の直前まで）。
- 呼び出し側は日付とフラグだけを渡す。クエリ、Jinja、SMTP の組み立てはモジュールの内側で行う。
- 戻り値があれば、M2（送信済みスキップ）、M3（部分拒否と0件）、M4（ログ）を同じ場所で判定できる。

**件数: high 1 / mid 4 / low 5**

`/security-review` の推奨: なし。Agent 6 を起動しておらず、セキュリティに関する high/mid も出ていないため。

## security-reviewer の起動

**no**

`--security` も `--no-security` も指定されていないため、SKILL.md の条件に従い、内容の意味から判定した。
- **信頼境界を越えるデータフローは無い**:
  - 入力は社内の `usage_events` テーブルを読むだけで、外部からの入力は無い。
  - 認証・認可の設計は対象外。
  - 外部に公開するエンドポイントも無い。呼び出し元は社内のバッチ cron と手動 CLI だけ。
  - メールの宛先は設定ファイルにある社内の「関係者」で、送るのは社内ダッシュボードの集計レポートである。
  - SMTP は「接続済みクライアント」として受け取る前提で、認証情報の扱いは設計書に書かれていない。
- **機微情報をファイル・ログ・キャッシュに保存しない**:
  - 途中の結果はメモリにしか置かない（L44）。
  - HTML は送信後に破棄する（L44）。
  - キャッシュは使わない（L61）。
  - ログに出すのは送信件数だけ（L57）。

以上から、起動条件のどちらにも当たらない社内向けのバッチ処理と判断した。
