## 経路

- **dispatch した agent**: `aidd:reviewer` を3つ、1つのメッセージで並列に起動した。
  - Agent 1 は構造 (責務分割・インターフェース) を担当した。
  - Agent 2 はデータとエラー (データフロー・データモデル・性能・エラー処理) を担当した。
  - Agent 3 は実用性 (YAGNI・運用) を担当した。
  - 各 agent には、対象パス `cases/data-error.md` と担当観点、「棄却済み指摘: なし」だけを渡し、「このファイルだけをレビューする」と指示した。
- **起動しなかった agent**:
  - Agent 4 (プロジェクト固有) は、`.aidd/design-perspectives.md` が無いので起動していない。
  - Agent 5 (source-verifier) は、`--verify-sources` が無いので起動していない。
  - Agent 6 (security-reviewer) は、条件判定で起動しないと決めた (下の節を参照)。
- **小規模対象ショートカット**: 使っていない。対象は1ファイル45行だが、指示に従って並列 dispatch の経路を取った。
- **refuter (`aidd:refuter`, sonnet)**: high/mid の指摘があったので起動した。2回に分けた理由は次のとおり。
  - **1回目は手順の誤り**: reviewer の報告が届く前に、私が会話の中に reviewer の結果を予測で書き、その予測から作った F1〜F6 を refuter に渡してしまった。後から届いた実際の報告と照らし合わせると、F1〜F4 と F6 は実際の指摘とほぼ同じ内容だった。F5 (監視不足) は実際には Agent 3 が mid と付けていたので、mid として扱い直した。
  - **2回目で穴を埋めた**: 実際の報告にあって F1〜F6 に入っていなかった mid を G1〜G7 として追加で反証にかけた。これで、実際に出た high/mid はすべて refuter を通っている。
- **arbiter (`aidd:design-arbiter`)**: 起動した。deep 構成で、反証後に high/mid が残り、agent 間の矛盾もあったため。
  - 代案の矛盾: DB を正本にする案と、Redis だけに保持する案に分かれた。
  - 深刻度の食い違い: 配置・インターフェース・境界の指摘で深刻度が揃っていなかった。
  - 最終報告は arbiter の結果をそのまま使う。

## refuter の判定

1回目 (F1〜F6) と2回目 (G1〜G7) の13件は、すべて**反証失敗**だった。

|---|---|---|
| F1 タイムアウト→在庫0 (L38) | 反証失敗 | L38 に書いてあるとおり。欠測を区別する手段も、タイムアウトを観測する手段も無い |
| F2 書き込み失敗を数えず exit 0 (L39) | 反証失敗 | L29 と矛盾する。L45 は exit code しか見ないので検知できない |

| F4 廃番商品の復活 (L34, L15) | 反証失敗 | 有効な商品に絞る記述も、論理削除も、排他も無い |

| G3 WMS 境界が無い | 反証失敗 | 表に WMS 連携の担当コンポーネントが無い |

## 最終報告

(arbiter の裁定をそのまま載せる)

**矛盾の裁定**
- **M1 の代案**: DB を正本にし、更新を1つのコンポーネントに集約し、Redis は TTL 付きの派生キャッシュにする案を採る。「Redis のみ保持」案は採らない。L34 の設計が DB を永続層として前提にしており、Redis が消えると次の同期まで返す値が無くなって、L11 の目的と両立しないため。
- **M9〜M11**: low に下げる。L7 で要約形式と宣言しており、データの正しさには影響しない記述粒度の問題であるため。
- **重複の整理**: L2 は M5 に統合する。M2 は M1 から起きる具体的な不具合なので、M1 の下に置く。

**high**
- **H1 (L38) タイムアウトした商品に在庫0を書き込む**
  - 欠測が「在庫切れ」として確定し、サイトに出る。書き込みは成功扱いなので失敗として観測されない。
  - M4 と重なると、WMS が全件タイムアウトしたときに全商品が在庫0になり、しかも exit 0 で終わる。
  - 代案: 書き込まずに前回値を保持する。失敗件数に数える。商品ごとに最終同期時刻を持たせる。
- **H2 (L39) 個別商品の書き込み失敗を数えず exit 0 で終わる**
  - L29 と矛盾し、L45 の監視では検知できない。
  - 代案: failed に数える。商品 ID 付きで ERROR ログを出す。失敗率が閾値を超えたら非ゼロ終了にする。

**mid**
- **M1 (L22, L34)**: DB と Redis の両方に持っているが、正本が決まっていない。書き込みが原子的でなく、書き込む主体も2つに分かれている。代案は上の裁定のとおり。
  - **M2 (L34)**: 廃番削除の後に `SyncBatch` が書き戻すと、在庫行とキーが復活する。代案: 有効な商品だけを書き込む、または論理削除にする。
- **M3 (L15, L22)**: 多重起動に対する排他と冪等の記載が無い。代案: ジョブ単位のロックを取る、または取得時刻を比べてから上書きする。
- **M4 (L40)**: 「5xx連続」の閾値が無く、タイムアウトが全面障害の判定に入っていない。H1 を直しても、全件タイムアウトで exit 0 になる問題は残る。
- **M5 (L45、L2 を統合)**: 所要時間、失敗件数・タイムアウト件数、最終成功時刻、鮮度アラートが無い。
- **M6 (L44)**: ロールバックがジョブの削除だけで、最後に書いた値がそのまま配信され続ける。データと `StockApi` を切り戻す手順が無い。
- **M7 (L22, L38, L40)**: 想定件数、呼び出し方式、所要時間、タイムアウト値が書かれておらず、5分間隔に収まる根拠が無い。

**low**
- M8: `inventory(product_id)` のキー/インデックスと、Redis/DB 障害時に `StockApi` がどう失敗するかが書かれていない。
- M9: コンポーネントの配置が書かれていない。
- M10: I/F の定義が足りない。H1 を直すと「値が不明」「値が古い」をどう返すかを決める必要があるので、その範囲だけは H1 と一緒に決めること。
- M11: WmsClient の境界が無い。
- L1: read-through がどこにあるか不明。
- L3: リトライと再実行の方針が書かれていない。
- L4: Repository と Cache の分割は維持してよい。

**横断して見えたこと**: H1・H2・M4・M5 が重なると、設計の中に「正常な値」と「欠測・失敗・古い値」を見分ける手段が1つも無い。最悪の場合、全商品が在庫切れ表示のまま、監視上は正常に見え続ける。

**最優先で直すべき1点: H1 (L38)**。誤った値を自ら作ってユーザー向けの表示に出すのは H1 だけで、全件タイムアウトのときは被害が全商品に広がる。L38 の書き換え案は次のとおり。
- タイムアウトした商品は書き込まず、前回値を保持する。
- タイムアウト件数として数え、WARN ログを出す。
- `synced_at` を持たせ、古い値は「在庫不明」として返す。
- タイムアウトの割合が閾値を超えたら非ゼロ終了にする。これで M4 も同時に解消する。

この裁定と代案は判断材料のたたき台です。設計書に反映する前に、担当者が内容を確認してください。

**件数**: high 2件 / mid 7件 (M2 は M1 の下に表示) / low 7件 (L2 は M5 に統合)

**`/security-review` の推奨**: 出していない。Agent 6 を起動しておらず、`--no-security` で抑止したケースにも当たらないため、SKILL.md の条件を満たさない。

## security-reviewer の起動

**no**。理由は次のとおり。
- `StockApi` は「サイト内部からのみ参照」(L30) の内部エンドポイントで、外部に公開していない。
- 認証認可の設計は含まれていない。
- 個人情報・プロンプト・認証情報などの機微情報を、ファイル・ログ・キャッシュに保存する記述も無い。Redis に入るのは在庫数だけ。
- L40 の「認証エラー」は WMS 側の障害分類として触れているだけで、秘密情報の保管・受け渡しは設計の対象になっていない。

以上から、意味の上で信頼境界を跨ぐデータフローを持たない内部バッチだと判断した。
