> **design-review 結果: `cases/data-error.md`（在庫数同期バッチ 設計書）**
> 経路: standard。小規模対象のためメインが直接レビューし、high/mid は refuter による反証を経たもの。arbiter は起動条件を満たさないため起動していない。
>
> ### high（2件）
> 1. **タイムアウト時に在庫 0 を書き込む（:38）。** 取得できなかった値が実在庫 0 と区別できない形で正しい値を上書きし、在庫がある商品が品切れ表示になる。障害としても観測されない。
>    → タイムアウトした商品は書き込まずに直前値を残し、失敗件数に数える。在庫に更新時刻を持たせて鮮度を判定する。
> 2. **書き込み失敗を数えずに exit 0 で終わる（:39, :29, :45）。** 監視は exit code だけなので、全件が失敗しても成功扱いになる。DB と Redis の部分書き込みによる不整合も残る。
>    → 失敗を `SyncResult` に計上し、失敗率が閾値を超えたら非 0 で終了する。失敗した商品 ID をログに出す。DB と Redis の書き込み順序と整合回復の方法を決める。

> ### mid（3件）
> 3. **DB と Redis の二重管理を、2者が直接操作している（:34, :22-24）。** どちらが正か、書き込み順序、整合回復が書かれていない。バッチと廃番処理が競合すると、廃番商品の在庫が復活する。
>    → DB を正、Redis を TTL 付きのキャッシュとし、書き込み経路を1箇所に寄せる。廃番商品は書き込み時に除外する。

>    → 件数と所要時間を見積もり、ページングまたは差分取得の方針と、5分を超えたときの扱い（多重起動の抑止）を書く。

## security-reviewer の起動

**no**

`--security` も `--no-security` も指定されていないため、内容から判定した。起動条件のどちらにも当たらないと判断した。

- **信頼境界を跨ぐデータフロー:**
  - `StockApi` は `/internal/` の読み取り専用エンドポイントで、サイト内部からだけ参照される（:30）。外部に公開されるエンドポイントではない。
  - WMS は社内システムから在庫数を取り込む連携で、外部の利用者からの入力ではない。
  - 認証認可や秘密情報の扱いは、設計の対象として書かれていない。:40 の「認証エラー」は失敗の分類として出てくるだけである。
- **機微情報の保存:** Redis と DB に保存するのは商品ごとの在庫数だけで、個人情報・プロンプト・認証情報は含まれない。

判断が分かれうる点が1つある。「サイト内部からのみ参照」をどう担保するか（ネットワークでの制限など）は、設計書に書かれていない。ただし、そこで漏れうるのは在庫数という機微でない情報なので、起動条件には当たらないと判断した。
