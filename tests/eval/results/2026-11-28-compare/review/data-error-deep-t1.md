## 経路

- **dispatch した agent**: `aidd:reviewer` を3体、1つのメッセージで並列に起動した。
  - Agent 1: 構造
  - Agent 2: データとエラー
  - Agent 3: 実用性
  - 各 agent には対象パス `cases/data-error.md` と担当観点だけを渡し、「このファイルだけをレビューする」と明示した。棄却済み一覧は「なし」として渡した。
- **起動しなかった agent**:
  - Agent 4(プロジェクト固有): `.aidd/design-perspectives.md` が無いため起動しなかった。
  - Agent 5(source-verifier): `--verify-sources` が無いため起動しなかった。
  - Agent 6(security-reviewer): 起動しなかった。理由は後述の「security-reviewer の起動」に書いた。
- **refuter**: 起動した(sonnet)。high/mid の指摘があったため。3体の指摘で内容が重なるものは12件(F1〜F12)にまとめてから渡した。low は渡していない。
- **arbiter**: 起動した。理由は2つある。
  - deep では、反証後に high/mid が残れば arbiter を起動する。
  - agent 間に矛盾があった。F3 を Agent 3 は high、Agent 2 は mid と評価していた。
- **小規模対象ショートカット**: 使っていない。対象は1ファイル・45行だが、指示に従って並列 dispatch の経路で処理した。
- **issue-split の提案**: しなかった。対象は単一バッチとキャッシュ層の変更で、独立してマージできる単位が2つ以上あるとは判断しなかったため。

### 横断的な指摘(arbiter が新たに見つけたもの)
- **[high] WMS が遅くなるだけで、全商品が「在庫0」と表示され、バッチは正常終了する。**
  - 次の4点が重なって起きる。
    1. F1: タイムアウトした商品は0として書かれる。
    2. F6: L40 でバッチを失敗にする条件は認証エラーと5xx連続だけで、タイムアウトの連続は入っていない。
    3. F2: 書き込みの失敗も数えない。
    4. F8: 監視は exit code と件数ログだけで、0で書いた件数も「同期した件数」に含まれる。
  - 結果として、WMS が落ちずに遅くなっただけでサイト全体が欠品表示になり、どの監視にも引っかからない。

### 最優先で直すべき1点: F1(L38)のタイムアウト時の0書き込みをやめる

F2 より優先する理由:
- F2 で書けなかった商品は前回の値のまま残るので、表示はそれほど壊れない。
- F1 は誤ったデータを積極的に書き込み、上の横断的な指摘のとおりサイト全体の欠品表示につながる。

L38 の差し替え案:
- タイムアウトした商品は書き込まず、DB と Redis の前回値を残す。
- `SyncResult` に `timeout_count` を追加する。L39 の書き込み失敗も `failed_count` に数える(これで F2 も直る)。
- `(timeout_count + failed_count) / 対象件数` が閾値(例: 5%)を超えたら、ERROR ログを出して非0で終了する。これで既存の監視で検知できる。
- `inventory` と Redis の値に `synced_at` を持たせる。StockApi は一定時間(例: 30分)より古い値を「在庫数不明」として返し、表示側が欠品とは別に扱えるようにする。

注記: 閾値と時間は例として置いた値で、未確認。実際の値は担当者が業務要件から決めること。設計書への反映とレビューの最終判断も担当者が行うこと。

## security-reviewer の起動

**no**

理由: 対象の内容から、信頼境界を跨ぐデータフローにも、機微情報の保存にも当たらないと判定した。
- **公開エンドポイント**: StockApi は `/internal/stock/{product_id}` で、L30 に「サイト内部からのみ参照」とある。外部に公開されたエンドポイントではない。
- **扱うデータ**: 在庫数だけで、個人情報や認証情報など機微な情報を DB・Redis・ログに保存する記述は無い。
- **WMS 連携**: 社内システムとのバッチ連携で、設計書は認証や秘密情報の扱いを設計対象にしていない。L40 で認証エラーに触れているのは、失敗を判定する条件としてだけ。
- 以上から、SKILL.md の「内部ライブラリ・バッチ処理などそのどちらにも当たらない設計」に当たると判断した。

ただし、WMS の認証情報をどう保管するかが実装段階で決まる場合は、別途確認が必要。
