## 経路

- **対象**: `cases/crosscut.md`（1ファイル・385行）。フラグは `--depth=standard`。`--security` と `--verify-sources` は付けていない。`.aidd/` は無いため、棄却一覧の読み込みと Agent 4（プロジェクト固有観点）は省いた。
- **小規模対象ショートカット**: 使っていない。対象は100行を超えており、実行指示でも並列 dispatch が求められている。
- **issue-split の検討**: 提案しない。新サービス・注文サービス・会員サービス・移行が台帳の契約（API・イベント・残高移行）でつながった横断的変更で、独立してマージできる単位に分けられない。このレビューをそのまま続けた。
- **並列 dispatch**: 1メッセージで次の4つを起動した。
  - aidd:reviewer ×3: Agent 1（構造）、Agent 2（データとエラー）、Agent 3（実用性）
  - aidd:security-reviewer ×1: Agent 6
  - aidd:source-verifier（Agent 5）は、フラグが無いため起動していない。
- **refuter**: 起動した（aidd:refuter、sonnet、1回）。理由は、high/mid の指摘があったため。4 agent の high/mid 指摘を重複統合して26件（F1〜F26）にし、引用行を付けて渡した。low は規定どおり refuter に渡していない。
- **arbiter**: 起動していない。standard では、agent 間の矛盾があるか Agent 5 がある場合だけ起動する。Agent 5 は無く、内容の矛盾も無かった。違いは F6 の深刻度だけ（Agent 2 は high、Agent 6 は mid）で、指摘の中身は一致している。メインで high に統一した。理由は、目標「改定後の規約どおりにポイントを失効させる」（L22）を直接満たせなくなるため。

## 最終報告

> # design-review 結果: 会員ポイント台帳サービス 設計書（`cases/crosscut.md`）
>
> 経路は standard。reviewer 3つと security-reviewer を並列で動かし、high/mid は refuter で反証した。反証が成立した指摘は無い。arbiter は起動していない（agent 間に矛盾が無く、Agent 5 も無いため）。
>
> ## high（7件）
> 1. **F1 CS の「残高編集」が台帳を経由せず `point_balances` を直接書き換える**（L367）。次の点と矛盾する。
>    - 書き込みの唯一の入口と、手作業による更新の禁止（L63, L246）
>    - DB への接続権限（L371）
>    - 翌日の Reconcile による上書き（L248）
>
>    台帳に記録も `operator_id` も残らず、権限も定義されていない。実行者による不正と監査不能を招く。→ この手順を削除し、訂正は `POST /admin/v1/adjustments` に一本化する。
> 2. **F3 仮付与が利用できてしまう**（L269-270 が、L51・L101・L116 と矛盾）。仮付与を使ってから返品すると、利用済みの分を回収できない（L311 の前提が崩れる）。→ 残高判定は `confirmed_balance` だけ、引き当ては `status='confirmed'` だけにする。
> 3. **F2 `members.point_balance` 列を同じリリースで削除するため、ロールバックが成立しない**（L302, L339, D5）。→ 列削除はデプロイと動作確認の後の別ステップかリリースにする。削除前にスナップショットを取り、復元手順をロールバック節に書く。
> 4. **F4 冪等キーの保持期間（24時間、L361）が再送期間（72時間、L320）より短く、二重利用になる。** → 保持を再送の上限より長くする（例: 7日）。
> 5. **F5 DB 書き込みの失敗時に、残高を確認せず 200 を返す**（L319）。silent failure になり、`redemption_id` も決まらない。キューの保存先と消費側も定義されていない。→ 503 を返し、タイムアウト時と同じ「ポイント処理待ち」の再送（L320）に統一する。`redemption_retry` は削除する。
> 6. **F6 D2（確定のたびに確定ポイント全体の期限を延長する）が、データフローのどこにも実装されていない**（L261, L285-289）。このままでは規約どおりに失効しない（L22 の目標に反する）。→ 確定トランザクションで同じ会員の確定付与の期限を一括で延長し、台帳に記録する。または D2 を付与ごとの期限に改める。いずれの場合も法務との再確認が必要。
> 7. **F7 応答を受け取れないまま 72 時間後にキャンセルすると、利用が返還されずに残る**（L166, L278, L320）。→ `Idempotency-Key` か `order_id` で返還できるようにする。キャンセル後に届いた利用要求は拒否する。
>
> ## mid（19件）
> - **F8** 返品イベントが遅れたり DLQ に滞留したりすると、確定済みの付与への返品が実際に起こる（L313）。→ 確定前に返品状態を照会する。確定後の返品は自動で取り消す。
> - **F9** BalanceReconcileJob に排他が無く、並行する更新を古い値で上書きする（L248）。→ 会員行を `FOR UPDATE` し、同じトランザクションで再計算する。
> - **F10** 利用以外の書き込み経路（確定・失効・返還・返品取消）に排他制御が書かれていない。→ 「全経路で会員行をロックし、状態を再読み込みしてから判定する」という共通ルールを書く。
> - **F11** confirm 行が0ポイントのため、台帳だけでは確定残高と仮残高を導出できない（L220, L248, L262）。→ 再計算の入力は `point_grants` の集計だと明記する。
> - **F12** インデックスの前提が L213 以外に無い。管理台帳 API は全行を返す（L158）。→ `point_grants` の `(status, confirm_at)`・`(status, expires_at)`・`(member_id, status, expires_at)`、`point_ledger` の `(member_id, ledger_id)` を明記し、管理台帳 API をページングする。
