## 指標

採点の対象は各試行の最終報告である (設計レビューの構成は `## 最終報告`、baseline は回答全体)。シードは、キーの一致判定基準で意味的に照合した。安全上重要なシードの規則は SKILL.md の C 節のとおりで、期待深刻度が high のもの、または対応観点が「セキュリティ」で始まるもの。

| ケース | シード |
|---|---|

| data-error | DE2・DE3 |
| security | SEC1・SEC2・SEC3・SEC7 |
| crosscut | CC1・CC2・CC3・CC6 (high)、CC11・CC14・CC15・CC18 (セキュリティ) |

- data-error と security のキーにはデコイが無い (「—」)。structure (D1) と crosscut (CD1〜CD4) のデコイ誤検出は、全試行で0。
- ノイズ率は、最終報告の指摘のうち、キー外で「判断保留」か「誤検出」と確定したものの割合。
- 指摘1件が複数のシードに当たるもの (例: structure standard t2 の high1 が S1 と S4) は、どのシードも検出として数えた。複数のシードを組み合わせた横断の high (data-error deep t1・t3、security deep t2) は、シードの合成として扱い、キー外の指摘には数えていない (指摘件数には含む)。
- 最終報告の1件の指摘は、主となる論点1つに割り当てた (シードに当たる部分があればシードとして数え、キー外に数えない)。
- baseline との差は、同じ試行番号の baseline との差 (high/mid/low の順)。件数が増えたことを、検出の改善とも見逃しの埋め合わせとも数えない。
- 一致の判定で、次の約束を置いた (キーの基準の読み方):

## キー外指摘の分類

## 過去の比較と違う条件

`2026-11-07-baseline.md`・`2026-11-22-crosscut-comparison.md` とは次の点で違うので、数値を直接並べない。予備測定 (`2026-11-28-compare-prelim.md`) とは、試行数 (1 → 3) と git SHA (27a1845 → f343b96。差分は予備測定の結果ファイルの追加だけで、比べる資産は同じ) が違う。

- **実行の仕方**:
  - 過去は、メインのセッションの Agent tool で reviewer などを起動した (A)。baseline も `general-purpose` の agent に `model: "opus"` で行わせた (B)。
  - 今回は、構成ごとに新しい `claude -p` のセッションを起動した (`--model opus`、baseline は `--tools ""`)。利用者の設定 (CLAUDE.md・hook・他のプラグイン) はそのまま読み込まれる。
- **偽指摘**: 過去の design-review 側 (A) は、refuter に偽指摘を混ぜた。今回は混ぜていない。
- **深さ**: 過去の A は deep だけだった。今回は deep・standard・direct を比べた。
- **版とキー**:
  - 過去は 0.51.0・0.54.0 で、今回は 0.93.0。
  - キーは昇格で増えている。拡張検出の分母が違うので、比べられるのはコア検出だけである。
- **試行数**: 過去は各3回、今回も各3試行。
- **採点**:
  - 過去の 11-07 では、メインが要約した出力を採点エージェントが採点した。
  - 今回は、メインが最終報告の全文をキーと照合した。キー外の指摘は判定エージェント2体で分類し、割れたものと誤検出はユーザーが確定した。

## 未測定の項目とそろえきれなかった条件

- **待ち時間**: meta の `duration_ms` は最後の `result` の区間だけである。全 `result` の合計も、`result` の間の待ち時間を含まない。runner の記録では、1試行の実時間 (起動から抽出の終わりまで) は 0.65〜8.2 分だった (最長は crosscut standard t2、次が crosscut deep t3 の 8.0 分)。
- **agent ごとの実測モデル**: modelUsage はモデル別の合計だけなので、arbiter が opus で動いたかは分からない。
- **baseline の環境**: aidd 0.87.0 を含む利用者のプラグインが読み込まれた (ツールなしなので使われてはいない)。利用者の指示に由来するとみられる文言 (最終判断は担当者が行う旨) が、一部の回答の末尾に混ざっている。
- **組織の指示**: 実行担当のセッションは、利用者の設定と組織の指示を読み込んだ状態で動いた。`--safe-mode` は使っていない。`--safe-mode` でも組織の指示は外れないことを、coordinator が別に確かめている。したがって、組織の指示を外した条件はどちらの方法でも作れず、その影響は測っていない。
- **時間帯**: 実行は C2 の順に直列で行った。各試行番号の中でケースと構成を回しているので、試行の間で時間帯が偏る。
- **再 dispatch の理由**: 同じ種類の agent が複数回出た試行 (経路の注記) の理由は、個別に確かめていない。
- **direct の security-reviewer**: security の direct では全3試行で Agent 6 を起動した。予備測定の direct は起動していない。ショートカットで Agent 6 を起動するかは、SKILL.md の読み方で割れている。
- **leak_guard の誤検知**: 準備中、Read ツールの leak_guard フックが `skills/eval/SKILL.md` を秘密を含むと誤検知し、読み込みを拒否した (予備測定と同じ)。そのため SKILL.md は Bash で読んだ (測定の手順には影響なし)。
