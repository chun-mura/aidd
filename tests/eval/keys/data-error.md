# 正解キー: cases/data-error.md (在庫数同期バッチ)

このファイルは /aidd:eval の採点専用。**design-review の実行が完了するまで読んではならない** (reviewer への汚染防止)。

## シード欠陥

コアシード (バージョン間比較の分母): **DE1, DE2, DE3**。DE4, DE5 は昇格シードで拡張検出率のみに数える。

| ID | 該当セクション | 対応観点 | 期待深刻度 | 欠陥 | 一致判定基準 |
|---|---|---|---|---|---|
| DE1 | データフロー | データフロー | mid | 在庫数を DB と Redis の両方に保持し、`SyncBatch` と `ProductAdminService` がそれぞれ両方を直接更新している (持ち主不明の二重管理。生存商品は5分ごとの全件上書きで回復するが、廃番時の片系削除失敗は恒久的な不整合として残る) | 在庫数の二重管理・書き込み経路の複線化・不整合リスクを指摘していれば検出。解決策の形 (単一書き込み経路・TTL 等) は問わない |
| DE2 | エラー処理 | エラー処理 | high | 個別商品の書き込み失敗を catch してスキップし、失敗件数にも数えず exit code 0 で正常終了する (完全な silent failure。監視にも `SyncResult` にも現れない) | 個別失敗の握りつぶし・失敗が観測不能である旨を指摘していれば検出 |
| DE3 | エラー処理 | エラー処理 | high | WMS タイムアウト時に在庫数 0 として同期する (欠測を偽データで埋める。在庫ありの商品が「在庫切れ」表示になる実害。WMS 全体が遅延すると、全商品が 0 で上書きされたまま exit 0 が続く。タイムアウトは40行の全面障害判定に含まれない) | タイムアウト時の 0 埋めが誤データを作る旨を指摘していれば検出。「前回値保持にすべき」等の代案の形は問わない |
| DE4 | 運用 | 運用 | mid | ロールバックが「ジョブ定義の削除」のみで、書き込み済みの在庫データ (誤データを含む) は DB と Redis に残り、`StockApi` は停止時点の値を返し続ける。復旧・再同期の手順がない | ロールバック後に残る在庫データの扱い (再同期・修復・参照の切替) がない旨を指摘していれば検出 |
| DE5 | 運用 | 運用 | mid | 監視が exit code と同期件数の INFO ログだけで、最終成功時刻 (データの鮮度) を観測しない。バッチが起動しない・止まった場合は exit code が出ないため、`StockApi` が古い在庫数を返し続けても検知できない | 最終成功時刻・データ鮮度を観測できず、同期の停止を検知できない旨を指摘していれば検出。所要時間・レイテンシ等の監視項目不足だけの指摘は検出としない |

(DE4 は 2026-11-07 の評価でキー外指摘として検出され、ユーザー承認により昇格。DE5 は 2026-11-07 の3回の評価すべてで監視不足として挙がり、3回目の後にユーザー承認により昇格 (昇格日 2026-11-07)。ケース作成時の意図的シードは DE1-DE3 のみ)

期待深刻度の変更 (2026-11-07、ユーザー承認): DE1 high → mid、DE3 mid → high。2026-11-07 の2回の評価で arbiter が2回とも同じ値を付け、reviewer の深刻度ルーブリック (high = 本番障害等の実害、mid = 範囲限定) に照らしてそちらが妥当と判断した。それより前の結果ファイルの深刻度一致は変更前の期待値で採点されている。
